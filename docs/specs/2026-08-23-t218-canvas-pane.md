## 1. Problem

Stated in full in the [PRD](../prds/T218-canvas-pane.md) §1. In one paragraph: an
agent-produced visual is delivered today through `open_file` into a **read-only** viewer
pane. The moment a mockup is on screen is exactly the moment the operator wants to point
at it — circle a wrong number, drag a card, drop a note saying "this row belongs below the
hairline". Instead they must retype the correction as prose into the terminal. The canvas
pane makes the picture editable and makes the agent able to read the edits back.

The feature is **the loop**, not the drawing surface. A canvas the operator draws on alone
is a toy; a canvas the agent renders into alone is the viewer we already have. §7 (Save)
and §8 (the verb) are what make it a loop, and the live loop test recorded on the card is
the evidence that they are load-bearing rather than plumbing.

---

## 2. What v1 is, and what it is not

**v1 is:** a pan/zoom canvas pane, backed by one plain JSON file scoped to one worktree,
where the agent adds and updates nodes and edges through an MCP verb, and the operator
drags, draws, renames, connects, deletes and pastes — committing their work with an
explicit **Save** that the agent then reads.

**v1 is not:** freehand ink, multi-page canvases, real-time collaboration, a merge
algorithm, a shared project-wide board, or a general diagram-authoring product. Each
exclusion has a reason, listed in the [PRD](../prds/T218-canvas-pane.md) §4.

### 3.3 Why the existing canvas is not the base

The gap is not one of size. It is one of **kind**.

`PrStackCanvas` is a _read-only view of a graph that exists somewhere else_. Its own
comments say so — the arrangement rule is "the arrow carries the chain, the coordinate
never does", and a moved card is "provenance, not a state to act on"
(design.md §6 → PR Stack Canvas). Every node corresponds to a live GitHub PR; the
operator's only authority is where a card sits, and even that is a _decoration layer_
(`overrides`) painted over a computed layout that main recalculates on every refresh.

T218 needs the opposite program: a **document with two authors**, where a node exists
because somebody made it, persists because somebody saved it, and carries a stamp saying
which of the two authors that was (§4.4). There is no computed layout to fall back to and
no external source of truth to re-derive from — the file _is_ the truth.

Generalising the first into the second means writing selection, history, transform,
snapline, ports, routing, inline editing, and a serialization format — every expensive
item in the table above — and then retrofitting T198 onto the result without regressing a
shipped feature. What we would inherit for that price is the ~150 lines of pan/zoom/drag
that are the cheapest and least risky part of the job, and which X6 supplies anyway.

Concretely: X6 2.19.2 plus four 2.x plugins was **verified running** with selection,
history, transform, snapline, drag-to-create-a-box, port-to-port Manhattan-routed arrows
that bind and follow, inline rename, and an exact `toJSON → clear → fromJSON` round-trip —
in a throwaway prototype, in a real browser (spike README). That is the whole 85% we would
otherwise be writing, already de-risked.

**One deliberate loss, recorded honestly:** X6 renders through its own SVG/HTML pipeline,
so the pane will not share `PrStackCanvas`'s dot-grid CSS or its floating-control markup.
Those get rebuilt against X6's grid API and Capy's tokens (U2 AC-3). That is a small,
visible cost, and it is the correct trade against the table above.

### 3.4 Why X6, and the version pin — the pin is load-bearing

**Pin `@antv/x6` to `2.19.2`, with the 2.x plugins:**

| Package                     | Version  |
| --------------------------- | -------- |
| `@antv/x6`                  | `2.19.2` |
| `@antv/x6-plugin-selection` | `2.2.2`  |
| `@antv/x6-plugin-history`   | `2.2.4`  |
| `@antv/x6-plugin-transform` | `2.1.8`  |
| `@antv/x6-plugin-snapline`  | `2.1.7`  |

**The reason (spike README trap 1), which must be written as a comment at the dependency
site in `package.json`:**

1. **X6 core 3.x has no working plugin ecosystem.** The 2.x plugins throw
   `TypeError: t.View.dispose is not a function` against core 3.x — 3.x removed the
   disposable-decorator API they compile against. Verified live: all four failed to load,
   followed by `X6PluginSelection.Selection is not a constructor`.
2. **The `3.0.0` plugin releases are empty stubs** — each package ships CSS and **zero
   `.js` files**. They cannot be used at all.
3. **The plugins' npm `latest` dist-tag still points at 2.x.** So
   `npm i @antv/x6@latest @antv/x6-plugin-selection` silently produces the _broken_
   3.1.8-core + 2.x-plugin pairing. The failure mode of an unpinned or "helpfully bumped"
   install is a pane that renders nodes and has no selection, no undo, no resize and no
   snaplines — which looks like a bug in our code, not a dependency mismatch.

Treat core 3.x as unusable until AntV republishes real 3.x plugins. **A dependency bump
that moves X6 without re-verifying the four plugins load is a regression**, and U2 AC-5
makes that testable rather than a matter of vigilance.

### 3.5 The Excalidraw arm — closed explicitly, not left hanging

**The Excalidraw spike is not run, and Excalidraw is rejected.** Stated here rather than
silently skipped, per the plan's CP1 gate. Reasons, in order of weight:

1. **The evidence is already asymmetric.** X6 was verified doing the specific things this
   card needs, in a browser. Spiking Excalidraw could at best produce equal evidence for a
   candidate that loses on the substantive axes below.
2. **HTML nodes.** "The agent's mockup lives ON the canvas as a live node" is the fourth
   motivating image. X6 renders it natively as a registered component in the same
   document, picking up Capy's CSS variables with no iframe (verified). Excalidraw can
   only approximate it through an `embeddable`/iframe element, whose allowlist would have
   to be relaxed for local files — a security surface this design otherwise avoids
   entirely (§5.2).
3. **Bound arrows with routing.** Three of the four motivating images are node+edge
   diagrams. Manhattan routing that follows a moved target is built into X6 and is not
   Excalidraw's model.
4. **React.** Mounting one React island in one pane is annoying rather than expensive
   (~45 KB gzip, no reach into the rest of the app) — this is _not_ the deciding reason,
   and it is recorded here so nobody re-litigates the decision believing it was.

**What we give up, honestly:** freehand ink and loose "anything on a blank page" drawing,
which Excalidraw is genuinely better at. If freehand is later wanted, `perfect-freehand`
(~5 KB, framework-free) is the addition — not a substrate change.

### 3.6 The third canvas — T101, and whether a shared primitive is warranted

**T101** (`Graph/canvas view of project memories`, backlog, unspecced) would be Capy's
third canvas surface. The question the card asks is whether a shared primitive is
warranted now.

**Answer: no — and the reason is the same taxonomy as §3.3.**

| Surface                     | Kind                   | Nodes come from                    | Operator authority            |
| --------------------------- | ---------------------- | ---------------------------------- | ----------------------------- |
| PR Stack (T198, shipped)    | derived-graph **view** | `gh` snapshot                      | rearrange only                |
| T101 memory graph (backlog) | derived-graph **view** | cards, pages, `[[links]]`, `deps:` | rearrange, navigate           |
| T218 canvas (this card)     | editable **document**  | the operator and the agent         | create, edit, delete, connect |

T101 sits on **PrStackCanvas's** side of the line, not T218's. So the shared primitive
that might one day exist is "a viewport for a derived graph" — and its two consumers are
T198 and T101, neither of which is this card. Building it as part of T218 would mean
paying for an abstraction whose actual consumers are elsewhere, and constraining an
editable-document pane to fit a read-only-view shape.

Three further reasons not to extract anything now:

- **Rule of three, with only two candidates, one of which is unwritten.** T101 has no
  spec — its own card says mockups first, then a decision, then a PRD. Designing a shared
  API against an imagined consumer is how the wrong abstraction gets locked in.
- **The reusable part is already extracted, and does not transfer.** The viewport math is
  pure and already lives outside the component (`clampScale`, `fitToView`, `lodForScale`
  in `src/main/pr-stack-core.ts`). X6 supplies its own equivalents (`graph.zoomToFit()`,
  scale clamping in `Graph` options), so even that piece is not shared with T218.
- **T101 may not pick X6 either.** Its own card names `vue-flow`, `d3-force` and
  `cytoscape` as candidates, and a force-directed memory graph has very different
  requirements from a hand-arranged whiteboard.

**Concrete follow-up instead of an extraction:** when T101 is specced, its first substrate
question should be _"does the `PrStackCanvas` viewport generalise to a second derived-graph
view?"_ — a note for that card, not work for this epic. T218 must neither wait for it nor
pay for it.

## 4. The canvas file

The canvas file — not the pane's memory — **is the contract between the operator and the
agent.** This sentence is the design; §4.4, §4.6 and §7 are consequences of it. The live
loop test proved the alternative: with state only in the page, the agent was not degraded,
it was _blind_.

### 4.1 Name and format

**Format:** plain JSON, UTF-8, LF, 2-space indent, keys written in a stable order so a
Save produces a minimal diff.

**Name:** `<name>.capycanvas.json`. Default file: `board.capycanvas.json`.

Why this and not the alternatives:

- Not `.json` alone — the pane must be routed by name without reading the file, and every
  other `.json` in a repo must keep opening as text exactly as it does today.
- Not `.x6.json` — the vendor must not be in the file name. §3.4 is a pin, not a marriage;
  a substrate swap must not rename every operator's files.
- Not `.excalidraw` — that format is no longer what we write.
- The **double extension** keeps `extname()` returning `.json`, so nothing that already
  classifies by `extname` changes behaviour.

> **Implementation trap.** `src/main/markdown-core.ts` classifies with `extname()`, which
> yields `.json` here. The canvas classifier must therefore match the **suffix**
> `.capycanvas.json` (case-insensitive), and must run **before** the existing text
> classification. U4 AC-2 tests exactly this.

### 4.2 Location and scope — per worktree, by default

**Default:** `.capy/out/canvas/` **inside the worktree**, with assets in
`.capy/out/canvas/assets/`. `.capy/` is already gitignored (`.gitignore:44`), so the
default canvas is a **per-branch scratch board** that never lands in a commit and
disappears with the worktree.

This is the card's resolved scoping decision, and the mechanism is the same one a terminal
uses: a worktree is a physically separate checkout, so `WT-A/.capy/out/canvas/board…` and
`WT-B`'s are different files with no coordination needed between them.

**Deliberate contrast with project memory.** `resolveMemoryCheckout`
(`src/main/mcp/memory-core.ts`) collapses any worktree to its main checkout via the git
common-dir, so every branch shares one `.capy/memory/`. A canvas **must not** use that
resolver. _The directory is the scope decision_, and using the memory resolver by reflex
would silently make every canvas repo-wide.

| Location                                  | Scope                                  | When                                                                                            |
| ----------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `.capy/out/canvas/` (gitignored)          | this worktree, ephemeral               | **default.** The branch's scratch board.                                                        |
| `docs/canvas/*.capycanvas.json` (tracked) | this worktree, travels with the branch | via an explicit **"Save into the repo"** action (U8), when the diagram is itself a deliverable. |
| `.capy/memory/canvas/`                    | whole repo                             | **deferred.** Not built in v1; no project-wide board has been asked for.                        |

**Containment.** Every read, write and watch is confined to the folder root the same way
`markdown-read.ts` confines file reads, and a path resolving outside it is refused with a
machine-readable code — never clamped, never silently redirected.

### 4.3 Document schema

```jsonc
{
  "capycanvas": 1, // schema version — an unknown major is refused, not migrated
  "meta": {
    "title": "Daily budget review",
    "createdAt": "2026-08-23T10:00:00.000Z",
    "updatedAt": "2026-08-23T10:42:00.000Z"
  },
  "nodes": [
    {
      "id": "n-7f3a", // stable, opaque, unique within the document
      "shape": "box", // one of §5.1, or a registered HTML shape name
      "x": 120,
      "y": 64, // world coordinates, numbers, finite
      "width": 180,
      "height": 72,
      "label": "Budget row", // normalized on read — §4.5
      "origin": "agent", // "agent" | "operator" — §4.4, REQUIRED
      "zIndex": 3,
      "props": {} // shape-specific, plain JSON only — §5.2
    }
  ],
  "edges": [
    {
      "id": "e-91cc",
      "source": "n-7f3a", // must reference a node id present in this document
      "target": "n-2b10",
      "label": "reads",
      "origin": "operator",
      "router": "manhattan"
    }
  ]
}
```

Rules that hold for every document:

- Every `id` is unique across nodes **and** edges. A duplicate is a validation failure.
- Every edge's `source`/`target` resolves to a node in the same document. A dangling edge
  is a validation failure, not a silently-dropped edge.
- Every value is plain JSON. Functions, DOM nodes and class instances cannot appear — this
  is what §5.2 protects.
- Unknown top-level keys are **preserved** on a read/write round-trip (so a newer minor
  schema written by a newer Capy is not destroyed by an older one), but unknown keys
  inside a node or edge are not — nodes and edges round-trip through X6, which normalizes
  them.

### 4.4 Origin stamp — required on every node and edge

**Every node and every edge carries `origin: "agent" | "operator"`, written by whichever
side created it.** The pane stamps `"operator"` on anything the operator creates; the MCP
verb stamps `"agent"` on anything it adds. Neither side may set the other's value, and a
node arriving without an origin is a validation failure (§8.3), not a defaulted one.

**Why (live loop test, finding 2).** Without the stamp, an agent re-reading a canvas it
previously drew on cannot tell _what the human added_ from _what it drew last time_. That
distinction is the entire review loop: with it, "the operator deleted three of my boxes
and drew two of their own and moved `Browser`" is actionable feedback; without it, the
agent sees a bag of nodes and can only diff against a memory it does not have. The loop
test worked precisely because the paste handler happened to stamp
`data: { origin: 'paste', … }` on the node — this section makes that accident a contract.

The stamp is **creation provenance, not ownership**. Either side may move, relabel or
delete any node; the stamp records who first put it there and does not change when the
other side edits it. Deliberate: the alternative — a last-writer stamp — would erase the
"what did the human contribute" answer on the agent's next tidy-up pass, which is the one
question the field exists to answer.

### 4.5 Label normalization — required in the reader

**Any canvas-file reader must normalize a node's label across both attribute paths,
preferring the most recently written one, and expose exactly one `label` to everything
above it.**

**The failure it prevents (spike README trap 3, observed live).** In X6, a label given at
node creation lands on `attrs.text.text`; a later `node.attr('label/text', …)` writes
`attrs.label.text` and **leaves the original stale**. A reader that picks the wrong path
reports the name the node had _before_ the human renamed it. This happened during the
spike: the agent misreported what the operator had named things — the exact failure that
makes the loop untrustworthy, because a confidently wrong read is worse than no read.

Requirements:

- Normalization lives in the **pure core** (`canvas-core.ts`), not in the pane and not in
  the verb handler, so the pane, the reader IPC and the MCP verb can never disagree.
- The persisted document carries the normalized `label` at the top level of the node
  (§4.3), so a consumer that does not know X6's attribute layout is never asked to.
- Round-tripping a document through the pane must not resurrect a stale label: on write,
  the normalized value is authoritative and both attribute paths are set from it.
- Unit-tested against all four shapes: only `attrs.text.text`; only `attrs.label.text`;
  both, agreeing; both, disagreeing (U1 AC-4).

### 4.6 Images are externalised — never inline data URIs

**An image node stores a relative path into an `assets/` sibling directory. Image bytes
never enter the canvas file.**

**The failure it prevents (live loop test, finding 3).** A 1,486-byte pasted image became
a 2,006-byte data URI (base64 inflates ~33%) and grew the canvas file from 18,604 to
23,158 bytes — for one paste of a tiny image. A real screenshot is megabytes; three of
them make the file unusable, and **every Save rewrites the whole file**, so the cost is
paid repeatedly rather than once.

**The precedent to follow is already in this repo**, and it is to be copied rather than
redesigned — the Capy board's card-`images` handling:

| Board mechanism                                                                                               | File                                                                 | Canvas equivalent                                          |
| ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------- |
| Source jail: a source must be under `~/.claude/image-cache/` or inside the repo folder; anything else refused | `resolveCardAssetSource` (`roadmap-core.ts:1103`)                    | identical, same two roots                                  |
| Extension must look like an image                                                                             | `imageMimeType` (`markdown-core.ts:96`)                              | reuse as-is                                                |
| Destination filename is **server-generated**, never the caller's path                                         | `buildCardAssetFilename` (`roadmap-core.ts:1128`)                    | `<canvasName>-<n><ext>`                                    |
| Destination jail against traversal                                                                            | `resolveCardAssetDestination` (`roadmap-core.ts:1138`)               | same shape, `canvas/assets/`                               |
| Relative embed written by the server                                                                          | `formatCardAssetEmbed` → `../assets/<file>` (`roadmap-core.ts:1147`) | node `props.src` = `assets/<file>`                         |
| Validate **all** sources before copying **any**                                                               | `attachCardAssets` (`tool-handlers.ts:567`)                          | identical — no partial attach on disk                      |
| Copy with `COPYFILE_EXCL`, retry the index on `EEXIST`                                                        | `tool-handlers.ts:610`                                               | identical — a later attach never overwrites an earlier one |
| Per-file cap 2 MB, max 6 per call                                                                             | `CARD_ASSET_MAX_BYTES` / `CARD_ASSET_MAX_PER_CALL`                   | same caps                                                  |

The rationale for the source jail transfers unchanged and is worth restating: the
destination is always server-generated, but an MCP-only session has no `Read` tool of its
own, so an unrestricted absolute-path source would let it copy arbitrary local files (SSH
keys, dotfiles) into a directory the agent can subsequently read back.

**Operator paste and drag-drop** land in the same `assets/` directory through the same
server-side path, so a pasted screenshot and an agent-attached one are indistinguishable
on disk. **Orphan assets** (an asset whose node was deleted) are **not** garbage-collected
in v1 — deletion is recoverable by undo before a Save, and a sweep that deletes a file the
operator can still undo their way back to is worse than a few stale bytes in a gitignored
directory. Recorded as deferred in §11.

### 4.7 Caps and validation

| Cap                | Value                                   | Why                                                                                                                                                 |
| ------------------ | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Canvas file size   | **2 MB** (`MAX_MARKDOWN_BYTES`, reused) | Same reason as the viewer's: a giant file must not blow up the renderer. Externalising images (§4.6) is what makes this generous rather than tight. |
| Nodes per document | **2,000**                               | A ceiling that no hand-built board approaches and a runaway verb call would.                                                                        |
| Edges per document | **2,000**                               | as above                                                                                                                                            |
| Ops per verb call  | **200**                                 | §8.3                                                                                                                                                |
| Assets per call    | **6**, ≤2 MB each                       | Matches the board's card-image caps exactly.                                                                                                        |
| Label length       | **2,000** chars                         | A label is a label.                                                                                                                                 |

Exceeding a cap is a **refusal with a machine-readable code**, never a truncation.

## 5. Node kinds in v1

### 5.1 The four node kinds and the one edge kind

| Kind           | `shape`       | What it is                                     | Notes                                                               |
| -------------- | ------------- | ---------------------------------------------- | ------------------------------------------------------------------- |
| Box            | `box`         | Rounded rectangle with a centred label         | The default. Created by dragging on empty canvas.                   |
| Text           | `text`        | A bare label, no frame or fill                 | For annotations and callouts.                                       |
| Image          | `image`       | Renders an asset by relative path              | `props.src` = `assets/<file>` (§4.6). Never a data URI.             |
| HTML component | `capy/<name>` | A **registered** Vue/HTML component (§5.2)     | e.g. `capy/plan-usage-card`. The agent writes a name, never markup. |
| **Edge**       | —             | Manhattan-routed arrow binding source → target | Follows a moved endpoint. Created by dragging from a port.          |

**`frame` / container is deferred to v2, deliberately.** The delivery plan's CP0 lists it
as a v1 candidate; this spec declines it, and the reason is the same discipline the spike
exists to enforce. X6's `embedding` was **not** exercised in the spike, and a container
implies drag-into, drag-out-of, resize-propagation and delete-cascades — four behaviours
whose interaction with `history` and `transform` is exactly the kind of thing that looks
free until it is written. Shipping it unverified would put the riskiest untested surface
into the most-used unit. It is a clean follow-up card once U3 is real.

### 5.2 Registered HTML components — the catalog

**HTML nodes must be registered components referenced by shape name. An `html` payload
passed inline on a node is forbidden.**

**Why, on three independent grounds:**

1. **It does not work.** An inline element or function makes `graph.toJSON()` throw:
   `Can only serialize node with plain-object props, but got a "[object HTMLDivElement]"`
   (spike README trap 2). Since the file _is_ the contract (§4), a node that cannot be
   serialized is a node that cannot exist.
2. **It keeps agent-authored markup out of the canvas file.** The agent writes
   `shape: "capy/plan-usage-card"` — a name from a fixed catalog — and the renderer owns
   how that component draws. There is no path by which arbitrary agent-written HTML
   reaches the DOM, which retires most of the security concern the card originally flagged
   (an `embeddable`/iframe allowlist relaxed for local files) rather than mitigating it.
3. **It survives a substrate change.** A shape name is a stable contract; a serialized DOM
   fragment is not.

**Who defines them.** The repo, in code. Each shape lives under
`src/renderer/src/components/canvas/shapes/`, registers once at pane setup via
`Shape.HTML.register({ shape, html })`, and is listed in a **pure manifest module**
`src/renderer/src/components/canvas/canvas-shapes.ts`:

```ts
export interface CanvasShapeSpec {
  /** Namespaced so a shape name can never collide with a built-in. */
  name: `capy/${string}`
  /** One line, shown to the agent — this is how it decides which to use. */
  description: string
  defaultSize: { width: number; height: number }
  /** Names of the plain-JSON keys this shape reads from `node.props`. */
  props: readonly string[]
}
```

The manifest is pure (no Vue, no DOM), so `src/main` can import it to validate a verb call
without pulling the renderer into the main process.

**How the agent discovers the names — three ways, no guessing:**

1. **Every `draw_canvas` ACK carries `shapes`** — the full catalog as
   `{ name, description, defaultSize }[]`. One call and the agent knows what exists.
2. **An unknown shape is refused by name, listing the valid set** — so the failure is
   self-correcting rather than silent.
3. **`docs/capy-features.md`** states that the catalog is discoverable from the ACK (it
   does **not** enumerate the shapes — that list changes with the code, and a doc that
   drifts is worse than one that points).

v1 ships **one** registered shape beyond the built-ins — a mockup card
(`capy/mockup-card`) — because one is enough to prove the mechanism and a catalog is
cheaper to grow than to shrink.

## 6. The pane in the app shell

### 6.1 A new pane kind, in the helper stack — not a takeover, not a Markdown-pane mode

The delivery plan asks: a new pane kind, or does the Markdown pane gain a canvas mode?
**A new pane kind: `DiagramPane.vue`**, a sibling of `MarkdownPane` / `MemoryPane` /
`ExplorerPane` in the **helper stack**.

Why the helper stack rather than a sixth main-pane takeover:

- **It must be reachable through `open_file`**, which opens into the selected worktree's
  helper stack in the background. That is the delivery path the whole card is built on.
- **It must coexist with the terminal.** Annotating a mockup _while talking to the agent
  about it_ is the loop; a takeover that replaces `<main>` puts the conversation behind
  the drawing.
- **Every takeover is per-repo or global and mutually exclusive** through `stores/ui.ts`'s
  mutex. A canvas is per-**file** and per-**worktree**, and two canvases open at once is a
  reasonable thing to want.
- **The space problem is already solved.** The pane header's existing **maximize** button
  (design.md §6 → "Maximizing a pane") grows a pane to fill the stack while every other
  pane collapses to a 24px strip. That is the "give me room to draw" affordance, and it
  costs nothing to inherit.

Why not a mode of `MarkdownPane`: that component's body is a text draft buffer plus an
editor, and its state (`draft`, dirty tracking, prose-vs-monospace rendering) has no
overlap with a graph document. The two share the **header** and the **stale-on-disk
banner** — both of which are already documented as reusable pane conventions — and nothing
else.

**Like the other non-PTY panes, `DiagramPane` has no PTY**: it is reproducible from its
`filePath`, does not enter `liveHelpers`, and mounts/unmounts freely. It does **not**
inherit the terminal's detach-not-dispose rule.

### 6.2 Header

Reuses the standard pane header (`h-6`, `--surface`, `border-bottom --border`, header
doubles as the resize handle). Left to right:

1. canvas icon (12px, `--text-3`);
2. **file basename** (truncated, native `title` shows the full path);
3. **dirty dot** — `•` in `--color-accent`, only when there are unsaved edits (identical to
   `MarkdownPane`'s);
4. **undo** / **redo** buttons (18×18px targets, disabled when the history is empty at
   that end);
5. **Save** button — `--color-accent` when dirty, `--text-disabled` + `disabled` when
   clean. Identical idiom to `MarkdownPane`'s save;
6. **maximize** button (inherited, unchanged);
7. **close** button (inherited, unchanged) — with the same unsaved-edits discard guard the
   Markdown pane already applies.

All header buttons `@mousedown.stop` so they do not start a pane resize.

The **stale-on-disk banner** (§7.3) is the existing one: `bg-warning/10 text-warning`,
replacing the filename row, with a Reload action routed through the same discard guard.

**No new design tokens are expected.** Any that turn out to be needed — a canvas grid
colour, a selection-halo treatment — go into `design.md` **first**, in the same change, per
the design contract. The floating zoom cluster follows the anatomy `PrStackCanvas` already
established (§3.3's one deliberate loss: rebuilt against X6, same visual contract).

### 6.3 How it opens

Three paths, mirroring the Markdown pane exactly:

1. **Explorer pane `eye` icon** on a `*.capycanvas.json` row.
2. **`open_file`** from an agent — routed to `DiagramPane` by the suffix classifier (§4.1,
   U4). Background, never steals focus.
3. **The `draw_canvas` verb** on a canvas that is not currently open — it opens the pane
   the same way `open_file` does, so the agent's drawing is visible without a second call.

### 6.4 Theme

The canvas reads Capy's CSS variables and **re-reads them on a theme switch**, exactly as
`TerminalPane` reapplies its palette to every live terminal. An HTML node is a real DOM
node in the same document, so it inherits tokens for free; SVG shapes are styled from the
same variables. No raw hex anywhere in the component (U2 AC-3).

## 7. The Save model

**The pane holds working state. An explicit Save writes the file. The agent reads the
saved file.** No live bidirectional sync, no locking, no merge algorithm.

This is the Claude Design precedent recorded on the card — "Save publishes a new version"
— and it is adopted for the same reason: a discrete commit point replaces a distributed
systems problem with a button.

### 7.1 Working state

Everything the operator does — create, move, resize, rename, connect, delete, paste — is
applied to the in-memory graph and pushed onto X6's `history` plugin. None of it touches
the file. The dirty dot (§6.2) appears on the first change and clears on a successful Save.

**Undo/redo is pane-local and does not survive a reload or a pane close.** Stated so
nobody expects the file to carry history: it carries a document, not a timeline.

**One exception writes without a Save: asset bytes.** A pasted or dropped image is copied
into `assets/` immediately (it has to be — the bytes exist only in a clipboard event), and
the _node_ referencing it is ordinary unsaved working state. If the operator never saves,
the asset is an orphan in a gitignored directory. That is the accepted cost of not holding
megabytes in memory, and it is why §4.6 does not garbage-collect.

### 7.2 Save

On Save the pane:

1. serializes via `graph.toJSON()`;
2. **normalizes every label** (§4.5) — both attribute paths written from the normalized
   value, so the file never carries a stale name;
3. asserts every node and edge carries an `origin` (§4.4);
4. validates against §4.3 and the caps in §4.7;
5. writes through the confined writer **atomically** (write-temp-then-rename, as
   `mcp/atomic-write.ts` already does), so a crash mid-write cannot leave a truncated
   canvas;
6. updates `meta.updatedAt` and clears the dirty state.

A validation failure **aborts the Save** and surfaces a toast naming what failed. It never
writes a partially-valid document.

### 7.3 The file changes on disk underneath — three cases

This is the question CP0 requires a decision on. The watcher (`canvas-watch.ts`, same
shape as `markdown-watch.ts`) reports "file changed on disk", and the pane's response
depends entirely on whether it is dirty:

| Case  | Pane state                               | Behaviour                                                                                                                                                                                                                                                                                     |
| ----- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A** | **clean**                                | Silently reload: `fromJSON` the new document, **preserve the viewport** (pan/zoom must not jump — the operator may be reading it). Clear the undo history, because it now refers to a document that no longer exists. This is the common case: the agent drew while the operator was looking. |
| **B** | **dirty**                                | **Do not reload.** Show the stale-on-disk banner (§6.2). The operator chooses: **Reload** (discard guard → their edits are lost, deliberately, on an explicit confirm) or keep editing.                                                                                                       |
| **C** | **dirty, and the operator presses Save** | **Last write wins — the operator's document replaces the file, and whatever the agent wrote since is gone.**                                                                                                                                                                                  |

**Case C is a decision, not an oversight.** The alternatives were considered and rejected:

- _Merge_ — a 2-author structural merge of a graph document is a research project, and the
  commit-point model exists precisely so we never need one.
- _Refuse the Save_ — traps the operator's work in a pane with no way out. Worse than
  losing the agent's write, which the agent can trivially redo because it knows what it
  wrote.
- _Lock the file while the pane is dirty_ — makes the agent fail unpredictably from its
  own point of view, and the failure would be invisible in the pane.

The banner is what makes C **informed rather than silent**: the operator cannot reach case
C without having been told the file moved. That is the whole safety property, and U3 AC-6
tests it.

### 7.4 What the agent sees

The agent reads the file, not the pane. So:

- Unsaved operator edits are **invisible** to the agent. Correct, and it is the point: the
  operator has not committed them.
- The agent's own writes go straight to the file (§8) and reach the pane through the
  watcher — case A or B above.
- An agent that wants the operator's latest work asks for a Save; it cannot take it.

## 8. The MCP verb

### 8.1 Name and shape

```ts
draw_canvas({
  folder: string,        // absolute path of the known repo/folder (gate anchor)
  path?: string,         // canvas file; defaults to <folder>/.capy/out/canvas/board.capycanvas.json
  ops: Op[],             // 1..200, applied in order, all-or-nothing
  images?: string[],     // 0..6 absolute source paths to externalise into assets/ (§4.6)
  open?: boolean         // default true — open/reveal the pane so the operator sees the drawing
})
```

**ACK** carries: `{ ok, path, nodeCount, edgeCount, applied, shapes }` — where `shapes` is
the registered HTML-component catalog (§5.2), so the agent learns the vocabulary from its
first call.

### 8.2 Incremental ops, not whole-document replace

**Decision: incremental ops.** The verb never replaces the document wholesale.

| Op            | Arguments                                                                              |
| ------------- | -------------------------------------------------------------------------------------- |
| `add_node`    | `shape`, `x`, `y`, `width?`, `height?`, `label?`, `props?` → returns the assigned `id` |
| `add_edge`    | `source`, `target`, `label?`, `router?`                                                |
| `update_node` | `id` + any of `x`, `y`, `width`, `height`, `label`, `props`                            |
| `update_edge` | `id` + any of `label`, `router`                                                        |
| `remove_node` | `id` — **cascades** to every edge touching it                                          |
| `remove_edge` | `id`                                                                                   |
| `clear`       | removes only nodes/edges whose `origin` is `"agent"` — see below                       |

Why ops rather than replace, in order of weight:

1. **Replace makes the agent destroy operator edits it never read.** That is the exact
   failure §4.4 exists to prevent — an agent that regenerates "its" diagram would silently
   erase the two boxes the operator drew and the note they attached. With ops, the agent
   must name what it touches.
2. **The file is a two-author contract** (§4). A verb that overwrites the whole document
   makes the agent the sole author by construction.
3. **Cost.** A 2 MB canvas does not have to round-trip through the transcript for the
   agent to move one node.

`clear` is deliberately scoped to `origin: "agent"`: "redraw my diagram" is a real and
common intent, and it must not be a foot-gun that takes the human's annotations with it.
An agent that genuinely wants an empty canvas writes to a new `path`.

**Reading back** is not a `draw_canvas` op — the agent reads the canvas file with its
ordinary file-reading tools, because it is plain JSON in the working tree and no new
surface is needed to read plain JSON. (An MCP-only session with no `Read` tool is the one
gap; it is recorded as an open question in §11 rather than pre-solved with a verb nobody
has asked for.)

### 8.3 Validation rules

All validation is **pure** (`canvas-core.ts` + the shape manifest) and runs in main
**before any write**. The whole call is rejected if any op fails — there is no partial
apply.

1. **Folder gate** — `folder` must be a known Capy folder; the standard permission gate
   applies unchanged.
2. **Path containment** — `path` must resolve inside `folder`, must end in
   `.capycanvas.json`, and must be under `.capy/out/canvas/` or `docs/canvas/` (§4.2).
   Anything else: `PATH_NOT_ALLOWED`.
3. **Schema version** — an unknown `capycanvas` major is refused (`SCHEMA_UNSUPPORTED`),
   never migrated silently.
4. **Ops count** — 1..200. Empty or over: `BAD_ARGS`.
5. **Shape names** — a `shape` must be a built-in (§5.1) or a name in the registered
   catalog. Unknown: `UNKNOWN_SHAPE`, **listing the valid set**.
6. **Props are plain JSON** — no functions, no DOM, and only the keys the shape's manifest
   declares. An undeclared key is refused rather than stored, so the file cannot accumulate
   junk that no renderer reads.
7. **Geometry** — `x`/`y`/`width`/`height` finite numbers; width/height > 0. `NaN`,
   `Infinity` and negative sizes are refused (they render as invisible or inverted nodes,
   which is worse than an error).
8. **Referential integrity** — `add_edge`'s `source`/`target`, and every `update_*` /
   `remove_*` `id`, must exist in the document **as it stands after the preceding ops in
   the same call**. A dangling reference: `UNKNOWN_ID`.
9. **Origin** — the server stamps `origin: "agent"` on everything this verb creates. An
   `origin` supplied by the caller is **refused**, not overwritten: an agent that can
   claim `"operator"` can launder its own output as human feedback.
10. **Caps** — the resulting document must satisfy §4.7 (node/edge counts, label length,
    2 MB). Exceeding: refusal, never truncation.
11. **Images** — the board's asset rules (§4.6) apply verbatim: source jail, image
    extension, ≤2 MB each, ≤6 per call, all validated before any copy.
12. **Atomic write** — validated document → temp file → rename.

### 8.4 Gate class

`mutates: true`, `grantable`, `alwaysAllowable`, `silentAllowInAgentFolder` — **the same
class as `open_file`, `notify` and the board writers.** It runs without a per-call confirm
in a folder that is not blocked, and every call is recorded in the audit log.

Justified because it writes a gitignored scratch file inside the folder the session is
already working in, it cannot escape that folder (rule 2), and it cannot write anything the
agent could not already write with its ordinary tools. It is a _rendering_ verb, not an
actuator. Under "Ask before agent actions" it confirms like every other mutating verb.
