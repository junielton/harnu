## 0. Summary and the decisions that need a human

Harnu has **26 modal-like surfaces** (24 own components + 2 inline overlays) and **no shared shell**. Each re-implements Teleport, scrim, card, header, footer, Esc, backdrop-close and (mostly) focus handling, and they have drifted: 5 `max-height` values + 2 dialogs with none + 2 fixed heights, 9 widths, 3 radii, 2 scrim values (3 counting the viewer), 3 z-index values (60/65/70), 3 close-state idioms, and no dirty-guard convention beyond two components. BUG-184 is just the first drift that hurt.

**Recommendation.** Build one `components/ui/Dialog.vue` (+ `useDialogStack`), tokenize the scrim / cap / z-layers, and migrate in **11 PRs (batch 0 safety net, BUG-184, then batches 1–8) behind a characterization-test net that lands first**. Land **BUG-184 first as a standalone fix, written in the primitive's final shape** (§7). The migration is a _shell swap_: component names, emits, store contracts and every `data-testid` / `data-test` / `data-dsqa` stay exactly where they are.

## 1. Inventory (AC-1)

### 1.0 Scope rule

"Modal-like" = blocks the app behind it with a scrim **or** is a `role="dialog"` overlay. Anchored popovers/menus/previews, takeovers, toasts and non-blocking drag overlays are **out of scope** and listed in §1.3 with the evidence for each, so the boundary is auditable.

Search used: every `*Dialog.vue` / `*Modal.vue`, `McpConfirmOverlay`, plus `git grep -lE 'Teleport|fixed inset-0|position: fixed' src/renderer/src` (45 files, `git grep -l`) — each file classified.

## 2. What we measured about the tooling the migration depends on

- **Test stack:** Vitest 2 + `@vue/test-utils` 2 + jsdom (opt-in per file with `// @vitest-environment jsdom`); `tests/**/*.test.ts`. jsdom has **no layout engine** — `getBoundingClientRect()` is all zeros — so "the footer is on screen" can only be proven in a real browser (§6.3).
- **Playwright, two projects** (`playwright.config.ts`). `smoke`: `tests/e2e/*.spec.ts` attach over CDP (`:9222`) to a running `npm run dev` and need a live Claude — local only. `ci`: `tests/e2e/ci/*.spec.ts` call `_electron.launch()` on the **built** app (`out/main/index.js`, no `--remote-debugging-port`, throwaway `--user-data-dir` + `HOME`), run per PR under `xvfb-run -a npm run e2e:ci` (`.github/workflows/ci.yml` job `e2e`, :145-178). Two local specs touch a dialog today, both Settings: `folder-sort.spec.ts` and `os-notifications.spec.ts:57-62`. `ci/scheduler-result-css.spec.ts` is the precedent for what jsdom cannot do: it pins layout in real Chromium from a seeded `userData` (§6.3).
- **No store handle for dialogs.** `window.__omStore` exposes only the _sessions_ store and only in dev builds (`main.ts:30-32`, `import.meta.env.DEV`); the `ui` store that owns `openDialog()` is not reachable from outside, and a built (`ci`) app has no handle at all. A driver opens dialogs through the UI.
- **Contract-test precedent:** `tests/cleanup-design-contract.test.ts` reads component source and asserts design-token rules (no raw sizes outside a documented allow-list). The same pattern gives us a cheap ratchet for "no hand-rolled shell" (§6.4).
- **App shell:** `html, body, #app { overflow: hidden }` (`main.css:28-35`). Nothing behind a dialog can scroll the page, so a scroll-lock is **not required**; the contract suite asserts the shell invariant instead of implementing a lock (§6.1).
- **i18n:** the close button's `aria-label` is a per-dialog key (`renameFolder.close`, …) — there is no shared `dialog.close`. The primitive needs one, in **both** `en.json` and `pt-BR.json` (`MessageSchema = typeof en`, so a missing key breaks `vue-tsc`).

## 4. Standard layout (AC-4)

Everything below is **the paste-ready replacement for the `### Dialog` block at design.md:5730** (and its satellites: the §4 "Layout dimensions" rows, the §6 "Floating surfaces" table, the "Form controls — canonical components" list). **`design.md` is not edited in this PR** — it is edited in batch 1, together with the code that implements it, per the design contract in `CLAUDE.md`.

### 4.1 Decisions baked into the draft

- **Title type is a documented exception, not §3's Subtitle.** 14+ dialogs ship `13.5px/20px · 600`; §3 says dialog titles are Subtitle `15/22/500` and only Dehydrate, Sweep and CleanupBulk follow it. Moving 14 dialogs to follow §3 is the bigger visual change, so the standard keeps the dominant value and names it as a type token (`--text-dialog-title`) rather than a raw `13.5px` (decision **D8**, recommendation: keep dominant).
- **The stale footer rule is dropped.** design.md:5736 says the footer has a `#0f0f12` background. No shipped dialog does that, and a raw colour is forbidden by the contract; the footer is transparent on the card's `--color-surface`.
- **`role="dialog"` everywhere.** `alertdialog` is tempting for destructive confirms but `cleanup-bulk-confirm-dialog.test.ts` and `containers-view.test.ts` select on `[role="dialog"]`; changing the role is a test-visible behaviour change with no user benefit in v1. Destructive confirms get `aria-describedby` instead.

### 4.2 Draft (copy from here)

````markdown
### Dialog

The one modal shell (`components/ui/Dialog.vue`). Every blocking overlay with a card is a
`Dialog`; **hand-rolled scrims are a bug** (a contract test enforces it — see "Enforcement"). Two
surfaces deliberately keep their own shell because they have no header/footer anatomy: the
**Command palette** and the **Image lightbox**; they use the same scrim and z tokens.

#### Anatomy

```
Scrim  (--color-scrim, fixed, inset 0, flex-centered)           z = layer
└─ Card (--color-surface, 1px --color-border-2, --radius-lg, --shadow-pop)
   ├─ Header   shrink-0 · padding 14/18/10 · border-b --color-border
   │     [icon] Title (13.5/20 600)  [subtitle: mono 11.5 --color-text-4]        [✕ 24×24]
   ├─ Body     flex-1 · min-h-0 · overflow-y-auto (.scrollable) · padding 14/18   ← the ONLY scroller
   └─ Footer   shrink-0 · padding 12/18 · border-t --color-border
         [meta · left, optional]                         [Cancel] [Primary]   gap 8, right-aligned
```

- **The card never scrolls and is never taller than the cap.** Header and footer are `shrink-0`; the
  body is `flex-1 min-h-0 overflow-y-auto`. A secondary section (e.g. a "refused" list) lives _inside_
  the body — it does not get its own cap unless it is a self-contained widget (a code `<pre>`, a
  filmstrip), and never grows the card.
- **No footer** is allowed (a viewer-style or single-action card); **no header** is not — a dialog
  always has an accessible name (title, or `aria-label` when the header is a custom slot).
- Footer actions use `ui/Button` (`ghost` Cancel, `primary` or `danger` action). Order: dismiss left of
  commit. The destructive action uses `variant="danger"`; it is never the default (Enter) action.
- The close button is 24×24 (a documented exception to the 22×22 icon-only trigger of design.md:463 — decision D9), `X` icon 14px/1.5, `--color-text-3` → `--color-text` + `--color-surface-2`
  on hover, labelled by the shared key `dialog.close`. It is absent when the dialog is not dismissible.

#### Size scale

Width is always `min(<size>, 90vw)`. A dialog picks a size; it does not invent a width.

#### Viewport cap (mandatory)

`max-height: var(--dialog-max-h)` = `84vh` on **every** card. There is no variant without it. 84vh is the
middle of the shipped 80–88vh range and leaves ≥ 8vh above and below. A fixed `height`
(`xl` Settings `min(80vh, 720px)`, Open subfolder `min(70vh, 560px)`) is allowed only if it is ≤ the cap, so
the card is still capped and the nav/pane or list keeps its own scroll inside the body.
At a 560px-tall window the card is 470px: header + footer ≈ 100px, the body scrolls the rest.

#### Placement

Centered (default). `placement="top"` (`margin-top: 10–12vh`) is for the MCP confirm only: a card whose height changes as its queue grows would jump if it were centered. (The Command palette keeps its own shell and its own top anchor.)
````

## 5. Component API (AC-5)

### 5.1 `components/ui/Dialog.vue` — controlled, emits instead of closing

The primitive **never closes itself**: it emits `close(reason)` and the owner runs the close logic it already has. That single decision is what lets one component serve all four close idioms (§1.2) with no rewrite — `ui.closeDialog()`, an `emit('cancel')`, a local ref, and a dirty/busy guard are all just the handler wired to `@close`.

```ts
// props
open: boolean                              // required; the owner keeps its own state (store flag, v-if, local ref)
size?: 'sm' | 'md' | 'lg' | 'xl'           // default 'md'
height?: string                            // CSS height for fixed-size cards (Settings, Open subfolder); must be ≤ the cap
placement?: 'center' | 'top'               // default 'center'
layer?: 'dialog' | 'raised'                // default 'dialog'  (60 | 65)
title?: string                             // header title; or use #header
subtitle?: string                          // mono, text-4
ariaLabel?: string                         // required when #header replaces the title (Card modals)
describedby?: string                       // id of the body copy (confirms)
dismissible?: boolean                      // default true; false = no ✕, Esc/scrim do nothing (MCP gate)
initialFocus?: string | (() => HTMLElement | null)   // selector within the card, or a getter; default first focusable
escIgnore?: string                         // default '[data-esc-owner],[data-branch-combobox-panel]'

// emits
close: [reason: 'esc' | 'scrim' | 'button']

// slots
icon      // leading header icon (destructive red icon, shield)
header    // replaces the whole title row (Card modals, MCP gate)
default   // body — the only scroll region
meta      // footer left (totals, "Reset")
footer    // footer right (actions); omit for no footer
```

**`initialFocus` resolution.** `useFocusTrap` takes an `initialFocusRef: Ref<HTMLElement | null>` and reads `.value` once, after `nextTick`, when the trap activates. `Dialog` therefore does not pass a string or a getter through; it builds a `customRef` (no caching) whose getter re-resolves on every read — `card.querySelector(selector)` for a string, `getter()` for a function — and hands **that** ref to `useFocusTrap`. An unresolved target returns `null`, which `useFocusTrap` already treats as \"fall back to the first focusable, then the card\". This is why a selector is scoped to the card (slot content is mounted by then) and why no `watch` is needed.

\1, `$attrs` bound to the **card** element. That is where `data-testid="bulk-dialog"`, `:data-mode`, `data-dsqa="containers-remove-dialog--orphan"` live today, so selectors keep resolving. `Teleport to="body"` is inside the primitive (as in every dialog now); the redundant outer Teleport in `App.vue` is left alone.

### 5.2 `composables/useDialogStack.ts` (new) and a small change to `useFocusTrap`

- **`useDialogStack`**: a module-level ordered list of open dialogs and **one** window-capture `keydown` listener (installed on first open, removed on last close). On `Esc`: skip if the target is inside an `escIgnore` match; otherwise route to the **top** entry only and `stopPropagation()`. This replaces N per-dialog capture listeners, and with them the hand-written guards (`confirming`, `busy`, the combobox exemption) that exist only because every listener fires.
- **`useFocusTrap` gains suspension** (the one change to an existing composable): while a dialog is not the top of the stack its trap neither handles Tab **nor restores focus**; when it becomes top again it refocuses the element that had focus inside it. Today `MissionsReviewDialog` achieves this with `active: open && !confirming`, but deactivation _restores focus to the page opener_ — it works there by timing. This is the riskiest 20 lines of the project and gets its own contract cases (§6.1, C14..16).
- Initial focus and focus restore stay `useFocusTrap`'s job; `Dialog` calls it.

### 5.3 What does **not** go in the API

`beforeClose` (the owner's `@close` handler is the hook), a `role` prop (always `dialog`, §4.1), `closeOnEsc` / `closeOnScrim` (one `dismissible` switch; the two have never differed except in the gate), animation props, a native `<dialog>`.

**Native `<dialog>.showModal()` was considered and rejected for v1.** It would give top-layer stacking, built-in inerting and Esc for free, but the top layer paints above every `z-index` — including the comboboxes' dropdown panels (z-70) that `NewWorktreeDialog` depends on to appear above the card. Re-evaluate once the combobox panels are popovers in the top layer too.

### 6.3 (c) Before/after visual baseline against the real app

jsdom cannot tell you the footer is on screen. The real app can. This section is the runnable recipe; two parts of it are batch-0 deliverables (the seed and the driver) and are marked.

**1 · Two builds, two worktrees.** `before` = a detached worktree at the batch's merge-base (`git worktree add --detach ../harnu-before <merge-base>`); `after` = the branch's own worktree. Each needs its own `npm ci` (native `node-pty` is rebuilt per checkout) and `npm run build`, which produces `out/main/index.js` + `out/renderer`. The two sides share nothing but the seed.

**2 · Launch with `_electron.launch()`, no CDP port.** Exactly as `tests/e2e/ci/*` does it: `args: ['out/main/index.js', '--user-data-dir=<dir>', '--no-sandbox', '--disable-gpu']`, `env: { ...process.env, HOME: <dir> }`, working directory = that side's worktree. Per side: its own `<dir>` (`<tmp>/baseline-before`, `<tmp>/baseline-after`) — the single-instance lock is keyed on `userData`, so the two sides, and the user's own running Harnu, cannot collide. Playwright talks to Electron over a debugging **pipe**, not a TCP port, so there is no `--remote-debugging-port` to allocate.

- **Why not a CDP port.** `IS_DEV` is keyed on `--remote-debugging-port` in argv (`docs/dev/live-verify-second-instance.md`): passing it forces dev mode, and the window then loads `http://localhost:5174`. Two sides cannot both own `:5174` (and an IPv6 listener there silently shadows an IPv4 one — check `document.title`). With no port flag, each side loads its own `out/renderer` from disk and the `:5174` gotcha never applies. So `before` and `after` can run at the same time or one after the other, interchangeably.
- **The CDP-attach route of the `smoke` specs is not used** for the baseline: it needs a running `npm run dev`, a live Claude and `:9222`, and it can only ever drive one side at a time.
- **`scripts/dev/qa-parallel.sh` is not part of this method.** Its header says it is "Not wired for CDP": it launches the packaged binary for a human to click. It stays useful for the human keyboard pass of §6.4 and nothing else here.

**3 · Seed — batch-0 deliverable `tests/e2e/ci/fixtures/dialog-seed.ts`.** One function builds the on-disk world under a tmp dir and returns its paths; both sides call it with the same arguments, which is the only reason their numbers are comparable (fixed commit dates, fixed names, no randomness).

**4 · Driver — batch-0 deliverable `scripts/dev/dialog-baseline.mjs`.** Takes `--build-dir <worktree>` and `--label before|after`; launches that side as in step 2; seeds; then for each reachable surface opens the dialog through its **UI route** (table below; role/label selectors like `button[aria-label="Settings"]` in `os-notifications.spec.ts`, never the `ui` store — §2), waits for `[role="dialog"]`, and records at **1280×900 and 1280×560** (`BrowserWindow.setContentSize`, as `scheduler-result-css.spec.ts` does):

- a PNG of the viewport (for the human look);
- JSON: bounding rects of the card, header, body, footer; computed `width`, `max-height`, `height`, `border-radius`, `background-color`, `padding`, the title's `font-size`/`font-weight`; the scrim's `background-color` and `z-index`; `getComputedStyle(body).overflowY`; `document.activeElement` (tag + `data-*`/`aria-label`); the body's `scrollHeight`/`clientHeight`.

**5 · Diff — `dialog-baseline.mjs diff <before> <after>`.** Prints a per-dialog table of changed properties and fails on any change **not listed** in the batch's `expected-deltas` (copied from §3.3). That is the BUG-184 acceptance criteria turned into a loop over every dialog.

**6 · Output** under `.harnu/out/dialog-baseline/<label>/` (gitignored); the PR body carries the diff table and 2–3 hand-picked PNG pairs, not the whole set.

**7 · Themes.** Default dark + `light` for every batch; one more dark theme and one more light theme once per batch (scrim at `.55` over a light theme is what a dark-only run would hide).

**8 · What runs in CI, and what does not.** The existing **`ci` Playwright project is the right home for the geometry invariants, and the wrong home for the before/after diff.**

- _Why geometry belongs there._ `tests/e2e/ci/scheduler-result-css.spec.ts` (T312/BUG-120) is the exact precedent: it pins layout in real Chromium — box-model facts jsdom cannot see — from a seeded `userData`, and runs on every PR under xvfb (`ci.yml` job `e2e`, :145-178). The invariants of step 5 need only **one** build and one seed.
- _Why the diff does not._ It needs two builds; CI checks out one tree, and building `before` on every PR doubles the job. The diff stays a local/orchestrator tool run at PR time, with its table pasted in the PR (§6.4).
- _So batch 0 also adds `tests/e2e/ci/dialog-geometry.spec.ts`:_ it reuses `dialog-seed.ts`, sets the window to 900 and 560 tall, and for each dialog reachable on disk asserts the step-5 invariants plus "computed `max-height` ≤ the cap" once batch 1 exists. - _Limits of the `ci` project:_ empty fleet, no Claude, headless xvfb on Linux, production build (so no `__omStore`). Reach = what the seed can put on disk: everything except the four "not seedable" rows.

### 6.5 What is **not** covered by automation (a human must check)

- **Motion feel** (the 140ms scale-in, reduced-motion) — only asserted to be the same classes.
- **Screen readers.** `aria-modal` + labelled/described is asserted structurally; actual announcements in VoiceOver / NVDA / Orca are not.
- **macOS and Windows** window chrome and focus behaviour; the CDP baseline runs on Linux only (Wayland quirks per `CLAUDE.md` apply).
- **IME / composition** inside the form dialogs' inputs while `Esc` is pressed.
- **xterm focus return.** Closing a dialog restores focus to the opener; when the opener was the terminal, whether the cursor is live again is checked by hand.
- **The two surfaces nobody can characterize headlessly:** the RoadmapBoard dispatch overlay and the ReviewPane confirm in a live PR flow; and Containers remove without Docker.
- **MCP gate fail-closed semantics under timeout** (timeout → deny) — the primitive must not change it, and only a real MCP round-trip proves it.
- **Light-theme scrim contrast** beyond the sampled themes (12 themes ship).

The only textual overlap with batch 1 is adjacent lines of the `@theme` block — a mechanical rebase.                                                                                                   |

**(b) Serialized merges for the hub files.** Batches 2a, 3, 5 and 6 are _independent in what they change_ but all four edit the same hub files: `design.md` (per-dialog §6 subsections, the Floating-surfaces table), `CHANGELOG.md`, the ratchet allow-list in `tests/dialog-shell-ratchet.test.ts` and the `KNOWN_DEVIATIONS` table. Rule:

1. **Merge order is a single line:** `0 → BUG-184 → 1 → 2a → 2b → 3 → 4 → 5 → 6 → 7 → 8`. Authoring may overlap (separate sessions in separate worktrees after batch 1); **merging does not.** After batch 1, batches 2a, 3, 5 and 6 may merge in any order — first green first — but one at a time.
2. **Each batch rebases onto `main` after the previous one merged and re-runs §6.4 before it merges.** No stacked PRs: a stack would carry a stale `before` baseline and force a `git rebase --onto` cascade on every squash-merge.
3. **Single-owner rules for the hub files:**
   - _Ratchet allow-list_ and _`KNOWN_DEVIATIONS`_: **one entry per line, keyed by component filename, sorted.** A batch deletes only its own dialogs' lines, so two batches' edits are different lines and merge without conflict; a sort violation fails the test.
   - _`CHANGELOG.md`_: the bullet is added **at merge time, as the last step after the final rebase**, under that day's `## YYYY-MM-DD` heading; one bullet per batch; never edit another batch's bullet.
   - _`design.md`_: a batch edits **only** its own dialogs' §6 subsections and its own rows' cells in the Floating-surfaces table. Batch 1 owns the table's structure and §6 "Dialog"; batch 8 finalizes the table. Hunks are disjoint by construction.
   - _`themes.css` / `main.css` / locale files_: touched by batch 1 (and BUG-184, and 2b's one removal) only. A later batch that needs a new token stops and amends batch 1's contract instead of adding one ad hoc.
4. **A conflict that survives these rules is a spec bug**: fix the rule here before resolving the conflict.
