# Assumptions

Places where `.specs/features/json-list-key/spec.md` did not settle something, and what I chose.

- **`--code` with `--key`/`--auto-key`**: on `insert`/`upsert` this is rejected with the existing error, `--code cannot be used with input format options`. The spec does not mention `--code`. It produces Python rows, not a JSON document, so neither option can mean anything there.
- **CSV-implying options**: `--delimiter`, `--quotechar`, `--sniff` and `--no-headers` already switch `insert`/`upsert`/`bulk` into CSV mode. Combined with `--key`/`--auto-key`, they give `Error: --key and --auto-key only apply to JSON input`. The spec lists only `--csv`, `--tsv`, `--nl`, `--lines` and `--text` (JSONKEY-04 AC 11).
- **Which error wins**: with `--key`, `--auto-key` and a non-JSON format option all passed, the "Cannot use --key and --auto-key together" error wins. In Python, `Cannot use key= and auto_key= together` likewise comes before the explicit-format `ValueError`. The spec defines each error on its own but not what happens when several apply.
- **Empty `key`**: `key=""` (or `--key ""`) counts as passing the option, because the test is `key is not None`. It then reads the top-level key `""`. The spec does not say what an empty key name means.
- **Top-level scalar JSON** (for example `5` with `format=Format.JSON`): with `key=` this raises `RowsFromFileBadJSON` `Cannot read key "...": the top-level JSON value is not an object`. With `auto_key=True` it keeps today's `JSON must be a list or a dictionary`. OQ-B covers only a top-level array.
- **Key names in messages**: names are put between plain double quotes (`"name"`) and are not JSON-escaped. A key that itself contains a quote is shown raw. The spec gives the message templates only for simple names.
- **Errors in `memory`**: a `RowsFromFileBadJSON` becomes `Error: <message>` with exit code 1 only when `--key` or `--auto-key` is passed. Without either option, `memory` behaves exactly as today for malformed JSON. The spec defines the CLI error format only for the new options, and JSONKEY-06 asks for no change otherwise.
- **Explicit `:json` suffix in `memory`**: `--key`/`--auto-key` apply to an input with an explicit `:json` suffix, just as they do to an input detected as JSON. The spec says "every JSON input" but describes only detection and the `:csv`/`:tsv`/`:nl` suffixes.
- **When `memory` checks for both options**: the "both options" check runs before any input is opened, even when no paths are given. The spec does not say when this check happens.
- **Help text**: `--key`: "Read the records from this top-level key of a JSON object". `--auto-key`: "Read the records from the one top-level key of a JSON object that holds a non-empty list of objects". I also added a short paragraph to the `insert` and `memory` docstrings. The spec gives no help wording.
- **Shared helper**: `insert`/`upsert`/`bulk` parse JSON themselves and do not go through `rows_from_file()`. Both paths share one private helper, `sqlite_utils.utils._json_records()`. It is not public API, so it is not documented. The spec names only `rows_from_file()` as the Python surface.
- **Documentation scope**: besides the required section under "Inserting JSON data" in `docs/cli.rst`, I added a short note to the `memory` "Explicitly specifying the format" section. I added no entry to `docs/changelog.rst`, which this project writes per release. The spec's documentation criteria mention neither.
