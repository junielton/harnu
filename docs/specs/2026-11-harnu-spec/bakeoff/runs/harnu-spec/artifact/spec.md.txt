# Load JSON records held under a top-level key

## Problem

A JSON file whose top level is an object, with the records under one of its keys, cannot be
imported as records today. Both JSON parse sites wrap a top-level object as a single row with
`if isinstance(..., dict): ... = [...]`:

- `insert_upsert_implementation()` in `sqlite_utils/cli.py`, right after `json.load(decoded)`.
  `insert`, `upsert` and `bulk` all reach it: they share `_import_options`, so all three already
  accept `--nl`, `--csv`, `--tsv`, `--lines` and `--text`.
- the `Format.JSON` branch of `rows_from_file()` in `sqlite_utils/utils.py`, used by
  `sqlite-utils memory` and by Python callers. Today this branch returns a top-level array
  unchanged, with no check of its elements, and raises `RowsFromFileBadJSON` for anything that
  is neither a list nor a dict.

So the requester's example below inserts one row with a `Version` column and a `List` column
holding the array as JSON text, instead of two rows. The user has to run `jq .List` first.

```json
{
  "Version": "5.5.52.6",
  "List": [
    { "Description": "Nonpartisan", "Id": 1, "ExternalId": "" },
    { "Description": "Undeclared", "Id": 2, "ExternalId": "" }
  ]
}
```

Definitions used throughout:

- **The Alaska example** is exactly the document above.
- **A list of objects** is a non-empty JSON array whose every item is a JSON object. An empty
  array, an array of scalars and an array mixing objects with scalars are not lists of objects.
- **A candidate key** is a top-level key of an object whose value is a list of objects. The
  Alaska example has two top-level keys and one candidate key, `List`.

Format detection is unchanged:

- `insert`, `upsert` and `bulk` detect nothing. Input is JSON unless `--nl`, `--csv`, `--tsv`,
  `--lines` or `--text` is given, or `--delimiter`, `--quotechar`, `--sniff` or `--no-headers`
  is given, which today switch the input to CSV.
- `rows_from_file()` with no `format=`, which `memory` uses for inputs without a `:format`
  suffix, treats input whose first non-blank byte is `[` or `{` as JSON. This holds even for a
  single-line object. Any other input is CSV or TSV.

This spec is tier `large`: it records decisions (D-1 to D-3) and non-goals, which a `medium`
spec has no section for.

Request atoms. R-1 to R-5 are the original request, one per sentence. R-6 to R-14 are the
operator's answers to D-1, D-2 and D-3. R-4 is the requester's wording; D-1 settled it as "the one
candidate key, other keys ignored", because the Alaska example itself has two top-level keys.

- R-1 Load JSON records held in a file with a single top-level key that is a list of objects.
- R-2 JSON shaped like the Alaska example (a scalar `Version` beside a `List` of objects) is very common and should import.
- R-3 Today it cannot be imported without running it through `jq .List` first.
- R-4 A rule of thumb: if the input is an object with a single key whose value is a list of objects, use that list instead. (Superseded by D-1: the rule is "exactly one candidate key", other keys ignored, behind `--auto-key`.)
- R-5 Implement it in this sqlite-utils repository.
- R-6 Detection is opt-in through an `--auto-key` flag; without it a top-level object still imports as one row, exactly as today.
- R-7 With `--auto-key`, an input with no candidate key is an error, and so is one with two or more candidate keys; the latter error lists every candidate key; there is no fallback to one row.
- R-8 A `--key KEY` option names the key explicitly.
- R-9 Both options exist on every command that reads JSON input: `insert`, `upsert`, `bulk` and `memory`; in `memory` they apply to every JSON input of the call, and CSV and TSV inputs of the same call import as before, with no error.
- R-10 `rows_from_file()` gains `key=None` and `auto_key=False` keyword arguments, documented in `docs/python-api.rst`.
- R-11 `--key` takes a literal top-level key name: a list value makes each element a row (an empty list imports zero rows and succeeds); an object value is one row; a string, number, boolean or null value is an error; a missing key is an error naming the key; in Python a missing key raises `RowsFromFileBadJSON` with the key in the message.
- R-12 With `--auto-key` a top-level array imports as today; with `--key` a top-level array is an error, and in Python it raises `RowsFromFileBadJSON`.
- R-13 Every error is a clean CLI error: non-zero exit, a message, no traceback. (Read with NG-7: every error these options add.)
- R-14 Accepted edge defaults: `--key` with `--auto-key` is a usage error; `--key`/`--auto-key` with `--nl`, `--csv`, `--tsv`, `--lines` or `--text` on `insert`/`upsert`/`bulk` is a usage error; Python errors are `RowsFromFileBadJSON` (except the both-options misuse, which in Python is a `ValueError`, as for `ignore_extras=` with `extras_key=`); `--flatten` applies to the extracted rows; newline-delimited JSON inputs to `memory` import as before.

## Goals

- G-1 `sqlite-utils insert data.db records alaska.json --key List` (or `--auto-key`) inserts two rows with the columns `Description`, `Id` and `ExternalId`, with no `jq` step.
- G-2 The same two options work on `upsert`, `bulk` and `memory`, and as `key=` / `auto_key=` on `rows_from_file()`.
- G-3 With neither option, every input to `insert`, `upsert`, `bulk`, `memory` and `rows_from_file()` imports exactly as it does today (proven for the shared `insert_upsert_implementation()` path through `insert`, AC-14, and for `memory`, AC-24).

**Non-goals:**

- NG-1 No detection without the flag: a top-level object is never unwrapped unless `--key` or `--auto-key` is given (R-4, R-6).
- NG-2 Sibling keys of the extracted one (`Version` in the Alaska example) are dropped; they are not copied into rows or stored anywhere else (R-2, R-4).
- NG-3 No nested paths: `--key a.b` looks up a top-level key literally named `a.b`; there is no dotted or JSONPath traversal (R-8, R-11).
- NG-4 No new validation of list elements under `--key`: `rows_from_file()` returns the elements unchanged, exactly as it returns a top-level array today, and the CLI then treats them as it treats a top-level array of the same elements today (for `insert`, the existing "Rows must all be dictionaries" error; with `--flatten`, the same failure a top-level `[1]` with `--flatten` gives today) (R-11).
- NG-5 No change to how newline-delimited JSON, CSV or TSV are detected or parsed; `rows_from_file()` ignores `key=` and `auto_key=` for those formats (R-9, R-14).
- NG-6 No per-file error prefix in `memory`: a failing JSON input fails the whole call with the `RowsFromFileBadJSON` message as is (R-9, R-13).
- NG-7 No change to error paths these options do not add: invalid JSON in `memory`, or a top-level scalar given to `insert` with neither option, fails exactly as today (R-13).

**Anti-goals:** a command run without `--key` or `--auto-key` produces a different table than
before this change; any new error path prints a Python traceback.

### S-1 · `rows_from_file()` gains `key=` and `auto_key=`

Add one helper to `sqlite_utils/utils.py`:
`_rows_for_json_key(data, key: str | None = None, auto_key: bool = False) -> list`. It takes an
already-decoded JSON value and applies the rules below, in this order:

1. **Neither option given.** Return the value as today: an object becomes `[obj]`, a list is
   returned unchanged, anything else raises `RowsFromFileBadJSON("JSON must be a list or a dictionary")`.
2. **`key` given** (`key is not None`, so `key=""` looks up the empty-string key). Every "key given" test in S-1 and S-2 is `key is not None`, never truthiness.
   - A top-level array raises `RowsFromFileBadJSON`.
   - A top-level string, number, boolean or null raises `RowsFromFileBadJSON`.
   - A top-level object without `key` raises `RowsFromFileBadJSON` whose message contains the key.
   - Otherwise it looks at `data[key]`:
     - a list is returned unchanged (`[]` included, with no element check: NG-4);
     - an object becomes `[obj]`;
     - a string, number, boolean or null raises `RowsFromFileBadJSON` naming the key.
3. **`auto_key=True`.**
   - A top-level array bypasses candidate detection and is handled exactly as rule 1 handles it.
   - A top-level string, number, boolean or null raises `RowsFromFileBadJSON`.
   - A top-level object with exactly one candidate key returns that key's list.
   - Zero candidate keys raises `RowsFromFileBadJSON` (by the definition of a candidate key, an
     object whose only lists are empty, hold scalars or are mixed has zero).
   - Two or more candidate keys raise `RowsFromFileBadJSON` whose message names every candidate
     key, in document order.

`rows_from_file()` gains the keyword arguments `key: str | None = None` and
`auto_key: bool = False`:

- Passing both a `key` (not `None`) and `auto_key=True` raises `ValueError("Cannot use key= and auto_key= together")`,
  checked right after the existing `ValueError("Cannot use ignore_extras= and extras_key= together")`.
- The `Format.JSON` branch calls the helper in place of its own dict/list check.
- The `format=None` path passes both arguments into its recursive `Format.JSON` call.
- CSV, TSV and NL ignore both arguments.

Document both parameters with `:param key:` and `:param auto_key:` lines in the docstring, which
`docs/python-api.rst` renders through `autofunction`. Add a short paragraph with the Alaska
example under "Reading rows from a file" in `docs/python-api.rst`.

### S-2 · `--key` and `--auto-key` on `insert`, `upsert`, `bulk` and `memory`

Add two options to `_import_options`, which reaches `insert`, `upsert` and `bulk`:

- `click.option("--key", help="Import the list of objects stored under this top-level key")`
- `click.option("--auto-key", is_flag=True, help="Import the one top-level key that holds a list of objects")`

Add the same two options to `memory`'s own options.

Plumbing: the `insert`, `upsert`, `bulk` and `memory` command functions gain `key` and `auto_key`
parameters. `insert_upsert_implementation()` gains `key=None, auto_key=False` keyword
parameters, appended after its current last parameter `code=None`, and the three calls to it (positional from `insert` and `upsert`, keyword from `bulk`)
pass `key=key, auto_key=auto_key`. `cli.py` imports `RowsFromFileBadJSON` and `_rows_for_json_key`
from `.utils`.

In `insert_upsert_implementation()`, the new checks run in this order, and the first that fails is
the error. R-14's "usage error" is a `click.ClickException` (exit 1), like the existing option checks:

- `key is not None` and `auto_key` join the list the existing `--code` check tests (the
  `if any([flatten, nl, csv, tsv, empty_null, lines, text, convert, sniff, no_headers, delimiter, quotechar, encoding])`
  inside `if code is not None:`), so `--code` with
  either option raises its existing "--code cannot be used with input format options" error.
- Both options given raise `click.ClickException("Use either --key or --auto-key, not both")`.
- Either option given after the existing CSV switch has run (so `csv`, `tsv`, `nl`, `lines` or
  `text` is set, including through `--delimiter`, `--quotechar`, `--sniff` or `--no-headers`) raises `click.ClickException("--key and --auto-key can only be used with JSON input")`.
  This check sits right after the CSV switch line
  `if (delimiter or quotechar or sniff or no_headers) and not tsv: csv = True` and before the existing `(nl + csv + tsv) >= 2`,
  `--flatten`, `--empty-null` and `--encoding` checks, so `--key --csv --flatten` reports this error.
- After `json.load(decoded)`, when `key is not None` or `auto_key` is set, it calls
  `_rows_for_json_key(docs, key, auto_key)` in place of today's dict check; with neither option,
  today's code runs unchanged (NG-7). It catches `RowsFromFileBadJSON` and re-raises it as
  `click.ClickException(str(ex))`.

`memory`:

- Both options given raise the same `click.ClickException` as above. This is the first statement
  of the function body, before any input is opened.
- `memory` reads every input through one `rows_from_file(fp, format=format, encoding=encoding)`
  call inside its `for i, path in enumerate(paths)` loop. It passes `key=` and `auto_key=` to that call, whatever the input's
  `:format` suffix; `rows_from_file()` ignores them for CSV, TSV and NL. A call with no JSON
  input at all therefore accepts the options and imports as without them.
- It catches `RowsFromFileBadJSON` around that one call and re-raises it as `click.ClickException(str(ex))`.
  Nothing catches it there today.

Every error therefore exits with code 1 and prints `Error: <message>`. AC-23 is the final gate:
it runs the full suite on the S-2 branch, which already holds S-1 (`depends-on: S-1`); AC-28 runs
it on S-1 alone.

Document both options in `docs/cli.rst`, in a new section right after "Flattening nested JSON
objects". The section has the label `.. _cli_inserting_data_key:`, the title "Importing records
held under a top-level key", and the same heading level (a `---` underline). It shows the Alaska
example with `--key List` and with `--auto-key`, and states the two error cases of `--auto-key`. Then regenerate `docs/cli-reference.rst` with `uv run --group docs cog -r README.md docs/*.rst`,
the repo's `cog` recipe (`Justfile` line 27; its lint recipe runs `uv run cog --check README.md docs/*.rst`, line 21).
Only `docs/cli-reference.rst` embeds the `insert`, `upsert`, `bulk` and `memory` help. `README.md`
has no cog block, and the one cog block in `docs/cli.rst` lists tabulate formats. So
`docs/cli-reference.rst` is the only file cog rewrites, and any other file cog changes is a stop.
