# Missions v4: one Mission → Milestone → Step model, shown in a Mission pane beside the session

## Problem

Missions and Campaigns grew in layers (goal files, Mission v1 to v3, Campaign chapters 1 to 6, the steward, the merge batch). Each layer added states, lists and surfaces and retired none. The operator opens the popover to find calm and leaves stressed. Measured on `main` at `fa5feba6` (2026-11-14):

| What                      | Today                                                                                                                                                                                                                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| State vocabularies        | 6: stored status (5 values, 3 written), proof plus verdict, 7 step states, 5 gates times 5 states, 5 chapter states, 7 pill states                                                                                                                                                              |
| "What waits on you" lists | 3 that disagree: the server list (10 kinds), the popover (adds a decide row and, until T701 removed it after this measurement, a merge-batch row), the Activity cue and the sidebar chip (ignore both)                                                                                          |
| The pill                  | Mixes two missions: the campaign's current chapter next to the owned mission's step ("Ch. 9/12 · Step 2/4"); up to 4 numbers and 12 ticks in 18 px                                                                                                                                              |

The operator's decisions of 2026-11-13 and 2026-11-14, one atom per decision, plus the three constraints the delivery adds:

- R-1 Rethink from the concept, borrowing from project management: one hierarchy, tasks unified with the board, one state flow, one queue of what waits on the operator.
- R-2 The hierarchy is Mission → Milestone → Step; a step is one pull request and, when it is dispatched to its own session or worktree, the board card (the operator said the step is the card; D-16 narrows it to dispatched steps); Campaign and Chapter go away.
- R-3 Acceptance criteria live on the step, each settled by an automatic fact, a second session or the operator; the mission keeps its own "Done when"; a milestone has none.
- R-4 The merge batch is removed entirely.
- R-5 No popover: the Topbar pill stays and toggles a Mission pane in the helper stack.
- R-6 The pane follows the selected session and shows only that session's mission; the folder's open missions are listed only in the "no mission" state, as an attach picker.
- R-7 Glance first: the pane reads as "I did this, so this, there is this, and this is the next step"; no long "Done when" paragraph; the task count sits inside the progress bar.
- R-8 A tree with chevrons, milestone then step then criteria; only the current milestone opens by itself.
- R-9 The mission is durable and the session is disposable: the mission keeps its plan, brief, history and the list of sessions that worked on it (role, from and to, where each stopped); a fresh session continues from the brief.
- R-10 Attaching a session to a mission needs confirmation; a session only sees and touches the mission it is attached to.
- R-11 The operator always decides a hand-off; Harnu may notice and offer and never switches sessions by itself.
- R-12 The pane is the only surface: no kanban full view of a mission and no cross-mission "My work" queue.
- R-13 A vertical line joins the milestone glyphs (green past a done milestone) and runs through an open milestone's steps.
- R-14 Mission text follows a writing contract: a tired reader, several sessions, no context from the session that wrote it.
- R-15 The Campaign map is removed; the pane replaces its tiles, "You are here", You ledger and focus panel.
- R-16 Scope for now is one orchestrator at a time; parallel work is steps in parallel inside the current milestone, each with its own worktree and session; milestones are planned in order.
- R-17 Parallel work shows in the milestone summary ("4 running · 9 waiting for review · 1 blocked"); inside a milestone the order is what needs the operator, then what runs now, then the rest collapsed.
- R-18 A step receives links from its session: the pull request, and the address of the finished page.
- R-19 A small task is a mission with no milestones; its steps sit directly on the timeline.
- R-20 `scope-task` pulls a task's acceptance criteria and links into the mission.
- R-21 A fourth way to settle a criterion is another person (a QA analyst, a designer); the operator marks it when the person approves and Harnu does not watch the tracker.
- R-22 The mission pane is proactive: when a session shows intent or work that will clearly take several steps, the mission, its steps and the next step appear without being asked for.
- R-23 Missions and campaigns written by the current version stay readable, are never rewritten in place without keeping the original, and a campaign that is mid-flight keeps going.
- R-24 The agent side (verbs, skills, awareness doc, user docs) speaks the same model.
- R-25 The domain leaves the MCP handlers: one module, a read with no side effects, one server-owned waiting list.

The research behind this spec (a diagnosis, four maps of the current code, UI, history and agent side, and the operator's decision record) is kept outside the repository. Everything a slice needs from it is restated here, with `file:line` pointers kept only where they are stable.

## Goals

- G-1 The operator reads one pane beside the session and knows where the mission is, what is done, what is left and what waits on them, in one glance.
- G-2 One model: Mission, optional Milestone, Step, with acceptance criteria on the step and one state vocabulary.
- G-3 What a fact can settle is settled by the fact; nobody ticks what Harnu can see.
- G-4 A mission outlives its sessions: a fresh session continues from the summary, and the operator decides when.
- G-5 Agents write short, plain mission text because the verbs refuse anything else.
- G-6 The agent side is smaller: 16 verbs instead of 22, an awareness section under 2,000 words instead of about 6,900, skills that say the same thing the pane shows.
- G-7 Every record written by the current version still opens, and no v4 build ever modifies one.

**Non-goals:**

- NG-1 No kanban view of a mission and no cross-mission "My work" queue (R-12).
- NG-2 No several orchestrators at once and no view across missions or sessions (R-6, R-16).
- NG-3 No sidebar tag as the cross-session "needs you" signal (R-6).
- NG-4 No limit on the review queue, no ready-to-start rule before dispatch, no ordering of what waits by age (R-1).
- NG-5 Harnu does not watch the tracker to tick another person's sign-off (R-21).
- NG-6 No merge batch, merge engine or any surface that merges (R-4).
- NG-7 Harnu builds no timeline of its own for a session that has no mission, because no transcript carries a step list; decision 22 is met by the session creating the mission itself, which makes the timeline appear (R-22, D-2, D-22).
- NG-8 No bulk conversion of stored files at upgrade, and no write to a v3 file by any v4 code (R-23).
- NG-9 This delivery does not change the operator's personal `scope-task` skill, which lives outside the repository; that is a follow-up the operator owns. v4 ships the door that any skill can use to create a step with its criteria and links from a tracker task (R-20, D-28).

**Anti-goals:** a plan an agent can silently shrink; a mission the operator cannot find because its leader session is gone; a hand-off Harnu makes by itself; a record from the current version that the new build cannot open; a v3 file rewritten by a v4 build, which the installed build running beside it could then no longer read; a pane that grows into another overloaded popover (more than the glance plus one open step on screen at rest).

### Design · The model

**Entities.** A **Mission** is the objective. A **Milestone** is an optional stop on the way. A **Step** is one unit of work, one pull request, and has a board card only when it is dispatched to its own session or worktree (D-16). An **acceptance criterion** (AC) is a fact that is true when its step is done. A mission with no milestones is valid and is the small-task shape (R-19). The old Campaign is a Mission, its Chapter is a Milestone, its Step is a Step. The fixed step "Delivered and verified" is gone; the mission's **Done when** (one sentence) is confirmed by the operator at close.

**The v4 record** (one Markdown file with YAML frontmatter and an append-only Log, in `.harnu/missions-v4/`, a new directory, so the v3 directory `.harnu/missions/` is only ever read; every schema stays `.passthrough()`):

```yaml
schemaVersion: 4
id: mnt-1a2b3c4d
title: Measure harnu:spec, then fix what the numbers show # 60 characters at most
doneWhen: A test set we trust scores harnu:spec, and two fixes are each proven by the score.
status: open # open or closed; closedAs and closeReason once closed
closeRequested: { at: 2026-11-14T10:00:00Z } # the agent says "ready"; one fact, no second status
milestones:
  - { id: mls-1, title: A test set we can trust, optional: false, waitsFor: null }
steps:
  - id: stp-1
    milestone: mls-1 # absent when the mission has no milestones
    title: Load the test files # 50 characters at most
    card: T685-load-test-files # only when the step is dispatched to its own session or worktree
    startedAt: 2026-11-13T09:30:00Z # set when a dispatched step starts or the leader starts a step it does itself
    acs:
      - { id: ac-1, text: The pull request is merged, by: fact, fact: pr-merged }
      - { id: ac-2, text: Every reviewer question has an answer, by: session }
      - { id: ac-3, text: The designer signed off, by: person, person: the designer }
    links: [{ kind: pr, ref: '256' }, { kind: url, ref: 'http://localhost:5173/score-report' }]
    blockers:
      [{ id: blk-1, reason: …, ask: …, unblocks: …, owner: operator, clearsWhen: pr-merged }]
    waitsFor: null
sessions: # the history of who worked on it
  - { id: <session uuid>, role: leads, from: 2026-11-13T09:00:00Z, to: null, stoppedAt: null }
links: [{ kind: doc, ref: docs/specs/example/spec.md }]
blockers: []
legacyV3: … # only on a record converted from v3: the values the mapping drops; the v3 file stays whole beside it
```

A criterion is settled when `fact` holds now (derived, never stored) or when its `settled` stamp exists (`{ at, by, evidence }`; stored for the three human-shaped ways). Caps are enforced by the verbs on write (see the writing contract) and never on read.

**One state vocabulary.** A step is **to do**, **running**, **waiting for review** or **done**. **Blocked** is a mark on a step, never a fifth state. First match wins:

1. `done`: every criterion settled, or the operator closed the step's card.
2. `waiting for review`: not done, and the work exists (a pull request is open or merged) while some criterion is open; or the step has no pull request and only operator or person criteria are still open, which is how a sign-off step reads.
3. `running`: a session other than the leader is working on it, its card is in progress, or the leader has started it (`startedAt`) and no pull request exists yet.
4. `to do`: otherwise (the board's Backlog and Ready both read as to do, D-6).

A milestone is **not started**, **in progress**, **waiting for review** (every unfinished step waits for review) or **done**, derived from its steps. More than one milestone can be open at once (D-9). The mission is **open**, **ready to close** (every required step is done; derived) or **closed**. "Delivered" stops meaning three things: closed as delivered is the operator's door, ready to close is derived, and the agent's close request is the single `closeRequested` fact.

**What settles a criterion.** Four ways and no other:

| Who or what      | How                                                                                                                                          | What is stored                         | Shown as             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | -------------------- |
| A fact           | Harnu reads it: `pr-opened`, `ci-green`, `pr-merged`, `main-green`, `link-exists`. Sticky when GitHub is unreachable, never a downgrade      | nothing (derived)                      | settled, "automatic" |
| A second session | A session that did not build the step calls `mission_settle_ac` with evidence. A session that built it only self-checks, which never settles | `settled { at, by, evidence }`         | "second session"     |
| The operator     | The "Mark done" door in the pane                                                                                                             | `settled { at, by: operator }`         | "you"                |
| Another person   | The operator marks it when the person approves (decision 21); it shows as "waiting for the designer" and is not the operator's next step     | `settled { at, by: operator, person }` | "the designer"       |

A blocker may declare the fact it waits for (`clearsWhen`); when the fact holds it stops showing and needs no manual clear (D-12). A criterion tied to a fact is never ticked by hand.

**Progress, next step and the waiting list** are derived once, server-side, from one pure function with no side effects, and read by the pane, the pill, the sidebar chip, Your move, the companion and MCP. Progress counts milestones when the mission has them ("1 of 10 milestones done", D-10) and steps when it has none; optional milestones and steps are outside the count and collapsed (D-13). The **waiting list** has one item type and a fixed rank: `main-failing` (a merged step whose `main` fact is red), `unblock` (an operator-owned blocker, a decision included), `settle` (an operator criterion to mark), `review` (pull requests that wait for the operator, grouped as "Look over N pull requests"), `close` (ready to close), `attach` (a session asks to lead or join). The first item is **Your next step**; the others are "N more waiting on you", one click away (D-14). A person's sign-off is not in the list; it is a line "waiting for other people". Each item carries `ask` (what to do, at most 90 characters) and `why` (what it unlocks, at most 60); no consumer writes its own wording.

**The durable mission.** The mission lives in the folder with its plan, Log and `sessions` history. A **session** is attached with a role: `leads` (at most one, decision 16) or `worked` (it built or checked a step). Each entry keeps `from`, `to` and `stoppedAt` (the step it was on and what it was waiting for). A session only sees and touches the mission it is attached to; a session that is not attached is refused `NOT_ATTACHED` with the way out (ask to join). Attaching needs the operator's confirmation: from the pane's picker it is a confirm dialog, from the agent it is a request the operator allows or denies. A session that creates a mission is attached to it and leads it with no confirmation: the confirmation applies only when a session asks to join a mission that exists or that another session leads. A session dispatched for a step (`submit_manifest`, a board dispatch, or `create_session` by the leader) is attached as `worked` without a prompt, not because the dispatch was approved (`create_session` runs without any operator approval) but because a `worked` session holds only the scoped verbs of its own step and so can neither lead nor touch another mission (D-19).

**The summary and the hand-off.** One deterministic function builds the **mission summary** from the record alone, at most 8,000 characters (about 2,000 tokens), with five parts: **Goal**, **Where it is** (milestone position and the four counts), **Decided** (the last five Log entries of kind decision), **Stopped at** (per session), **Next step** (the first waiting item), plus the open criteria of the open steps and the links. It replaces the post-compaction Mission Brief (D-5) and is served to the leader after a compaction and to a fresh session at the start of a hand-off. Harnu may notice that the leading session's context is high (80 percent of the window or more, read from the status-line data Harnu already collects for the session; with no reading there is no offer) and offers "Continue in a new session…"; the operator confirms; only then does Harnu start the session, attach it as `leads`, set the old one to `worked` with `to` and `stoppedAt`, and release it. Nothing else ever starts a session or changes who leads (R-11).

**A step is a board card when it is dispatched.** A step that goes to its own session or worktree is a board card: dispatching it (`submit_manifest`, a board dispatch, or `create_session` by the leader with the step) creates or binds the card in `backlog` and stamps `mission`, `milestone` and `step` on it; `roadmap-core.ts` gains those three system fields, which `update_card` refuses. A step the leading session does itself has no card, so small work never floods the board and the two trackers never track the same work twice (D-16). The criteria live on the step in the mission file (the single source); the card body carries them as one marked block `<!-- mission:begin stp-n -->` … `<!-- mission:end -->` that only Harnu rewrites, so an executor reading the card sees them. The card's column is an input to the step's state (D-6); Harnu never moves a card to `done`. The operator closing a card reads as the step done.

**Who may read and write.** Stated once and applied by every verb: **write** only from a session attached to the mission; **read the detail** (`mission_get`) from an attached session and from a Harnu system worker bound to that mission or folder (the Scheduler's observe worker); **list** (`mission_list`) from any session in the folder, as one-line rows (id, title, headline, who leads) with no steps, criteria, links or history, which is what "ask to join" needs. An unattached session may therefore list, and may ask to attach (that request is how it leaves `NOT_ATTACHED`); only reading the detail and writing are refused to it. The app's own interface is not a session and reads everything.

**Facts, and who is trusted.** The principles that survive from v3 are unchanged: N is position and never proof; the server counts once; the operator holds every door (close, discard, mark, approve a new Done when); close is never refused, open matters are warnings; the agent can add to a plan and never shrink it; a self-check is labelled and never proof; stall is deterministic and never stored; gates are derived and never stored; memory is written only from drafts the operator ticks; a false alarm beats a miss. One improvement: for a session Harnu spawned, the session id comes from the session's own credential (S-25), so "a second session" is checkable; for any other session it stays self-declared, convention plus audit.

### Design · The surfaces

**The Mission pane** (`MissionPane.vue`) is a pane in the helper stack. The Topbar **pill** (`4/21 · 3 for you`, the server's numbers for this session's mission) toggles it. The pane follows the selected session and shows only that session's mission (R-6). Top to bottom, as in the draft mockup:

1. The mission title; the progress bar with the count inside it ("4 of 21 steps done", or "1 of 10 milestones done"); no Done when paragraph.
2. **Your next step**: one box with the ask, the why, and one button; "N more waiting on you" expands in place.
3. The tree: milestone (chevron, glyph, title, count) ▸ step (title, state, `#256` dimmed at the right) ▸ criteria. A vertical line joins the milestone glyphs and runs through an open milestone. Only the current milestone opens by itself. A milestone line carries its summary ("4 running · 9 waiting for review · 1 blocked"); inside, steps run needs-the-operator, then running, then the rest behind "N more". Optional milestones sit under one collapsed line. A milestone that waits on one that is not the previous says "waits for X".
4. An open step lists its criteria with who settles each; verified ones collapse into one line ("19 criteria verified"); a blocked step shows the exact thing needed and "Done, continue"; "Links from the session" lists the pull request and the finished page.
5. **Sessions** (count, who leads) opens the history and "Continue in a new session…". **Ask** on a milestone sends a question to the leading session (D-1).

The other states, all in the mockup: no mission (attach picker of the folder's open missions and "Start a new mission"), attach request (Allow, Deny), hand-off suggestion and confirmation (with the summary the new session starts from), clear, done (Close mission…), closed (the pane toggled off; a mission the operator closed leaves the pane and the session shows the no-mission state), another session's mission, a small task and its sign-offs, a real 10-milestone mission waiting on five things. A **sample mission** renders the pane from a built-in fixture with no file, so every state can be seen without a live delivery.

**Until the cut-over** (S-35) a v3 record is served by the v3 stack unchanged: its pill opens the popover, its doors are the popover's, and no v4 code writes it. The pane serves v4 records and the sample mission. **The current milestone**, wherever the pane needs one, is the first milestone in plan order that is neither done nor optional.

**Removed (the last slices of chapter 5, after every caller has moved):** the mission popover, the campaign popover, the step rail and glyph, the campaign map (Ch. 1), the merge batch (Ch. 1), the steward dialog and Stewards block, the review and bulk-close dialogs (D-18), and `campaign-view`, `campaign-map`, `steward-view`, the campaigns store and `campaign-ipc`. **Kept, reading the v4 view:** the sidebar chip (not clickable, as today), the Activity cue (a notification, not a surface), Your move cards, the companion mod, the hibernation exemption. **Not built:** a kanban view, a cross-mission queue, a campaign map.

**Sessions Harnu spawns (BUG-253, built in S-25).** A session spawned for a step gets a per-session scoped credential (the mechanism the steward already uses, generalized and moved out of `steward-core.ts`). Role `worker`: `mission_get`, `mission_link`, `mission_log`, `mission_set_blocker` on its own step. Role `verifier`: the same plus `mission_settle_ac`. ### Design · Compatibility with records written by v3

Missions are in `.harnu/missions/` and campaigns in `.harnu/campaigns/` of every repo that used v3 (77 mission files and 7 campaign files in this repo alone), and some are in progress, including the mission and campaign that deliver this spec. The operator also runs an installed build of the current version beside any build of main, in this repo and in others. A v3 file rewritten by a v4 build could no longer be read by that installed build, so the rule is stronger than "keep the original": **a v4 build never modifies a v3 file, ever.** All of them stay readable. The rules:

1. **A read is a view, never a write.** `readMissionRecord` (in `record-store.ts`) looks for a v4 record in `.harnu/missions-v4/` first; if there is none it parses the v3 file with the frozen reader `v3-read.ts` and converts it in memory with the same pure function that conversion uses. Reading changes no byte and no `updatedAt`. Readers skip dot-directories.
2. **A write creates a v4 record by copy.** The first v4 write for a mission born in v3 (a v4-shaped verb or a door) writes `.harnu/missions-v4/<same id>-<same slug>.md`, converted from the v3 file as it is at that moment. The v3 file stays byte-identical. The id stays, so a running session's prompt keeps working. The installed build reads only `.harnu/missions/`, so it never sees a v4 file and never fails on one.
3. **A campaign converts by copy into one new mission.** A campaign and its chapter missions become one mission written on the first v4 write to any of them: id `mnt-` plus the first 8 hex of the sha256 of the sorted source ids (so conversion is deterministic and idempotent), and a sidecar `.harnu/missions-v4/.migrated/<old id>.json` that says "superseded by `mnt-…`", so every old id resolves to the new mission. The campaign and chapter files are not touched. Until that first write the campaign reads as one mission through rule 1.
4. **One format at a time.** Once a v4 record exists for an id, it is the mission and the v3 file is a snapshot. A v3-shaped verb aimed at it is refused with the way out (AC-67). The v3 stack serves a v3 record until the cut-over (S-35); no door writes one before then.
5. **What an installed v3 build then shows:** the mission as it was at the last v3 write, which is the moment of the first v4 write, and no later change; it never errors. Work an agent keeps doing in the installed build on that mission writes the v3 file and is not seen by the v4 build, so a live mission should be worked in one build after its first v4 write. For a campaign the installed build keeps showing the campaign and its chapters as they were.
6. **Retiring the steward writes no mission file.** It removes the Scheduler worker and the hooks and raises one Activity notice listing the missions affected (AC-69).

## Slices

**Rule for every slice: every file that must change for CI to be green at the slice's head is in that slice's `files-may-touch`.** A test that pins the text or the shape of a file belongs to the slice that changes that file, or to an earlier one; a test that reads several skills belongs to every slice that rewrites one of them, and the last of those deletes it when nothing it pins survives. A slice that deletes a module lists every importer of it (the lists below are the output of `git grep` on `origin/main`, minus the files chapter 1 or an earlier slice deletes), or names the earlier slice that repointed the importer. **Pins travel with the file.** Beyond its `files-may-touch` line, a slice may also change (a) a test that pins the text, the shape or the existence of a file in its scope, (b) a typed registry that must hold one entry per item the slice adds, renames or removes (for example the per-verb maps in `src/main/mcp/validate.ts` and `src/main/mcp/plan-input.ts`), and (c) a file that imports a module the slice deletes, when the only change is removing or repointing that import. It may do so only when CI cannot be green at its head otherwise. The slice's report lists every file touched under this rule with the in-scope file it pins or imports; the verifier checks each one and counts anything else outside `files-may-touch` as a scope breach. The lists in the slices below are the files known today; the rule covers the ones that surface later. One `###` block per slice: one branch, one session, one pull request. Chapter headings are plain text in this section because the gate reads every `###` here as a slice. `acs:` lists ids from the table below, nothing else. Every slice also keeps the repository's rules: English only, no client identifiers, `npm run typecheck` and the `local-ci` gates before the last push, and the CPU cap (at most half the cores, `--maxWorkers=4`).
