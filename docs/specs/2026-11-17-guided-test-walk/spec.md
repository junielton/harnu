# Guided walks: a fixed pane that walks the operator through a feature, a PR or a mission, one check at a time, saved and re-runnable

## Problem

Agentic work leaves the operator with things they did not watch being made, and some of what proves them is only the operator's eyes. Four situations have no home today:

1. **Learning a feature that was just built.** The operator often did not learn what was built while it was being built. They need to be shown what it does, where it lives and why it behaves that way.
2. **End-to-end QA of a feature.** "I want to test it from end to end and don't know where to start": the session builds the big list, and the operator walks it point by point.
3. **Testing someone else's PR**, for example a colleague's: a walk built from the PR (its diff, description and linked task).
4. **Mission QA at any level:** one step, one milestone, or the whole mission at its end.

What exists:

- The `step-by-step` skill walks a list in chat, one message per step. It is the operator's favourite way to work, but the walk lives in a scrolling transcript: it is lost on a compaction, its links and commands are Markdown, it cannot show an image beside the sentence, nothing records which check was verified how, and nothing keeps the walk for the next time.
- The Missions v4 delivery hand-made a 23-item `visual-checks/index.html` page to do this job. A page an agent writes for each walk looks different every time, repeats colours and sizes by hand, and cannot call anything inside Harnu.
- Learning mode (a `quiz` block in the Markdown pane, answered with a `[harnu-lesson]` turn) shows that a rich pane next to the session works. But a lesson is generated Markdown, not a product-grade fixed template.

The operator's decisions of 2026-11-17 (card T765, its notes and decision block, the brief of this spec, and the scope correction after the mockup), one atom per decision:

- R-1 Let the operator walk a guided panel in the helper stack, one check at a time; each check says exactly what to do and what they should see.
- R-2 There is no Markdown prototype: one fixed template, built once in the repo and faithful to `design.md`; the agent never writes HTML for a walk, it sends data (JSON: the checks, the images, the source) and the template renders it.
- R-3 Every entry point starts the same panel: from any session (a plain sentence, a skill or `/walk`: "walk me through what we just built", "test PR #48 with me"), from a Walks library, and from the Mission dropdown on a step, a milestone and the whole mission. A walk opens in the helper stack, never inside the dropdown.
- R-4 The session that holds the context writes the script, never a blank one: for a feature, the session that built it; for a PR, a session handed the PR; for a mission, the leader or a session handed the mission summary. Its sources are the diff, the description and linked task, the criteria, the summary and Log, the spec, the verifier's evidence and its own memory of what was hard.
- R-5 "Explain more" deepens one check from that same context and is core, not an extra: it explains why the check matters, appends edge-case checks under the current check, and, for a walk-through, teaches (what this part does, the file or concept behind it, with a link). The walk does not restart.
- R-6 The panel keeps the contract of the `step-by-step` skill, and the spec proves it with a conformance matrix (one row per rule, the three columns asked for); the skill gains a "panel" mode instead of being forked.
- R-7 Every link is clickable and opens the real thing (a PR, a file in the viewer, a URL in a browser pane, a folder); every value is copyable with one click.
- R-8 Failure capture takes one line plus a pasted screenshot; each check shows "Where" and "Observe" lines; an approximate dashboard path is marked as approximate.
- R-9 Enter means Done, and the skill's text controls exist as shortcuts; progress reads "Check 3 of 9" and nothing else; every element earns its place (minimalism first).
- R-10 Decide whether the final pane is a live-panel template or a native Vue pane fed by the same JSON, with a recommendation; the visual system is `design.md`, and the visual section is the approved mockup (revision 2) and its 28 decisions.
- R-11 Decide whether Done settles an operator criterion directly or stays a separate Mark done, and how an image is attached per check (mockup frame or live capture).
- R-12 A smoke test runs against the real app in an isolated second instance, and unit tests cover the view-model rules it does not.
- R-13 A walk survives a reload, a park and a compaction; agent-facing and user-facing documentation and the changelog are part of each slice.
- R-14 A walk is a first-class object of its own, not a mission feature. It has a title, a source, a list of checks and a run history. The source is one of: a free-text or feature description, a PR (number or URL), a branch or diff, a mission (whole, milestone or step), or a card. Mission persistence (operator criteria) applies only when the source is a mission; a PR or feature walk writes nothing to any mission.
- R-15 Walks are kept, not thrown away: saved per repo (the owner recommends `.harnu/walks/<id>/`, private to the machine, one JSON file for the checks and one file per run), so the operator can see the history (when it was walked, the outcome per check, notes, screenshots), reopen a past walk and re-run it later as a fresh run of the same checks.
- R-16 A Walks library lists past walks, a short list and not a dashboard: title, source, last run, outcome such as "8 of 9 passed", each with Re-run and Open, plus an empty state. A past run opens read-only with its notes and screenshots and a Re-run button; a run in progress that is a re-run shows a quiet "last time" hint per check.
- R-17 An Export action produces a Markdown copy of a walk to share or commit.
- R-18 The same pane serves a walk-through of a feature just built, end-to-end QA, testing someone else's PR, and mission QA at the level of a step, a milestone or the whole mission.
- R-19 Triggering a walk outside a mission is a first-class requirement: in any Harnu session a plain sentence ("harnu walk me through what we just built", "test PR #48 with me", the same in the operator's language) or `/walk` must work, through core MCP verbs that open and update a walk panel and read and save walks (always available when Harnu's MCP is on, documented in `docs/harnu-features.md`) and a walk skill that carries the contract; whether that skill ships on by default is a decision, and a smoke case proves a plain sentence in a fresh session opens a walk.
- R-20 The end of a feature may offer a walk once, with the mockup's three options (Walk me through it, Test it end to end, Not now); the offer cannot be a card drawn in the terminal, so how it appears is a decision.

Where to find things: the spec gate allows only six `##` sections, so the design sits under Goals (the shape, the walk and run model, the data contract, the flow, the library and re-run, the events and verbs, where things live, the recommendation for D-1, and the visual section, which follows the approved mockup), the smoke test and the conformance matrix sit under Acceptance criteria, and each decision is a row of Open decisions.

## Goals

- G-1 From a session, from the library or from the Mission dropdown, the operator starts a walk on a feature, a PR, a branch, a card or a mission, and a pane opens beside the session with check 1 of N. They answer each check with Done, Failed, Back, Skip or Explain more, and finish on a close-out that names how each check was verified.
- G-2 The walk is the `step-by-step` contract, kept by construction where a program can keep it and proved by the matrix and the smoke test where it cannot.
- G-3 An agent never writes a pixel of the pane. It sends JSON that a validator accepts or refuses whole.
- G-4 Nothing the operator owes is lost to a reload, a parked session or a compaction.
- G-6 In any session a plain sentence opens a walk, because the verbs are core and the skill that carries the contract is on by default.
- G-5 A walk outlives its first run: it is kept per repo, listed in a library, readable as history, re-runnable as a fresh run and exportable as Markdown.

**Non-goals:**

- NG-1 No Markdown prototype and no per-walk HTML, and no script generated from a diff or from criteria alone: a walk is written by a session that holds the context (R-2, R-4).
- NG-2 The Mission dropdown itself (its anatomy, its states) is the work of its own redesign and is not redone here; this spec only adds one control to a step, a milestone and the mission in it (R-3).
- NG-3 `harnu:one-by-one` is not changed (card T765, out of scope; R-6 concerns `step-by-step` only).
- NG-4 No verb lets an agent press a button of the pane, settle a criterion, perform a check, re-run, export or delete a walk; the operator's clicks are theirs (R-6, R-15).
- NG-5 Harnu does not capture screenshots of the running app for a walk in this version (an image is a file the agent already has), and the pane creates no board card or bug card: a failure becomes a card only when the agent offers it or, after the second failure, when the operator presses the escalation door and the agent acts on it (R-8, R-11, D-3, D-10).
- NG-6 A walk is not a mission tracker: it adds no step, milestone or criterion to any mission, and it never settles a criterion: with a mission source it links to Mark done in the Mission (R-14, D-2).
- NG-7 The chat behaviour of the two skill copies is not reconciled here: the bundled copy is not rewritten to the personal one's contract, which is a separate card (R-6, D-9).
- NG-8 The library is a list, not a dashboard (no charts, trends, scores across walks, filters beyond one outcome line per walk), there is no sharing or sync beyond the Markdown Export, no "Walk this PR" control on PR cards and no "New walk" form: a PR or feature walk starts from a session (R-3, R-14, R-16, R-17).
- NG-9 No walk templates, no scheduled or automatic re-runs (a re-run is the operator's click), and the optional "only what failed or was skipped last time" toggle of a re-run is a follow-up (R-15).

**Anti-goals:** outcomes that would make this a failure even if every AC passed.

- The operator presses Enter out of habit and a criterion is settled that nobody checked.
- The pane becomes a second place to read mission state, and the two disagree.
- The agent chats a paragraph for every button the operator presses, so the transcript the walk was meant to quiet gets louder.
- A walk reads well but the operator, three checks in, cannot tell what they should see.
- The library grows into a pile of stale walks that nobody dares re-run, because a re-run shows last time's answers as this time's.

### The shape: what the operator sees

One pane in the helper stack (`type: 'walk'`, `GuidedWalkPane.vue`) with the standard helper-pane header (the walk's title, expand, maximize, close) and, under it, a quiet **source line** (V-19). Where each element sits and how large it is is the approved mockup's (see "Proposed `design.md` section"). The pane opens on the roadmap and then serves one check at a time:

1. **Source line.** An icon and the source. For a PR, `PR #48 · title · author` (a link, with a copy of the URL); for a mission, the step, milestone or mission it covers (a link that opens the Mission dropdown); for a branch, `branch → base`; for a card, its slug; for a feature, its short description (plain text). On a re-run, a `Re-run · run N` chip.
2. **The roadmap (before check 1).** All N checks as rows with their glyph. Checks verified before the walk carry their evidence, each open check says how it will be checked, and what is left out ("ours") is one folded line. One primary action, **Start with 1** (Enter). A list icon beside the progress opens the roadmap again later (shortcut `L`).
3. **Progress.** `Check 3 of 9`, and a 4 px strip of one cell per check under it (closed, current, the rest) with no text. Nothing else is written about progress (V-7).
4. **The check.** Its title; under it, on a re-run, a quiet "Last time" line, and where a later check depends on it a quiet "Checks 2 to 6 depend on this one" (V-15). **Do**, numbered, with every command as a paste-ready block; **Where**, link chips each with a copy and the "path approximate" tag; **You should see**, the literal expected text, a muted `✗ Not: …` line (V-6) and the image as a 300 px thumbnail that enlarges (V-9); **I'll check**, the read-only check or "Nothing from here: why"; a quiet link **I didn't get this step** (V-3). In a walk-through a check's teaching and its edge checks sit behind **Explain more**.
5. **The action bar**, pinned: **Done** (primary, with an Enter chip), **Failed**, **Back**, **Skip**, **Explain more**; the other shortcuts are in tooltips (V-2). These five are on every check at the moment it asks for the operator's answer. While the agent checks, the pane shows one quiet line and no actions; after the agent disagrees it shows the evidence card (below).

Press Failed and the pane asks for one line and a pasted screenshot, nothing else. Closing the pane with its X, once at least one check is closed, asks one question, "End the walk and see the close-out?" (V-11). The close-out replaces the check when the run ends.

### The walk and the run: the model

A **walk** is what is kept: its title, its `purpose`, its **source**, its checks and what Explain more has added to them. A **run** is one pass through a walk: when it started and ended, who owned it, and per check the outcome, the attempts, the failure line and screenshot, the correction, the agent's report and how it closed. A walk has many runs; **one run may be live at a time** per walk.

- **Sources.** `source.kind` is one of:
  - `feature`: free text (at most 300 characters) saying what was built;
  - `pr`: `number`, `title`, `author` and optional `url` (a PR's own header);
  - `branch`: `branch` and `base` (a diff);
  - `mission`: `missionId`, `scope` (`step`, `milestone` or `mission`) and, for the first two, `id`;
  - `card`: `slug` of a board card.

  The validator checks what Harnu can read: a `mission` source's ids exist in the mission record, a `card` source's slug is on the board, a `pr` has a positive number, a `branch` is a name git accepts. A PR's title and author are the agent's declaration and are shown as such.

- **A walk is written once and only grows.** Explain more (deepenings) and a check found mid-walk (`append`) are added to the **walk**, each tagged `addedInRun` (the live run's ordinal, or the latest run's when none is live), so a re-run shows them and a plan only grows. A past run shows the checks as they were when it ended: additions with a later `addedInRun` are hidden from it.
- **Re-run** creates run `n + 1` of the same walk: every check is to do again, including the ones the script marked pre-closed (a regression pass checks them), with nothing copied from the earlier run except a quiet "last time" hint. Earlier runs are never edited.
- **A past run** opens read-only: the rail with each check's outcome, and a click on a row shows that check with what was recorded (the failure lines, the corrections, the agent's evidence, the screenshots) and a **Re-run** button.
- **A live run** left open (the pane was closed, the app restarted) stays live and continues from where it was; End walk closes it, and a check that was still awaiting the agent is recorded as a caveat ("ended before the agent answered"). A `walk_report` for an ended run is refused `RUN_ENDED`; `walk_extend` needs no run.

### The walk script: the data contract

`walk_open` receives one JSON object. The template renders it; nothing in it is markup. Limits are enforced by the validator (S-1), and the whole script is refused with one violation per rule if any check breaks one.

```json
{
  "title": "Search box on the notes list",
  "purpose": "check",
  "source": {
    "kind": "pr",
    "number": 101,
    "title": "Add a search box to the notes list",
    "author": "a colleague"
  },
  "leftOut": [{ "text": "Rename the index file", "owner": "ours" }],
  "checks": [
    {
      "id": "c1",
      "title": "Typing narrows the list",
      "why": "The box filters notes as you type; it is the whole feature.",
      "where": {
        "text": "example-web, Notes page, on the PR 101 preview",
        "path": "Notes page, search box above the list",
        "approximate": false,
        "links": [
          {
            "label": "PR 101 preview",
            "kind": "url",
            "target": "http://localhost:5173/notes",
            "checked": { "status": "ok", "at": "2026-11-17T21:10:00Z" }
          },
          { "label": "PR 101", "kind": "pr", "target": "101" }
        ]
      },
      "do": [
        {
          "text": "Open the Notes page and click the search box.",
          "see": "The caret blinks in the box and all 12 notes are listed."
        },
        {
          "text": "Type `standup`.",
          "see": "Only the two notes whose title contains `standup` stay.",
          "block": { "text": "curl -s localhost:5173/api/notes?q=standup", "lang": "sh" }
        }
      ],
      "passes": "The list shows exactly 2 rows: `Standup 14 Nov` and `Standup 7 Nov`.",
      "fails": "More than 2 rows, an empty list, or the list only updates after Enter.",
      "images": [
        {
          "src": "docs/design/notes-search/screens/search-typed.png",
          "alt": "Search typed",
          "kind": "expected",
          "caption": "Mockup frame"
        }
      ],
      "precheck": "The preview serves the new markup (the `data-search` attribute is in the page).",
      "check": { "how": "curl the preview and count the rows in the response" },
      "teach": {
        "what": "The box filters on every keystroke in the browser, with no request.",
        "where": [
          { "label": "filter-notes.ts", "kind": "file", "target": "src/notes/filter-notes.ts" }
        ],
        "idea": {
          "text": "A debounced filter over an in-memory list.",
          "link": {
            "label": "debounce",
            "kind": "url",
            "target": "https://example.org/debounce",
            "checked": { "status": "unchecked", "at": "2026-11-17T21:10:00Z" }
          }
        },
        "why": "The list is small, so a round trip would be slower than filtering it."
      },
      "edge": [
        {
          "text": "Narrow the window to 375 px and type `standup`.",
          "see": "The two rows still fit and nothing is clipped."
        }
      ],
      "blocks": ["c3"],
      "blocksWhy": "they need the running app",
      "undo": "Clear the search box."
    }
  ]
}
```

Rules the validator enforces (each is an AC or part of one):

- **A complete how-to.** Every check has `why`, `where.text`, at least one `do` item, and each `do` item has `see`; `passes` and `fails` are present and non-empty; at most 8 `do` items, 2 images, 12 `table` rows; text caps of 50 (title), 160 (why, undo), 240 (passes, fails, teach). A check has either `check` (what the agent will read-only check) or `nothingFromHere` (why it cannot).
- **Purpose, teaching and edge checks.** `purpose` is `check` (the default) or `learn`. In a `learn` walk `fails` is optional. Any check may carry `teach` (`what`, optional `where` links, optional `idea` with a text and a link, optional `why`) and `edge` (at most 6 prepared sub-checks, each one `do` item with its `see`); **Explain more reveals them** and, in a `learn` walk, shows `teach` first and folds `edge` under it, while in a `check` walk it shows `more` and `edge` first (V-26, D-15). A check with neither has Explain more ask the session.
- **A source.** `source` is required and valid for its kind (above). `criterion` (the id of a mission criterion a check answers) is accepted only when the source is a mission and the id exists on that mission.
- **Blocking is derived, never declared.** A check is blocking when its `blocks` list is not empty (a later check depends on it), which is the skill's own definition. There is no separate flag. An optional `blocksWhy` (at most 60 characters) names the reason in the quiet line "Checks 2 to 6 depend on this one".
- **Where links and table.** `where.links` are the chips of the Where line (V-13: links appear once, there is no separate closing list; a link of `file` kind may carry a `line` and then opens at it). `table` is `[{ item, shows, source }]`, at most 12 rows.
- **Inline copy.** Every backtick span in `text`, `see`, `passes`, `fails` renders as a copy chip. `block.text` renders as a copy block. A `<placeholder>` left in a `block` is refused (`PLACEHOLDER_IN_COMMAND`): the skill says real values.
- **Links are data, never URLs the page opens.** `kind` is `pr` (a number of the folder's repo), `file` (a path that exists inside the walk's folder; a PR or branch walk is opened from a folder that has that code checked out, and a file that exists only elsewhere is written as a `pr` or `url` link to it), `url` (`http` or `https`) or `folder` (a known Harnu folder); a target that fails its kind's test refuses the script. A `url` carries `checked` (`ok`, `login` or `unchecked`, plus the time). Harnu does not fetch an external address when it accepts a script: `checked` is the agent's own declaration and the pane prints it as such ("behind a login, not opened", "not checked"). That the address answered 200 and is the right page stays the skill's rule (agent side). A click path with no link goes in `where.path`, and `approximate` (true or false) is then required, so an agent must decide whether it is asserting a menu path.
- **No emoji, no secret.** Text with an emoji is refused. A `block`, `check.how` or copy chip that looks like a secret (the same patterns the `get_session` scrubber knows) is refused.
- **Images are files.** `src` is a path inside the folder, under the image cache or a pasted-image path (the same jail `draw_canvas` uses), at most 2 MB, copied into the walk's folder when the script is accepted. `kind` is `expected` (a mockup frame) or `capture` (a verifier or live capture) and drives the caption.
- **Pre-closed rows.** A pre-closed row is a complete check (every rule above applies to it, so a re-run can serve it) that also carries `status: "verified"` with `evidence`, or `"caveat"` with `evidence` and `openPr` (right in the open PR, not yet where it ships). In the first run it is drawn in the roadmap with its glyph and is never served; in a re-run it is a normal check, and its "last time" hint is that pre-closed status and the date of the walk (a check served in an earlier run hints that run's outcome instead).
- **Order and left out.** The order of `checks` is the order walked. `leftOut[].owner` is `ours`, `optional` or `decision`, at most 10 rows.

### Where walks live (D-8)

Each walk is a directory in the main checkout, shared by every worktree of the repo and private to the machine (the `.harnu/` directory is gitignored). A folder that is not a git repository keeps its own `<folder>/.harnu/walks/`:

```
<main checkout>/.harnu/walks/<walkId>/
  walk.json            the script, what Explain more added, rev, a pointer to the live run, and a summary of the last ended run
  images/              the script's images, copied in
  runs/<runId>.json    one file per run: state per check, outbox, the close-out text
  runs/<runId>/shots/  the operator's pasted screenshots for that run
```

Both files are written only by main, atomically and versioned. The library reads `walk.json` and, for a walk with a live run, that one run file, so listing stays cheap. The summary (`lastRun`: its time, `verified` and `N`) is rewritten when a run ends; the live pointer (`live`: `runId`, `n`) is set when a run starts and cleared when it ends, so a re-run on an ended walk shows "in progress" and not a stale outcome. `walkId` is `wlk-<8 hex>` and `runId` is `run-<8 hex>`; a run also has its ordinal `n` in its walk.

### Flow and states: the view-model

The rules live in one pure module (`src/shared/walk-machine.ts`, Electron-free, imported by main and by the renderer) so the pane draws what the machine says and recounts nothing. The machine runs over a **run**.

| Check state    | Glyph (turns, roadmap) | Icon in the pane | How it gets there                                                                                                      |
| -------------- | ---------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| to do          | `-`                    | `minus`          | not reached yet                                                                                                        |
| current        | (the served check)     | none             | the first to-do check whose blockers are closed; when none is left, the operator picks a skipped one from the list     |
| awaiting check | `-`                    | quiet line       | Done on a check that has an agent check; closes only on `walk_report`                                                  |
| disagrees      | `!`                    | `triangle-alert` | the report says fail after a Done; a blocking check stays here                                                         |
| verified       | `✓`                    | `check`          | Done plus a passing report, or Done on a check with `nothingFromHere`, or a pre-closed `verified` row in the first run |
| caveat         | `!`                    | `triangle-alert` | Follow anyway, or Continue without the check (D-7), or a pre-closed `openPr` row in the first run                      |
| failed         | `✗`                    | `x`              | Failed, or Treat as failed (open until Done or Skip)                                                                   |
| skipped        | `-`                    | `minus`          | Skip; before the close the pane lists the skipped checks, each with Check now; a check it blocks waits for its retry   |

Outcomes, exactly four on every check, plus one:

- **The roadmap first (D-5).** A run opens on the roadmap: every check as a row with its glyph, evidence on the checks verified before the walk, how each open check will be checked, the folded "left out" line, and one primary action, **Start with 1**. Reordering, "something is already done" and bringing a left-out item back are not offered here; the operator asks the session.
- **Done** closes the check (see above). **Failed** requires a line or a pasted screenshot before it can be sent, delivers it, and keeps the same check on screen. **Back** returns to the previous served check, whatever state it closed in: that check becomes current again, its agent report is cleared (the log keeps it), its attempts are kept, and when it has `undo` the pane leads with it. **Skip** marks the check skipped. **Explain more** deepens this one check and never moves the cursor. **Treat as failed** (after a disagreement) needs no new line: the agent's evidence is the symptom, and it is delivered with the turn. **I didn't get this step** is a sixth, quieter door: see below.
- **The outcome area in the other states.** While the agent checks (or prepares), the pane shows one quiet line and no actions. When the agent disagrees it shows the evidence card (ran, expected, found, each copyable) with **Try again** (primary); a non-blocking check also offers **Follow anyway (unverified)**, a blocking one **Treat as failed** and **Back** (V-10).
- **The failure loop.** After Failed, the agent gives one correction (`walk_report`, `kind: "correction"`). The pane shows it above the same check in the accent family; the operator answers again with the same outcomes. No attempt limit, and a second correction before the operator answers again is refused. From the second failure a quiet **escalation door** appears (V-5, V-22): pressing it sends an `escalate` turn naming the source kind, and the agent acts. For a mission step it sends a delta to the step's builder; for a PR walk it drafts a comment for the PR, a draft only, never posted unseen because it is outward-facing; for a feature, branch or card walk it makes a bug card (D-10). The pane itself creates nothing.
- **Explain more** reveals what the script prepared (`teach` and `edge`, in the order of the walk's purpose) as a card under the current check, with the edge checks as **tickable rows that never block Done**; unticked ones are listed in the close-out (V-4). A press with nothing left to reveal, or on a check with nothing prepared, asks the session with an `explain` turn, and its answer is appended with `walk_extend` as one **deepening** (`more` of at most 400 characters, `extra` of at most 6 sub-checks). Deepenings accumulate (at most 18 sub-checks per check, separate from the script's 8 `do` items). A **sub-check is an extra `do` item** of the same check, so the check keeps its state, its attempts and the page's scroll position, and the progress count does not change. While the session answers, the button shows a quiet "Asking…" and every other outcome stays live; this is a label, not a check state.
- **I didn't get this step.** A quiet link under the step sends a `simpler` turn; the session answers with `walk_extend` and the pane shows a "Said more simply" card over the same check, in the same position, with the same actions (V-3). It never advances and never answers "as I said above"; the text is stored on the check as `simpler`, tagged `addedInRun` like every addition.
- **Numbering.** `N` is the number of checks to walk: in the first run pre-closed rows are not counted and are not served, in a re-run every check counts. `n` is the current check's fixed ordinal among them, so a check that resurfaces after a skip still reads its own number, and Back shows the ordinal it returns to. `walk_extend` with `append` adds checks at the end: `N` grows, the roadmap marks them as added, nothing is reordered or removed.
- **A late report.** The wait for the agent starts when the turn is delivered, not when Done is pressed (a parked session can take up to 40 s to wake). A `walk_report` that arrives after Continue without the check is accepted: a pass upgrades the caveat to verified, a fail makes the check disagree. A report for a check that is not awaiting and was never awaiting is refused.
- **Close-out.** When no to-do or skipped check is left, or the operator ends the walk (the pane's X asks "End the walk and see the close-out?" once at least one check is closed, V-11), the run ends and the pane shows one row per check (its glyph and how it was verified, for example "verified, Done plus the check", "verified, you confirmed, nothing to check from here", "caveat, you confirmed, my check disagreed", "skipped"), the unticked extra checks, a `⚑ Still yours` card when something is owed (skipped, failed or unverified checks, "re-check N after #PR merges", and with a mission source the open criteria with the link to Mark done in the Mission, with the words "I never tick it for you"; with nothing owed one quiet "Nothing owed" line), a **Saved in Walks** card (Open Walks, Export markdown) on every source, and a copyable summary of at most three lines. There is no footer button (V-8). **The pane is the report.** The same text goes to the session as one `closed` turn so the agent has it, and the agent answers with at most three lines: offers of cards for what is owed, nothing else. The run's summary becomes the walk's `lastRun`.
- **No settle (D-2, V-12).** Nothing in the pane settles a criterion, with any source: Done does not, no close-out control does, and no verb does. With a mission source the close-out shows each criterion's state read live from the mission record ("criterion open" or "criterion settled"; a mission that was closed or removed shows "mission not available") and links to Mark done in the Mission, where the operator ticks it. A walk with any other source writes nothing to any mission.

### The library, history, re-run and export

**The Walks library** (`WalksPane.vue`, a helper-stack pane, V-16) is a list, not a dashboard. It is reached by a library icon in the walk pane's header (V-28) and by a folder and Topbar menu item. Its header reads `Walks` and `N walks · saved on this machine` (V-27). A row is a source icon, the title, a meta line (source, last run date and the outcome "4 of 6 passed", with a `!` when anything did not pass, or "in progress, check 4 of 9" for a live run), a compact **Re-run** and a ghost **Open**. Newest run first, no search and no filter (V-23). With no walks it shows `No walks yet`, one sentence and a copyable command: a walk starts by saying it in any session, from a PR, or with Test it in the Mission. Delete is a menu item of a row, after a confirmation that says when a run is live (D-18; it is not drawn in the mockup).

**Open** shows a past run read-only (V-24): `← Walks`, the title, `N passed · N failed · N skipped`, a run selector (`Run 3 · Nov 16`) with a `Read-only` chip that lists the walk's runs, and one row per check (glyph, number, title, how it was verified). A failed or noted check shows the operator's note and its screenshot chip. The run is shown as it was when it ended: additions made to the walk later are hidden. The action bar holds **Re-run** (primary) and **Export markdown**. Open on a live run continues it instead.

**Re-run** starts run `n + 1` of the same walk (V-25): the roadmap and each check carry a quiet `last time: passed`, `failed` or `skipped` (a check that failed last time shows what was written then), every check is to do (pre-closed rows included), and nothing from the old run is pre-answered. It is refused while a run of that walk is live, and the live run opens. An optional "only what failed or was skipped last time" toggle is a follow-up, not built here.

**Export markdown** is an operator action, not a verb. It writes the walk as Markdown (title, source line, the checks in order with Where, Do with its see lines, You should see and the `Not` line, links as Markdown links, and a "Last run" table with the operator's notes) and opens it in the viewer or copies it; it never overwrites a file (a suffix is added). Where it writes follows D-13.

When a saved walk already exists for the same source, the roadmap of a new walk opens with one line, "Re-run the saved walk (4 of 6 passed)?" (V-20); it starts a re-run of the saved walk and leaves the new one unrun.

### Starting a walk from anywhere

Triggering a walk outside a mission is a first-class requirement. In any Harnu session with Harnu's MCP on, a plain sentence in the operator's language ("walk me through what we just built", "test PR #48 with me", the same in Portuguese) or `/walk` must open a walk. Three parts make that true:

1. **Core verbs.** The four walk verbs are core: each carries `alwaysLoad: true` in `src/main/mcp/tool-catalog.ts` (the T93 mechanism), so `claude` loads them on turn one instead of deferring them behind ToolSearch. They open and update a panel (`walk_open`, `walk_extend`, `walk_report`) and read and save walks (`walk_get`; a walk is saved the moment `walk_open` accepts it). `docs/harnu-features.md` documents them, with the `[harnu-walk]` turns, so every session knows them without being told.
2. **The `walk` skill.** A bundled skill `walk` carries the contract (the `step-by-step` skill's walk, panel mode). Its description triggers on those sentences and on `/walk` (`/harnu:walk` is the namespaced form), so the session that holds the context writes the script: for "what we just built" its own work, for a PR the PR read with its own `gh`, for a branch the diff, for a card the card, for a mission the mission. It asks one question only when it cannot tell which source is meant.
3. **On by default (D-21).** The skill ships enabled, an exception to bundled skills being off until switched on, because a trigger that silently degrades to a chat walk is the failure this exists to prevent. The operator can still switch it off in Settings → Skills. Even then the verbs work and the "Test it" request turn carries a self-sufficient brief.

**The end-of-feature offer (D-20).** After the session finished building something, once per finished feature and never on a trivial change, it may offer a walk in one line with the same three options the mockup drew: **Walk me through it** (a `learn` walk), **Test it end to end** (a `check` walk) and **Not now**, which snoozes the offer for that feature (V-17, V-18). The session never starts one on its own. The mockup drew this as a card above the prompt, which cannot exist: the prompt is the Claude Code CLI. D-20 chooses how the three options appear.

### Events and verbs: how the pane and the session talk

The operator never types to drive the pane, and the agent never presses its buttons. Two directions:

**Pane to session: `[harnu-walk]` user turns.** They use the existing user-turn route with a new `walk` source and its own toast title (it needs i18n keys in both locales, so it is S-2's), so a parked session is woken and a turn waits while the operator types. A run's owner is the session that called `walk_open` for it; a re-run started from the library has no caller, so its owner is the session that wrote the walk if it is live, then the folder's selected session, as page events do, and the same fallback applies when an owner was released by a hand-off. Every turn names the check and its `check.how`, because the selected session may know nothing of the walk. An undeliverable turn is **kept in the run's outbox** (not in memory) and replayed when a session can take it, including after a restart. Only an outcome the agent must act on sends a turn; Back, Skip and a Done with nothing to check do not (D-19), and the next turn carries a progress line so the agent is never behind: the session learns of a Done that needed no check from that line.

```
[harnu-walk] Search box on the notes list — check 3 of 9 · done
walk: wlk-5d2e91ab · run: run-81c0ffee (2) · check: c3 · session: <owner session id>
The operator pressed Done. Run the read-only check of this check, then answer with walk_report.
progress: ✓ 2 · ! 0 · ✗ 0 · - 7
```

Kinds: `done` (a check with an agent check), `failed` (carries the operator's line verbatim and the saved screenshot's absolute path), `explain`, `simpler`, `treat-as-failed` (carries the agent's own evidence), `escalate` (the door after the second failure, naming the source kind) and `closed` (the close-out text). A failure line is the operator's own typing and is delivered as theirs; control characters and look-alike delimiters are stripped as `sanitizeUntrusted` does. The turn's first line carries the kind and never a score (the lesson precedent).

**"Test it" to the session: `[harnu-walk-request]`** (S-7), one turn naming the source (a mission step, a milestone or the whole mission), the walks that already exist for it and their last runs, plus a self-sufficient brief of at most 1,500 characters (the sources to read, the contract in eight lines, "open it with `walk_open`"). It does not depend on the skill being switched on. The other entry points need no request: the session that holds the context is already the one the operator is talking to ("walk me through what we just built", `/step-by-step PR #123`), and may offer a walk once, in one line, when a feature is done.

**Session to pane: four core verbs** (`alwaysLoad`, see "Starting a walk from anywhere"), run free like `open_file`, recorded in the audit log, absent from the Scheduler `observe` allowlist.

| Verb          | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `walk_open`   | `{ folder, sessionId, script }` (the source is part of the script). Validates the whole script, copies its images, writes the walk and its first run, asks the folder's helper stack to open the pane in the background. ACK: `walkId`, `runId`, `checks`, `rejected` (each violation with its JSON path and rule), `opened` (false until the pane type exists, S-3). Always creates a new walk; it is refused `WALK_RUN_LIVE` (with the ids) when a run of a walk with the same source identity is still live (identity: `pr` number, `branch` plus `base`, `mission` id plus scope plus id, `card` slug, `feature` text compared after trimming). |
| `walk_extend` | `{ walkId, checkId, more?, extra?, simpler? }` (Explain more, I didn't get this step) or `{ walkId, append }` (new checks at the end). Grows the walk, never edits or removes; refused on a deleted walk; `expectRev` guards a stale write.                                                                                                                                                                                                                                                                                                                                                                                                         |
| `walk_report` | `{ walkId, runId?, checkId, kind: "check", result: "pass" or "fail", evidence }` or `{ walkId, runId?, checkId, kind: "correction", text }`. `runId` defaults to the live run. Refused when the check is not awaiting a report or has no failure to correct.                                                                                                                                                                                                                                                                                                                                                                                        |
| `walk_get`    | `{ walkId }` or `{ folder, source }`. For a walk: its progress, the live run's cursor, each check's glyph, the last failure, what awaits the agent, the outbox, `rev`, and the list of runs with their summaries. For a source: the walks of that source with their last runs, so a session can say "this PR already has a walk" before writing another. Enough for a session with no memory of the walk to carry on: the read to make after a compaction.                                                                                                                                                                                          |

No verb takes a command to run, presses Done, Back, Skip or Failed, re-runs a walk, exports or deletes one, or settles a criterion.

### Where things live

- The walk and its runs: `<main checkout>/.harnu/walks/<walkId>/` (D-8), shared by every worktree, written only by main.
- The pane type `walk` in the helper stack, persistable like a Markdown pane (it stores `walkId` and `runId`, never content), so a restart restores it from the record. The Walks library (`WalksPane.vue`) is a pane of its own (V-16). Both are registered in `lib/pane-registry.ts` and `lib/pane-components.ts` and added to the `HelperPane` type (S-3, S-4).
- The entry from the Mission dropdown (S-7): a compact **Test it** control on a step, a milestone and the whole mission, wired to the dropdown spec's stub. It is drawn only where something is owed by hand (V-20): a step with an operator-owned check, a milestone with steps waiting, the whole mission only at its end. It sends `[harnu-walk-request]` to the mission's leader; with a live run for that source it focuses that pane instead (its label then reads "Continue test").

### Recommendation for D-1: a native Vue pane, fed by the same JSON

A live-panel template can render the data, but six consequences of the facts in the table of the Problem section make it the wrong host for this walk:

1. It cannot open a link by itself: while its network switch is off (the default) a page may go only to its own folder host and open no popup, so a PR, a URL, a file in the viewer or a folder would each need an emit, a round trip through the agent, and an agent verb to open them. Turning the switch on would let the page navigate anywhere, which is worse for a page that renders agent-supplied text.
2. It cannot settle a criterion or call any Harnu function, and it cannot list, reopen, re-run or export a saved walk; its only door out is an emit that reaches the agent as data.
3. It can lose an answer: emits are capped at 1 per second and 20 per minute, and what the cap drops reaches the agent only as a count. A quick Done, Back, Skip sequence would lose events the record must keep.
4. It cannot save a pasted screenshot into the run's folder: an emit carries at most 8 KiB of payload.
5. The visual system is a page's own CSS, so the tokens would be copied into the template and drift from `design.md`; a native pane uses `themes.css`, i18n and the theme switch as every other pane does.
6. State in a 256 KiB sidecar keyed by a page path is a worse record than versioned walk and run files that main owns, with an outbox that survives a restart and a library that can list them.

What a live panel does better is that it needs no new pane type and no new IPC. If D-1 flips to a live panel, the spec is amended: S-1 shrinks to the schema validator, the verbs and the `walk` turn source disappear in favour of `browser_set_data` and `[harnu-page-event]`, the library and re-run need a native surface anyway, and S-3 becomes a template file. That is why S-1 and S-3 are gated by D-1.

```markdown
**Glyphs.** The skill's six (`✓ ✗ ! - ⚑ ?`), `--font-mono` 700, never emoji. They mark outcomes in the
roadmap, the buttons and the close-out.

**Values.** Every command, path, id, branch, URL and error text has a one-click copy (18px icon button,
`--text-4` to `--text`). After a click the icon becomes a green check with the word `Copied` for 1.4s (a small
`--surface-2` tag above an inline copy, in place on a labelled one). The copy puts the **full** value on the
clipboard; absolute paths are never shown raw, only a short name.

**States.** `roadmap` · `step` · `step-image` · `lightbox` (over the pane, `--color-scrim-strong`, Esc) · `failed`
(one line + a paste area; the screenshot is a 40×28 chip) · `failed-retry` (the reported line, **one** correction
card in the accent family, the same step again, and from the second failure a quiet door to whoever should
fix it) · `check-failed` (warning card with ran / expected / found, then `Try again` primary and
`! Follow anyway (unverified)`) · `explain-more` (the same step, then a `Why this matters` paragraph and
`Extra checks · N` as tickable rows that never block Done, appended under it) · `did-not-understand` (an accent
card `Said more simply` over the same step) · `working` (a trace line, a pulsing 8px `--accent` dot, one sentence;
no spinner wall, no actions) · `skipped-at-end` (the skipped checks listed before the close, each with
`Check now`) · `close-out` (a row per step: glyph, number, title, how it was verified; a `⚑ Still yours` card;
a code block with the summary and its Copy) · `empty` · `error` (session gone, progress saved,
`Resume the session`).

**Keyboard.** `Enter` = Done (also **Start with 1** on the roadmap and **Try again** on a retry), unless focus
is in a field or on another button. `Esc` closes the lightbox. Focus starts on the primary action.

**Motion.** Only the §7 fade-in-scale on the lightbox and the pulse on the working dot; both are removed under
`prefers-reduced-motion`.

**Copy.** `testWalk.*` keys in both locales. Short labels have no trailing period; the glyphs and the layout
are fixed, the words follow the operator's language.

**Walks library** (`WalksPane.vue`, a helper-stack pane): a list, not a dashboard. Header `Walks`, `N walks · saved
on this machine`. A row is `16px | main | actions`: a source icon, the title (12.5px), a meta line (source ·
last run date · outcome glyph and `N of M passed`, `!` and `--warning` when anything did not pass) and a compact
**Re-run** (neutral, `refresh` icon) and ghost **Open**; in the narrow pane the actions wrap under the meta. Newest
first, hairline separators, no search or filter. Empty: the pane's centred block with `No walks yet`, one sentence
and a copyable command block.

**Runs.** **Open** shows a past run **read-only**: `← Walks`, the title, `N passed · N failed · N skipped`, a run
selector (`Run 3 · Nov 16 ▾`) with a `Read-only` chip, one row per check (glyph, number, title, how it was
verified); a failed or noted check shows the operator's note (`--red-line` left rule) and the screenshot chip. The
action bar holds **Re-run** (primary) and **Export markdown**. **Re-run** starts a fresh run of the same checks: the
roadmap and each check carry a quiet `last time: passed | failed | skipped` (`--text-4`; `--warning` when it
failed, and the check shows what was written then). Nothing from the old run is pre-answered.

**Teaching lens.** On a walk-through of a feature, **Explain more** appends a `Behind this check` card under the
current check (`--accent-soft`, `--accent-line`, `--radius`): `What it does`, `Where it lives` (`file:line` link
chips that copy), `The idea behind it` (text and a link) and `Why it behaves this way`; the edge-case checks fold
under it (`Extra checks · N`). A QA or PR walk keeps `Why this matters` + tickable `Extra checks`.

**Close-out.** Besides the checklist: a `Saved in Walks` card (`Open Walks`, `Export markdown`) on every source; the
`⚑ Still yours` card (what is owed: skipped, failed or unverified checks, "re-check N after #PR merges", and for a
mission source the open criteria with the link to Mark done) is drawn only when something is owed. No control
settles a criterion.

Plain numbers with no token (documented here, as §4 allows): thumbnail 300×132, attachment chip 40×28,
copy-button padding in a code block 76px, centred empty/error measure 340px.
```

### The smoke test

**Script:** `scripts/verify/guided-test-walk.mjs`. Run from the repo root, serial, at low priority:

```
nice -n 19 node scripts/verify/guided-test-walk.mjs [--no-build] [--case W-n] [--list-proofs] [--plant-fault <name>] [--evidence <dir>] [--keep]
```

**Isolation** (`docs/dev/live-verify-second-instance.md`): a second instance of the freshly built app with its own throwaway `HOME`, `--user-data-dir=/tmp/hv-walk-<id>` (kept short), its own `--remote-debugging-port`, a stub `claude` that appends every line it receives to a file and otherwise sleeps, a throwaway repo with two worktrees and a mission record, and a local `http` server for the URL link. It never reads or writes the operator's `.harnu/`, `~/.claude`, `~/.config/Harnu` or `~/.config/harnu`, never calls Claude, and stops only the PIDs it started (never a `pkill` pattern). CPU: one instance, serial cases, `nice -n 19`, nothing spawned beyond `nproc/2`; the unit tests of the slices run with `--maxWorkers=4 --minWorkers=1`.

**Driving the app.** The verbs are exercised through the throwaway instance's own control-server transport with a client, the way the landing script drives `mission_create`, so `walk_open`, `walk_extend`, `walk_report` and `walk_get` run as the agent would call them. The pane and the library are driven over CDP. Two product hooks exist and are honoured only when `!app.isPackaged`: a dev door to open a walk without a session, and `HARNU_WALK_CHECK_WAIT_MS` to shorten the 30 s wait of D-7 (case W-14); both live in the product code of S-2 and S-3, and S-5 only sets them.

**Output:** one line per case and a tally, evidence (screenshots, the stub's received file, the exported Markdown, a `results.json`) in the evidence folder whose path is the last line. The rows in brackets are the ones the matrix says the case proves:

```
guided-test-walk smoke: instance hv-walk-3f9a (CDP 9347, nice 19)
PASS  W-1   loads a sample walk                                  [M-4, M-27, M-28]
PASS  W-2   renders check 1 only                                 [M-6, M-19, M-20, M-30, M-31, M-32, M-33, M-34, M-35, M-55]

...
22 passed, 0 failed
evidence: /tmp/hv-walk-3f9a/evidence
```

Exit 0 when every case passes, 1 otherwise, 2 on a setup failure (build, launch, CDP). **`--plant-fault <name>`** follows the landing script: it breaks the script's own expectation or its own driving, not the product, so a run proves an assertion can fail (for example `expect-two-checks`, `click-wrong-chip`, `skip-no-resurface-expected`); the run must exit 1 with that case failing.
