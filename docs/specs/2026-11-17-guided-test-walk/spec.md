# Guided walks: a fixed pane that walks the operator through a feature, a PR or a mission, one check at a time, saved and re-runnable

## Problem

Agentic work leaves the operator with things they did not watch being made, and some of what proves them is only the operator's eyes. Four situations have no home today:

1. **Learning a feature that was just built.** The operator often did not learn what was built while it was being built. They need to be shown what it does, where it lives and why it behaves that way.
2. **End-to-end QA of a feature.** "I want to test it from end to end and don't know where to start": the session builds the big list, and the operator walks it point by point.
3. **Testing someone else's PR**, for example a colleague's: a walk built from the PR (its diff, description and linked task).
4. **Mission QA at any level:** one step, one milestone, or the whole mission at its end.

What exists:

- The `step-by-step` skill walks a list in chat, one message per step. It is the operator's favourite way to work, but the walk lives in a scrolling transcript: it is lost on a compaction, its links and commands are Markdown, it cannot show an image beside the sentence, nothing records which check was verified how, and nothing keeps the walk for the next time.
- The Missions v4 delivery hand-made a 23-item `visual-checks/index.html` page to do this job. A page an agent writes for each walk looks different every time, repeats colours and sizes by hand, and cannot call anything inside Harnu.
- Learning mode (a `quiz` block in the Markdown pane, answered with a `[harnu-lesson]` turn) shows that a rich pane next to the session works. But a lesson is generated Markdown, not a product-grade fixed template.

The operator's decisions of 2026-11-17 (card T765, its notes and decision block, the brief of this spec, and the scope correction after the mockup), one atom per decision:

- R-1 Let the operator walk a guided panel in the helper stack, one check at a time; each check says exactly what to do and what they should see.
- R-2 There is no Markdown prototype: one fixed template, built once in the repo and faithful to `design.md`; the agent never writes HTML for a walk, it sends data (JSON: the checks, the images, the source) and the template renders it.
- R-3 Every entry point starts the same panel: from any session (a skill or command, for example "walk me through what we just built" or `/step-by-step PR #123`), from a Walks library, and from the Mission dropdown on a step, a milestone and the whole mission. A walk opens in the helper stack, never inside the dropdown.
- R-4 The session that holds the context writes the script, never a blank one: for a feature, the session that built it; for a PR, a session handed the PR; for a mission, the leader or a session handed the mission summary. Its sources are the diff, the description and linked task, the criteria, the summary and Log, the spec, the verifier's evidence and its own memory of what was hard.
- R-5 "Explain more" deepens one check from that same context and is core, not an extra: it explains why the check matters, appends edge-case checks under the current check, and, for a walk-through, teaches (what this part does, the file or concept behind it, with a link). The walk does not restart.
- R-6 The panel keeps the contract of the `step-by-step` skill, and the spec proves it with a conformance matrix (one row per rule, the three columns asked for); the skill gains a "panel" mode instead of being forked.
- R-7 Every link is clickable and opens the real thing (a PR, a file in the viewer, a URL in a browser pane, a folder); every value is copyable with one click.
- R-8 Failure capture takes one line plus a pasted screenshot; each check shows "Where" and "Observe" lines; an approximate dashboard path is marked as approximate.
- R-9 Enter means Done, and the skill's text controls exist as shortcuts; progress reads "Check 3 of 9" and nothing else; every element earns its place (minimalism first).
- R-10 Decide whether the final pane is a live-panel template or a native Vue pane fed by the same JSON, with a recommendation; the visual system is `design.md`, and the visual section follows the approved mockup.
- R-11 Decide whether Done settles an operator criterion directly or stays a separate Mark done, and how an image is attached per check (mockup frame or live capture).
- R-12 A smoke test runs against the real app in an isolated second instance, and unit tests cover the view-model rules it does not.
- R-13 A walk survives a reload, a park and a compaction; agent-facing and user-facing documentation and the changelog are part of each slice.
- R-14 A walk is a first-class object of its own, not a mission feature. It has a title, a source, a list of checks and a run history. The source is one of: a free-text or feature description, a PR (number or URL), a branch or diff, a mission (whole, milestone or step), or a card. Mission persistence (operator criteria) applies only when the source is a mission; a PR or feature walk writes nothing to any mission.
- R-15 Walks are kept, not thrown away: saved per repo (the owner recommends `.harnu/walks/<id>/`, private to the machine, one JSON file for the checks and one file per run), so the operator can see the history (when it was walked, the outcome per check, notes, screenshots), reopen a past walk and re-run it later as a fresh run of the same checks.
- R-16 A Walks library lists past walks, a short list and not a dashboard: title, source, last run, outcome such as "8 of 9 passed", each with Re-run and Open, plus an empty state. A past run opens read-only with its notes and screenshots and a Re-run button; a run in progress that is a re-run shows a quiet "last time" hint per check.
- R-17 An Export action produces a Markdown copy of a walk to share or commit.
- R-18 The same pane serves a walk-through of a feature just built, end-to-end QA, testing someone else's PR, and mission QA at the level of a step, a milestone or the whole mission.

Where to find things: the spec gate allows only six `##` sections, so the design sits under Goals (the shape, the walk and run model, the data contract, the flow, the library and re-run, the events and verbs, where things live, the recommendation for D-1, and the visual section, which follows the approved mockup), the smoke test and the conformance matrix sit under Acceptance criteria, and each decision is a row of Open decisions.

## Goals

- G-1 From a session, from the library or from the Mission dropdown, the operator starts a walk on a feature, a PR, a branch, a card or a mission, and a pane opens beside the session with check 1 of N. They answer each check with Done, Failed, Back, Skip or Explain more, and finish on a close-out that names how each check was verified.
- G-2 The walk is the `step-by-step` contract, kept by construction where a program can keep it and proved by the matrix and the smoke test where it cannot.
- G-3 An agent never writes a pixel of the pane. It sends JSON that a validator accepts or refuses whole.
- G-4 Nothing the operator owes is lost to a reload, a parked session or a compaction.
- G-5 A walk outlives its first run: it is kept per repo, listed in a library, readable as history, re-runnable as a fresh run and exportable as Markdown.

**Non-goals:**

- NG-1 No Markdown prototype and no per-walk HTML, and no script generated from a diff or from criteria alone: a walk is written by a session that holds the context (R-2, R-4).
- NG-2 The Mission dropdown itself (its anatomy, its states) is the work of its own redesign and is not redone here; this spec only adds one control to a step, a milestone and the mission in it (R-3).
- NG-3 `harnu:one-by-one` is not changed (card T765, out of scope; R-6 concerns `step-by-step` only).
- NG-4 No verb lets an agent press a button of the pane, settle a criterion, perform a check, re-run, export or delete a walk; the operator's clicks are theirs (R-6, R-15).
- NG-5 Harnu does not capture screenshots of the running app for a walk in this version (an image is a file the agent already has), and the pane creates no board card or bug card: a failure becomes a card only when the agent offers it and the operator accepts (R-8, R-11, D-3, D-10).
- NG-6 A walk is not a mission tracker: it adds no step, milestone or criterion to any mission, and with a mission source it writes only through the operator's own Settle click (R-14).
- NG-7 The chat behaviour of the two skill copies is not reconciled here: the bundled copy is not rewritten to the personal one's contract, which is a separate card (R-6, D-9).
- NG-8 The library is a list, not a dashboard (no charts, trends, scores across walks, filters beyond one outcome line per walk), there is no sharing or sync beyond the Markdown Export, no "Walk this PR" control on PR cards and no "New walk" form: a PR or feature walk starts from a session (R-3, R-14, R-16, R-17).
- NG-9 No walk templates and no scheduled or automatic re-runs: a re-run is the operator's click (R-15).

**Anti-goals:** outcomes that would make this a failure even if every AC passed.

- The operator presses Enter out of habit and a criterion is settled that nobody checked.
- The pane becomes a second place to read mission state, and the two disagree.
- The agent chats a paragraph for every button the operator presses, so the transcript the walk was meant to quiet gets louder.
- A walk reads well but the operator, three checks in, cannot tell what they should see.
- The library grows into a pile of stale walks that nobody dares re-run, because a re-run shows last time's answers as this time's.

### The shape: what the operator sees

One pane in the helper stack (`type: 'walk'`, `WalkPane.vue`), with the standard helper-pane header (the walk title, expand, maximize, close). Where each element sits and how large it is follows the approved mockup (see "Proposed `design.md` section"). The body is one column:

1. **Source and progress.** A one-line source header (for a PR, `PR #123 · title · author`; for a mission, the step, milestone or mission it covers; for a feature, its short description; for a branch, `branch → base`), then `Check 3 of 9` and nothing else, with a `list` button (opens the roadmap, shortcut `L`) and a `…` menu with **End walk**. No bar. `n` is the check's fixed place among the checks to walk, `N` their number (rules in "Flow and states"). On a re-run, a quiet "last time" hint per check (its glyph and date).
2. **The check.** Its title; one line saying what this is and why it matters, and under it **More** when Explain more has added some; **Where** (a line, with an "approximate" mark when the path is not confirmed); a numbered **Do** list where every item says what the operator will see when it worked, and any command is a ready-to-paste block with real values filled in; **You should see**, quoting the literal expected value (it is the skill's Observe line), with the image when one exists; **Does not work if**, quoting the literal symptoms; a per-item table when one check covers several things; **Checked from here** (what the agent already proved) or "Nothing from here" with the reason; **Links**. In a walk-through (`purpose: "learn"`), a check also carries **What this is** (`teach`): what this part does, the file or concept behind it, with a link.
3. **The outcomes**, always visible with the check: **Done** (primary, Enter), **Failed**, **Back**, **Skip**, **Explain more**. These five are on every check at the moment it asks for the operator's answer. While the check waits for the agent, or after the agent disagreed, the outcome area shows what that state needs instead (below).

Press Failed and one line opens in the outcome area: a text field ("What did you see?"), a paste target for a screenshot, Send. Press Done on a check the agent can check from here and the outcome area becomes "Checking from here…" until the agent answers. The close-out replaces the check when the run ends.

### The walk and the run: the model

A **walk** is what is kept: its title, its `purpose`, its **source**, its checks and what Explain more has added to them. A **run** is one pass through a walk: when it started and ended, who owned it, and per check the outcome, the attempts, the failure line and screenshot, the correction, the agent's report and how it closed. A walk has many runs; **one run may be live at a time** per walk.

- **Sources.** `source.kind` is one of:
  - `feature`: free text (at most 300 characters) saying what was built;
  - `pr`: `number`, `title`, `author` and optional `url` (a PR's own header);
  - `branch`: `branch` and `base` (a diff);
  - `mission`: `missionId`, `scope` (`step`, `milestone` or `mission`) and, for the first two, `id`;
  - `card`: `slug` of a board card.

  The validator checks what Harnu can read: a `mission` source's ids exist in the mission record, a `card` source's slug is on the board, a `pr` has a positive number, a `branch` is a name git accepts. A PR's title and author are the agent's declaration and are shown as such.

- **A walk is written once and only grows.** Explain more (`more`, `extra`) and a check found mid-walk (`append`) are added to the **walk**, with the run that added them, so a re-run shows them and a plan only grows.
- **Re-run** creates run `n + 1` of the same walk: every check is to do again, including the ones the script marked pre-closed (a regression pass checks them), with nothing copied from the earlier run except a quiet "last time" hint. Earlier runs are never edited.
- **A past run** opens read-only: the rail with each check's outcome, and a click on a row shows that check with what was recorded (the failure lines, the corrections, the agent's evidence, the screenshots) and a **Re-run** button.
- **A live run** left open (the pane was closed, the app restarted) stays live and continues from where it was; End walk closes it.

### The walk script: the data contract

`walk_open` receives one JSON object. The template renders it; nothing in it is markup. Limits are enforced by the validator (S-1), and the whole script is refused with one violation per rule if any check breaks one.

```json
{
  "title": "Search box on the notes list",
  "purpose": "check",
  "source": {
    "kind": "pr",
    "number": 101,
    "title": "Add a search box to the notes list",
    "author": "a colleague"
  },
  "leftOut": [{ "text": "Rename the index file", "owner": "ours" }],
  "checks": [
    {
      "id": "c1",
      "title": "Typing narrows the list",
      "why": "The box filters notes as you type; it is the whole feature.",
      "where": {
        "text": "example-web, Notes page, on the PR 101 preview",
        "path": "Notes page, search box above the list",
        "approximate": false,
        "link": {
          "label": "PR 101 preview",
          "kind": "url",
          "target": "http://localhost:5173/notes",
          "checked": { "status": "ok", "at": "2026-11-17T21:10:00Z" }
        }
      },
      "do": [
        {
          "text": "Open the Notes page and click the search box.",
          "see": "The caret blinks in the box and all 12 notes are listed.",
          "links": [0]
        },
        {
          "text": "Type `standup`.",
          "see": "Only the two notes whose title contains `standup` stay.",
          "block": { "text": "curl -s localhost:5173/api/notes?q=standup", "lang": "sh" }
        }
      ],
      "passes": "The list shows exactly 2 rows: `Standup 14 Nov` and `Standup 7 Nov`.",
      "fails": "More than 2 rows, an empty list, or the list only updates after Enter.",
      "images": [
        {
          "src": "docs/design/notes-search/screens/search-typed.png",
          "alt": "Search typed",
          "kind": "expected",
          "caption": "Mockup frame"
        }
      ],
      "precheck": "The preview serves the new markup (the `data-search` attribute is in the page).",
      "check": { "how": "curl the preview and count the rows in the response" },
      "blocks": ["c3"],
      "undo": "Clear the search box.",
      "links": [
        {
          "label": "PR 101 preview",
          "kind": "url",
          "target": "http://localhost:5173/notes",
          "checked": { "status": "ok", "at": "2026-11-17T21:10:00Z" }
        },
        { "label": "PR 101", "kind": "pr", "target": "101" }
      ]
    }
  ]
}
```

Rules the validator enforces (each is an AC or part of one):

- **A complete how-to.** Every check has `why`, `where.text`, at least one `do` item, and each `do` item has `see`; `passes` and `fails` are present and non-empty; at most 8 `do` items, 2 images, 12 `table` rows; text caps of 50 (title), 160 (why, undo), 240 (passes, fails, teach). A check has either `check` (what the agent will read-only check) or `nothingFromHere` (why it cannot).
- **Purpose.** `purpose` is `check` (the default) or `learn`. In a `learn` walk `fails` is optional and each check may carry `teach` (`what`, an optional `where` link and an optional `concept`), so a walk-through that teaches is not forced to invent a symptom (D-15).
- **A source.** `source` is required and valid for its kind (above). `criterion` (the id of a mission criterion a check answers) is accepted only when the source is a mission and the id exists on that mission.
- **Blocking is derived, never declared.** A check is blocking when its `blocks` list is not empty (a later check depends on it), which is the skill's own definition. There is no separate flag.
- **Inline copy and link.** Every backtick span in `text`, `see`, `passes`, `fails` renders as a copy chip. `block.text` renders as a copy block. `do[].links` are indexes into the check's `links`, drawn as link chips at the point of use; the closing Links list repeats all of them. A `<placeholder>` left in a `block` is refused (`PLACEHOLDER_IN_COMMAND`): the skill says real values.
- **Links are data, never URLs the page opens.** `kind` is `pr` (a number of the folder's repo), `file` (a path that exists inside the folder), `url` (`http` or `https`) or `folder` (a known Harnu folder); a target that fails its kind's test refuses the script. A `url` carries `checked` (`ok`, `login` or `unchecked`, plus the time). Harnu does not fetch an external address when it accepts a script: `checked` is the agent's own declaration and the pane prints it as such ("behind a login, not opened", "not checked"). That the address answered 200 and is the right page stays the skill's rule (agent side). A click path with no link goes in `where.path`, and `approximate` (true or false) is then required, so an agent must decide whether it is asserting a menu path.
- **No emoji, no secret.** Text with an emoji is refused. A `block`, `check.how` or copy chip that looks like a secret (the same patterns the `get_session` scrubber knows) is refused.
- **Images are files.** `src` is a path inside the folder, under the image cache or a pasted-image path (the same jail `draw_canvas` uses), at most 2 MB, copied into the walk's folder when the script is accepted. `kind` is `expected` (a mockup frame) or `capture` (a verifier or live capture) and drives the caption.
- **Pre-closed rows.** A check may carry `status: "verified"` with `evidence`, or `"caveat"` with `evidence` and `openPr` (right in the open PR, not yet where it ships). In the first run it is drawn in the roadmap with its glyph and is never served; in a re-run it is a normal check (above).
- **Order and left out.** The order of `checks` is the order walked. `leftOut[].owner` is `ours`, `optional` or `decision`, at most 10 rows.

### Where walks live (D-8)

Each walk is a directory in the main checkout, shared by every worktree of the repo and private to the machine (the `.harnu/` directory is gitignored):

```
<main checkout>/.harnu/walks/<walkId>/
  walk.json            the script, what Explain more added, rev, and a summary of the last run
  images/              the script's images, copied in
  runs/<runId>.json    one file per run: state per check, outbox, the close-out text
  runs/<runId>/shots/  the operator's pasted screenshots for that run
```

Both files are written only by main, atomically and versioned. The library reads `walk.json` only, so listing is cheap; the summary (`lastRun`: its time, `verified` and `N`) is rewritten when a run ends. `walkId` is `wlk-<8 hex>` and `runId` is `run-<8 hex>`; a run also has its ordinal `n` in its walk.

### Flow and states: the view-model

The rules live in one pure module (`src/shared/walk-machine.ts`, Electron-free, imported by main and by the renderer) so the pane draws what the machine says and recounts nothing. The machine runs over a **run**.

| Check state    | Glyph (turns, roadmap) | Icon in the pane | How it gets there                                                                                 |
| -------------- | ---------------------- | ---------------- | ------------------------------------------------------------------------------------------------- |
| to do          | `-`                    | `minus`          | not reached yet                                                                                   |
| current        | (the served check)     | none             | the first to-do check whose blockers are closed; else the first skipped one                       |
| awaiting check | `-`                    | spinner          | Done on a check that has an agent check; closes only on `walk_report`                             |
| disagrees      | `!`                    | `triangle-alert` | the report says fail after a Done; a blocking check stays here                                    |
| verified       | `✓`                    | `check`          | Done plus a passing report, or Done on a check with `nothingFromHere`                             |
| caveat         | `!`                    | `triangle-alert` | Follow anyway, or Continue without the check (D-7), or a pre-closed `openPr` row in the first run |
| failed         | `✗`                    | `x`              | Failed, or Treat as failed (open until Done or Skip)                                              |
| skipped        | `-`                    | `minus`          | Skip; resurfaces after the last to-do check; a check it blocks waits for its retry                |

Outcomes, exactly four on every check, plus one:

- **Done** closes the check (see above). **Failed** requires a line or an image before it can be sent, delivers it, and keeps the same check on screen. **Back** returns to the previous served check, whatever state it closed in: that check becomes current again, its agent report is cleared (the log keeps it), its attempts are kept, and when it has `undo` the pane leads with it. **Skip** marks the check skipped and serves the next. **Explain more** asks the session to deepen this one check and never moves the cursor. **Treat as failed** (after a disagreement) needs no new line: the agent's evidence is the symptom, and it is delivered with the turn.
- **The outcome area in the other states.** While a check awaits the agent the outcome area is a status line ("Checking from here…"). When the agent disagreed it offers the skill's own options: for a blocking check Re-check, Treat as failed and Back; for a non-blocking one also Follow anyway.
- **The failure loop.** After Failed, the agent gives one correction (`walk_report`, `kind: "correction"`). The pane shows it above the same check; the operator answers again with the same outcomes. No attempt limit. A second correction before the operator answers again is refused.
- **Explain more** appends `more` (why it matters, where it was fragile, and in a walk-through what this part does, with a link; at most 400 characters) and `extra` (at most 6 sub-checks, each one `do` item with its `see`) under the current check with `walk_extend`. A **sub-check is an extra `do` item** of the same check, so the check keeps its state, its attempts and the page's scroll position, and the progress count does not change. The operator answers the whole check; one that fails is Failed with a line that says which.
- **Numbering.** `N` is the number of checks to walk: in the first run pre-closed rows are not counted and are not served, in a re-run every check counts. `n` is the current check's fixed ordinal among them, so a check that resurfaces after a skip still reads its own number, and Back shows the ordinal it returns to. `walk_extend` with `append` adds checks at the end: `N` grows, the roadmap marks them as added, nothing is reordered or removed.
- **A late report.** The wait for the agent starts when the turn is delivered, not when Done is pressed (a parked session can take up to 40 s to wake). A `walk_report` that arrives after Continue without the check is accepted: a pass upgrades the caveat to verified, a fail makes the check disagree. A report for a check that is not awaiting and was never awaiting is refused.
- **Close-out.** When no to-do or skipped check is left, or the operator picks End walk, the run ends and the pane shows the rail (one row per check: its glyph and how it was verified, for example "verified, Done plus the check", "verified, you confirmed, nothing to check from here", "caveat, you confirmed, my check disagreed", "skipped"), a `⚑ you` block that always prints (what is still owed: skipped, failed, followed unverified, "re-check N after #PR merges", or "nothing, you're clear"), the links of what is owed, and a summary of at most three lines. With a mission source a verified check also shows "criterion open" or "criterion settled", read live from the mission record. **The pane is the report.** The same text goes to the session as one `closed` turn so the agent has it, and the agent answers it with at most three lines: offers of cards for what is owed, nothing else. The run's summary becomes the walk's `lastRun`.
- **Settle (D-2), mission source only.** The close-out offers one button, "Settle N criteria", counting the checks that closed verified whose criterion is `operator` or `session` and not yet settled. A `person` criterion needs that person, so it is listed as owed ("approval by <person>"); a fact criterion is never ticked; a caveat or a skipped check never counts. The click writes each through the operator door with the evidence "Walk, check cN, confirmed by the operator" and changes nothing else in the mission. A walk with any other source has no such button and writes nothing to any mission.

### The library, history, re-run and export

The **Walks library** is one list of the repo's walks, newest run first, reached from the folder menu, the command palette and the walk pane's header (where it sits, and whether it is a pane or a popover, follows the approved mockup; D-12). A row is:

- the walk's title and a source chip (`PR #123`, `mission · milestone`, `feature`, `branch`, `card`);
- the last run: its date and an outcome, "8 of 9 passed" (`✓` checks over `N`; a caveat, a skip or a failure is not counted as passed), or "in progress, check 4 of 9" for a live run;
- **Open** (a live run continues; an ended one opens read-only, newest run) and **Re-run**;
- a `…` menu with **Export** and **Delete** (Delete asks first; it removes the walk and its runs).

An **empty state** says how a walk starts ("Ask a session to walk you through something, or press Test it on a mission step") and nothing more. There is no "New walk" form (NG-8), no chart and no count across walks (NG-8).

A **past run** opens in the walk pane, read-only: the rail with every check's outcome and how it was verified, then a click on a row shows that check as recorded (the operator's failure lines, the agent's corrections and evidence, the pasted screenshots as thumbnails that open the lightbox), and **Re-run** at the foot. **Re-run** starts run `n + 1`; if a run is already live for that walk it is refused and the live run is opened instead.

**Export** writes the walk as Markdown and opens it in the viewer: a title, the source line, the checks in order (Where, Do with see lines, You should see, Does not work if, links as Markdown links) and a "Last run" table (check, outcome, how verified, the operator's notes). It never overwrites a file (a suffix is added). Where it writes and whether it copies the images follows D-13. Export is an operator action: no verb exposes it.

### Events and verbs: how the pane and the session talk

The operator never types to drive the pane, and the agent never presses its buttons. Two directions:

**Pane to session: `[harnu-walk]` user turns.** They use the existing user-turn route with a new `walk` source and its own toast title (it needs i18n keys in both locales, so it is S-2's), so a parked session is woken and a turn waits while the operator types. Delivery goes to the run's owner session; when the owner was released by a hand-off, or the run is a re-run started from the library, it goes to the walk's source session if it is live, then to the folder's selected session, as page events do. An undeliverable turn is **kept in the run's outbox** (not in memory) and replayed when a session can take it, including after a restart. Only an outcome the agent must act on sends a turn; Back, Skip and a Done with nothing to check do not, and the next turn carries a progress line so the agent is never behind.

```
[harnu-walk] Search box on the notes list — check 3 of 9 · done
walk: wlk-5d2e91ab · run: run-81c0ffee (2) · check: c3 · session: <owner session id>
The operator pressed Done. Run the read-only check of this check, then answer with walk_report.
progress: ✓ 2 · ! 0 · ✗ 0 · - 7
```

Kinds: `done` (a check with an agent check), `failed` (carries the operator's line verbatim and the saved screenshot's absolute path), `explain`, `treat-as-failed` (carries the agent's own evidence), `closed` (the close-out text). A failure line is the operator's own typing and is delivered as theirs; control characters and look-alike delimiters are stripped as `sanitizeUntrusted` does. The turn's first line carries the kind and never a score (the lesson precedent).

**"Test it" to the session: `[harnu-walk-request]`** (S-7), one turn naming the source (a mission step, a milestone or the whole mission), the walks that already exist for it and their last runs, plus a self-sufficient brief of at most 1,500 characters (the sources to read, the contract in eight lines, "open it with `walk_open`"). It does not depend on the skill being switched on. The other entry points need no request: the session that holds the context is already the one the operator is talking to ("walk me through what we just built", `/step-by-step PR #123`), and may offer a walk once, in one line, when a feature is done.

**Session to pane: four verbs**, run free like `open_file`, recorded in the audit log, absent from the Scheduler `observe` allowlist.

| Verb          | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `walk_open`   | `{ folder, sessionId, script }` (the source is part of the script). Validates the whole script, copies its images, writes the walk and its first run, asks the folder's helper stack to open the pane in the background. ACK: `walkId`, `runId`, `checks`, `rejected` (each violation with its JSON path and rule), `opened` (false until the pane type exists, S-3). Always creates a new walk; it is refused `WALK_RUN_LIVE` (with the ids) when a run of a walk with the same source is still live. |
| `walk_extend` | `{ walkId, checkId, more?, extra? }` (Explain more) or `{ walkId, append }` (new checks at the end). Grows the walk, never edits or removes; refused on a deleted walk; `expectRev` guards a stale write.                                                                                                                                                                                                                                                                                              |
| `walk_report` | `{ walkId, runId?, checkId, kind: "check", result: "pass" or "fail", evidence }` or `{ walkId, runId?, checkId, kind: "correction", text }`. `runId` defaults to the live run. Refused when the check is not awaiting a report or has no failure to correct.                                                                                                                                                                                                                                           |
| `walk_get`    | `{ walkId }` or `{ folder, source }`. For a walk: its progress, the live run's cursor, each check's glyph, the last failure, what awaits the agent, the outbox, `rev`, and the list of runs with their summaries. For a source: the walks of that source with their last runs, so a session can say "this PR already has a walk" before writing another. Enough for a session with no memory of the walk to carry on: the read to make after a compaction.                                             |

No verb takes a command to run, presses Done, Back, Skip or Failed, re-runs a walk, exports or deletes one, or settles a criterion.

### Where things live

- The walk and its runs: `<main checkout>/.harnu/walks/<walkId>/` (D-8), shared by every worktree, written only by main.
- The pane type `walk` in the helper stack, persistable like a Markdown pane (it stores `walkId` and `runId`, never content), so a restart restores it from the record. The Walks library is reached as D-12 decides. Both are registered in `lib/pane-registry.ts` and `lib/pane-components.ts` and added to the `HelperPane` type (S-3, S-4).
- The entry from the Mission dropdown: a compact **Test it** control on a step, on a milestone and on the mission, drawn only where there is something to hand-check (an `operator` or `person` criterion, or a `session` criterion the verifier left open). It sends `[harnu-walk-request]` to the mission's leader; with a live run for that source it focuses that pane instead (its label then reads "Continue test").

### Recommendation for D-1: a native Vue pane, fed by the same JSON

A live-panel template can render the data, but six consequences of the facts in the table of the Problem section make it the wrong host for this walk:

1. It cannot open a link by itself: while its network switch is off (the default) a page may go only to its own folder host and open no popup, so a PR, a URL, a file in the viewer or a folder would each need an emit, a round trip through the agent, and an agent verb to open them. Turning the switch on would let the page navigate anywhere, which is worse for a page that renders agent-supplied text.
2. It cannot settle a criterion or call any Harnu function, and it cannot list, reopen, re-run or export a saved walk; its only door out is an emit that reaches the agent as data.
3. It can lose an answer: emits are capped at 1 per second and 20 per minute, and what the cap drops reaches the agent only as a count. A quick Done, Back, Skip sequence would lose events the record must keep.
4. It cannot save a pasted screenshot into the run's folder: an emit carries at most 8 KiB of payload.
5. The visual system is a page's own CSS, so the tokens would be copied into the template and drift from `design.md`; a native pane uses `themes.css`, i18n and the theme switch as every other pane does.
6. State in a 256 KiB sidecar keyed by a page path is a worse record than versioned walk and run files that main owns, with an outbox that survives a restart and a library that can list them.

What a live panel does better is that it needs no new pane type and no new IPC. If D-1 flips to a live panel, the spec is amended: S-1 shrinks to the schema validator, the verbs and the `walk` turn source disappear in favour of `browser_set_data` and `[harnu-page-event]`, the library and re-run need a native surface anyway, and S-3 becomes a template file. That is why S-1 and S-3 are gated by D-1.

### Proposed `design.md` section

**Follows the approved mockup.** The operator wants to see the panel before anything is decided, so a mockup of the pane and of the library is drawn first (a check, the failure form, awaiting the agent's check, the check disagrees, a correction, the roadmap and the close-out; a PR source header; a re-run with its "last time" hint; a walk-through check with its teaching lens; the Walks library with rows and its empty state; a past run read-only; wide and narrow, light and dark). The layout, the sizes and the exact copy of the pane and the library, and with them the `design.md` §6 section, are taken from that mockup once the operator approves it. S-3 writes the pane's section first and S-4 the library's, from the approved mockup, and this spec does not draw them. Until then nothing in this spec fixes where an element sits or how large it is.

What the mockup must obey, because the rest of this spec and the review depend on it:

- **Content and behaviour** are the ones in "The shape", "The library, history, re-run and export", "Flow and states" and "Events and verbs": one check on screen, the five outcomes, `Check n of N` with no bar, no dialog for an outcome, a numbered Do list with a see line per item, a copy chip for every backtick span, a link chip at the point of use, the image with its caption, the three failure states, the roadmap and the close-out, a library row with exactly the parts listed, and a read-only past run.
- **Nothing new in the system.** No colour, radius, easing or row height is added, and every size is on the type scale of §3. It reuses `Button` (Done is the only primary at any moment), the code-block copy control (always visible in this pane, a documented variant), `ImageLightbox`, the warning-callout pattern (`triangle-alert`), `Dialog` for Delete's confirmation and the row anatomy of the Links popover. The only new pieces it may define are the inline copy chip and the strip of pasted-screenshot thumbnails.
- **Icons.** The icon table of §5 gains the icons the mockup uses that are not yet listed.
- **Keyboard and focus.** A pointer click on a chip does not take keyboard focus from the pane, the chord of a shortcut is in the button's `title` and never a `<kbd>` inside an accent button, and a second Done within 400 ms of a new check is ignored.
- **The agent supplies data only.** No markup, class, colour or icon name comes from a script.

### The smoke test

**Script:** `scripts/verify/guided-test-walk.mjs`. Run from the repo root, serial, at low priority:

```
nice -n 19 node scripts/verify/guided-test-walk.mjs [--no-build] [--case W-n] [--list-proofs] [--plant-fault <name>] [--evidence <dir>] [--keep]
```

**Isolation** (`docs/dev/live-verify-second-instance.md`): a second instance of the freshly built app with its own throwaway `HOME`, `--user-data-dir=/tmp/hv-walk-<id>` (kept short), its own `--remote-debugging-port`, a stub `claude` that appends every line it receives to a file and otherwise sleeps, a throwaway repo with two worktrees and a mission record, and a local `http` server for the URL link. It never reads or writes the operator's `.harnu/`, `~/.claude`, `~/.config/Harnu` or `~/.config/harnu`, never calls Claude, and stops only the PIDs it started (never a `pkill` pattern). CPU: one instance, serial cases, `nice -n 19`, nothing spawned beyond `nproc/2`; the unit tests of the slices run with `--maxWorkers=4 --minWorkers=1`.

**Driving the app.** The verbs are exercised through the throwaway instance's own control-server transport with a client, the way the landing script drives `mission_create`, so `walk_open`, `walk_extend`, `walk_report` and `walk_get` run as the agent would call them. The pane and the library are driven over CDP. Two product hooks exist and are honoured only when `!app.isPackaged`: a dev door to open a walk without a session, and `HARNU_WALK_CHECK_WAIT_MS` to shorten the 30 s wait of D-7 (case W-14).

**Output:** one line per case and a tally, evidence (screenshots, the stub's received file, the exported Markdown, a `results.json`) in the evidence folder whose path is the last line. The rows in brackets are the ones the matrix says the case proves:

```
guided-test-walk smoke: instance hv-walk-3f9a (CDP 9347, nice 19)
PASS  W-1   loads a sample walk                                  [M-4, M-27, M-28]
PASS  W-2   renders check 1 only                                 [M-6, M-19, M-20, M-30, M-31, M-32, M-33, M-34, M-35, M-55]
FAIL  W-6   explain more keeps state                             [M-46]  — progress read "Check 4 of 9"
...
20 passed, 0 failed
evidence: /tmp/hv-walk-3f9a/evidence
```

Exit 0 when every case passes, 1 otherwise, 2 on a setup failure (build, launch, CDP). **`--plant-fault <name>`** follows the landing script: it breaks the script's own expectation or its own driving, not the product, so a run proves an assertion can fail (for example `expect-two-checks`, `click-wrong-chip`, `skip-no-resurface-expected`); the run must exit 1 with that case failing.

**Fixtures:** `tests/fixtures/guided-test-walk/` holds the sample walk (`sample-walk.json`), a neutral example app (a search box on a notes list in `example-web`) with a `pr` source, 9 checks to walk and 2 pre-closed rows: check 3 has an agent check and an image, check 4 a table, check 5 blocks check 6, one pre-closed row is verified with evidence, one carries `openPr`, and the links cover every kind. Beside it are a `learn` walk with a `feature` source (one `teach` per check), a `mission` walk (milestone scope) over a throwaway mission with an `operator` and a `session` criterion, and a two-run history.
