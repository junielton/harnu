# Guided test walk: a fixed pane that walks the operator through a hand check, one step at a time

## Problem

When a step of a mission is delivered, some of what proves it is only the operator's eyes: does the page look right at 375 px, does the menu say the right words, does the empty state show. Today that check has no home.

- The `step-by-step` skill walks a list in chat, one message per step. It is the operator's favourite way to work, but the walk lives in a scrolling transcript: it is lost on a compaction, its links and commands are Markdown, it cannot show an image beside the sentence, and nothing records which check was verified how.
- The Missions v4 delivery hand-made a 23-item `visual-checks/index.html` page to do this job. A page an agent writes for each walk looks different every time, repeats colours and sizes by hand, and cannot call anything inside Harnu.
- Learning mode (a `quiz` block in the Markdown pane, answered with a `[harnu-lesson]` turn) shows that a rich pane next to the session works. But a lesson is generated Markdown, not a product-grade fixed template.

The operator's decisions of 2026-11-17 (card T765, its notes and its decision block, plus the brief of this spec), one atom per decision:

- R-1 Let the operator hand-check a finished step by walking a guided panel in the helper stack, one step at a time; each step says exactly what to do and what they should see.
- R-2 There is no Markdown prototype: one fixed template, built once in the repo and faithful to `design.md`; the agent never writes HTML for a walk, it sends data (JSON: the steps, the images, the state) and the template renders it.
- R-3 The entry is a "Test it" control on a step in the new Mission dropdown; the walk opens in the helper stack, never inside the dropdown.
- R-4 The session that holds the context writes the script (the mission's leader, or a session handed the mission summary, never a blank session), from the criteria, the mission summary and Log, the spec and amendments, the diff, the verifier's evidence and its own memory of what was hard.
- R-5 "Explain more" deepens one step from that same context: why it matters, plus extra edge-case checks appended under the current step; the walk does not restart.
- R-6 The panel keeps the contract of the `step-by-step` skill, and the spec proves it with a conformance matrix (one row per rule, the three columns asked for); the skill gains a "panel" mode instead of being forked.
- R-7 Every link is clickable and opens the real thing (a PR, a file in the viewer, a URL in a browser pane, a folder); every value is copyable with one click.
- R-8 Failure capture takes one line plus a pasted screenshot; each step shows "Where" and "Observe" lines; an approximate dashboard path is marked as approximate.
- R-9 Enter means Done, and the skill's text controls exist as shortcuts; progress reads "Check 3 of 9" and nothing else; every element earns its place (minimalism first).
- R-10 Decide whether the final pane is a live-panel template or a native Vue pane fed by the same JSON, with a recommendation; the visual system is `design.md`, with a new section written as a proposed diff.
- R-11 Decide whether "It works" settles the operator criterion directly or stays a separate Mark done, and how an image is attached per check (mockup frame or live capture).
- R-12 A smoke test runs against the real app in an isolated second instance, and unit tests cover the view-model rules it does not.
- R-13 The walk survives a reload, a park and a compaction; agent-facing and user-facing documentation and the changelog are part of each slice.

Where to find things: the spec gate allows only six `##` sections, so the design sits under Goals (the shape, the data contract, the flow, the events and verbs, where things live, the recommendation for D-1, the proposed `design.md` section), the smoke test and the conformance matrix sit under Acceptance criteria, and each decision is a row of Open decisions.

## Goals

- G-1 The operator presses **Test it** on a step, and a pane opens beside the session with check 1 of N. They answer each check with Done, Failed, Back, Skip or Explain more, and finish on a close-out that names how each check was verified.
- G-2 The walk is the `step-by-step` contract, kept by construction where a program can keep it and proved by the matrix and the smoke test where it cannot.
- G-3 An agent never writes a pixel of the pane. It sends JSON that a validator accepts or refuses whole.
- G-4 Nothing the operator owes is lost to a reload, a parked session or a compaction.

**Non-goals:**

- NG-1 No Markdown prototype and no per-walk HTML (R-2).
- NG-2 The Mission dropdown itself (its anatomy, its states) is the work of its own redesign and is not redone here; this spec only adds one control to a step in it (R-3).
- NG-3 `harnu:one-by-one` is not changed (card T765, out of scope; R-6 concerns `step-by-step` only).
- NG-4 No verb lets an agent press a button of the pane, settle a criterion or perform a check; the operator's Done and Mark are theirs (R-6).
- NG-5 No script is generated from the criteria alone; a walk is written by a session that holds the context (R-4).
- NG-6 Harnu does not capture screenshots of the running app for a walk in this version; an image is a file the agent already has (R-11, D-3).
- NG-7 No new board card or bug card is created by the pane itself; a failure becomes a card only when the agent offers it and the operator accepts (R-8, D-10).
- NG-8 A walk is not a second mission tracker: it adds no step, milestone or criterion to a mission (R-13).
- NG-9 The chat behaviour of the two skill copies is not reconciled here: the bundled copy is not rewritten to the personal one's contract, which is a separate card (R-6, D-9).

**Anti-goals:** outcomes that would make this a failure even if every AC passed.

- The operator presses Enter out of habit and a criterion is settled that nobody checked.
- The pane becomes a second place to read mission state, and the two disagree.
- The agent chats a paragraph for every button the operator presses, so the transcript the walk was meant to quiet gets louder.
- A walk reads well but the operator, three checks in, cannot tell what they should see.

### The shape: what the operator sees

One pane in the helper stack (`type: 'walk'`, `WalkPane.vue`), with the standard 24 px pane header (icon, the walk title, expand, maximize, close). The body is one column:

1. **Progress.** `Check 3 of 9` and nothing else, with a `list` button at its right (opens the roadmap, shortcut `L`) and a `…` menu with **End walk**. No bar. `n` is the check's fixed place among the checks to walk, `N` their number (rules in "Flow and states").
2. **The check.** Its title; one line saying what this is and why it matters, and under it **More** when Explain more has added some; **Where** (a line, with an "approximate" mark when the path is not confirmed); a numbered **Do** list where every item says what the operator will see when it worked, and any command is a ready-to-paste block with real values filled in; **You should see**, quoting the literal expected value (it is the skill's Observe line), with the image when one exists; **Does not work if**, quoting the literal symptoms; a per-item table when one check covers several things; **Checked from here** (what the agent already proved) or "Nothing from here" with the reason; **Links**.
3. **The outcomes**, pinned at the foot: **Done** (primary, Enter), **Failed**, **Back**, **Skip**, **Explain more**. These five are on every check at the moment it asks for the operator's answer. While the check waits for the agent, or after the agent disagreed, the foot shows what that state needs instead (below).

Press Failed and one line opens above the foot: a text field ("What did you see?"), a paste target for a screenshot, Send. Press Done on a check the agent can check from here and the foot becomes "Checking from here…" until the agent answers. The close-out replaces the check when the walk ends.

### The walk script: the data contract

`walk_open` receives one JSON object (the mission and step are verb arguments, not part of the script). The template renders it; nothing in it is markup. Limits are enforced by the validator (S-1), and the whole script is refused with one violation per rule if any check breaks one.

```json
{
  "title": "Search box on the notes list",
  "leftOut": [{ "text": "Rename the index file", "owner": "ours" }],
  "checks": [
    {
      "id": "c1",
      "title": "Typing narrows the list",
      "why": "The box filters notes as you type; it is the whole feature.",
      "where": {
        "text": "example-web, Notes page, on the PR 101 preview",
        "path": "Notes page, search box above the list",
        "approximate": false,
        "link": {
          "label": "PR 101 preview",
          "kind": "url",
          "target": "http://localhost:5173/notes",
          "checked": { "status": "ok", "at": "2026-11-17T21:10:00Z" }
        }
      },
      "do": [
        {
          "text": "Open the Notes page and click the search box.",
          "see": "The caret blinks in the box and all 12 notes are listed.",
          "links": [0]
        },
        {
          "text": "Type `standup`.",
          "see": "Only the two notes whose title contains `standup` stay.",
          "block": { "text": "curl -s localhost:5173/api/notes?q=standup", "lang": "sh" }
        }
      ],
      "passes": "The list shows exactly 2 rows: `Standup 14 Nov` and `Standup 7 Nov`.",
      "fails": "More than 2 rows, an empty list, or the list only updates after Enter.",
      "images": [
        {
          "src": "docs/design/notes-search/screens/search-typed.png",
          "alt": "Search typed",
          "kind": "expected",
          "caption": "Mockup frame"
        }
      ],
      "precheck": "The preview serves the new markup (the `data-search` attribute is in the page).",
      "check": { "how": "curl the preview and count the rows in the response" },
      "criterion": "ac-4",
      "blocks": ["c3"],
      "undo": "Clear the search box.",
      "links": [
        {
          "label": "PR 101 preview",
          "kind": "url",
          "target": "http://localhost:5173/notes",
          "checked": { "status": "ok", "at": "2026-11-17T21:10:00Z" }
        },
        { "label": "PR 101", "kind": "pr", "target": "101" }
      ]
    }
  ]
}
```

Rules the validator enforces (each is an AC or part of one):

- **A complete how-to.** Every check has `why`, `where.text`, at least one `do` item, and each `do` item has `see`; `passes` and `fails` are present and non-empty; at most 8 `do` items, 2 images, 12 `table` rows; text caps of 50 (title), 160 (why, undo), 240 (passes, fails). A check has either `check` (what the agent will read-only check) or `nothingFromHere` (why it cannot).
- **Blocking is derived, never declared.** A check is blocking when its `blocks` list is not empty (a later check depends on it), which is the skill's own definition. There is no separate flag.
- **Inline copy and link.** Every backtick span in `text`, `see`, `passes`, `fails` renders as a copy chip. `block.text` renders as a copy block. `do[].links` are indexes into the check's `links`, drawn as link chips at the point of use; the closing Links list repeats all of them. A `<placeholder>` left in a `block` is refused (`PLACEHOLDER_IN_COMMAND`): the skill says real values.
- **Links are data, never URLs the page opens.** `kind` is `pr` (a number of the folder's repo), `file` (a path that exists inside the folder), `url` (`http` or `https`) or `folder` (a known Harnu folder); a target that fails its kind's test refuses the script. A `url` carries `checked` (`ok`, `login` or `unchecked`, plus the time). Harnu does not fetch an external address when it accepts a script: `checked` is the agent's own declaration and the pane prints it as such ("behind a login, not opened", "not checked"). That the address answered 200 and is the right page stays the skill's rule (agent side). A click path with no link goes in `where.path`, and `approximate` (true or false) is then required, so an agent must decide whether it is asserting a menu path.
- **No emoji, no secret.** Text with an emoji is refused. A `block`, `check.how` or copy chip that looks like a secret (the same patterns the `get_session` scrubber knows) is refused.
- **Images are files.** `src` is a path inside the folder, under the image cache or a pasted-image path (the same jail `draw_canvas` uses), at most 2 MB, copied into the walk's folder when the script is accepted. `kind` is `expected` (a mockup frame) or `capture` (a verifier or live capture) and drives the caption.
- **Pre-closed rows.** A check may carry `status: "verified"` with `evidence`, or `"caveat"` with `evidence` and `openPr` (right in the open PR, not yet where it ships). It is drawn in the roadmap with its glyph and is never served.
- **Order and left out.** The order of `checks` is the order walked. `leftOut[].owner` is `ours`, `optional` or `decision`, at most 10 rows.

The record Harnu keeps beside the script (`WalkRecord`, written only by main, atomic, versioned) holds the script, a `rev`, the cursor, an outbox of turns not yet delivered, and per check: its status, attempts, the failure line and image, the correction, the agent's report, the `more` text and `extra` sub-checks appended by Explain more, and the way it closed. `walk_get` returns it compactly.

### Flow and states: the view-model

The rules live in one pure module (`src/shared/walk-machine.ts`, Electron-free, imported by main and by the renderer) so the pane draws what the machine says and recounts nothing.

| Check state    | Glyph (turns, roadmap) | Icon in the pane | How it gets there                                                                  |
| -------------- | ---------------------- | ---------------- | ---------------------------------------------------------------------------------- |
| to do          | `-`                    | `minus`          | not reached yet                                                                    |
| current        | (the served check)     | none             | the first to-do check whose blockers are closed; else the first skipped one        |
| awaiting check | `-`                    | spinner          | Done on a check that has an agent check; closes only on `walk_report`              |
| disagrees      | `!`                    | `triangle-alert` | the report says fail after a Done; a blocking check stays here                     |
| verified       | `✓`                    | `check`          | Done plus a passing report, or Done on a check with `nothingFromHere`              |
| caveat         | `!`                    | `triangle-alert` | Follow anyway, or Continue without the check (D-7), or a pre-closed `openPr` row   |
| failed         | `✗`                    | `x`              | Failed, or Treat as failed (open until Done or Skip)                               |
| skipped        | `-`                    | `minus`          | Skip; resurfaces after the last to-do check; a check it blocks waits for its retry |

Outcomes, exactly four on every check, plus one:

- **Done** closes the check (see above). **Failed** requires a line or an image before it can be sent, delivers it, and keeps the same check on screen. **Back** returns to the previous served check, whatever state it closed in: that check becomes current again, its agent report is cleared (the log keeps it), its attempts are kept, and when it has `undo` the pane leads with it. **Skip** marks the check skipped and serves the next. **Explain more** asks the session to deepen this one check and never moves the cursor. **Treat as failed** (after a disagreement) needs no new line: the agent's evidence is the symptom, and it is delivered with the turn.
- **The foot in the other states.** While a check awaits the agent the foot is a status line ("Checking from here…"). When the agent disagreed the foot offers the skill's own options: for a blocking check Re-check, Treat as failed and Back; for a non-blocking one also Follow anyway.
- **The failure loop.** After Failed, the agent gives one correction (`walk_report`, `kind: "correction"`). The pane shows it above the same check; the operator answers again with the same outcomes. No attempt limit. A second correction before the operator answers again is refused.
- **Explain more** appends `more` (why it matters, where it was fragile, at most 400 characters) and `extra` (at most 6 sub-checks, each one `do` item with its `see`) under the current check with `walk_extend`. A **sub-check is an extra `do` item** of the same check, so the check keeps its state, its attempts and the page's scroll position, and the progress count does not change. The operator answers the whole check; one that fails is Failed with a line that says which.
- **Numbering.** `N` is the number of checks to walk: pre-closed rows are not counted and are not served. `n` is the current check's fixed ordinal among them, so a check that resurfaces after a skip still reads its own number, and Back shows the ordinal it returns to. `walk_extend` with `append` adds checks at the end: `N` grows, the roadmap marks them as added, nothing is reordered or removed (a plan only grows).
- **A late report.** The wait for the agent starts when the turn is delivered, not when Done is pressed (a parked session can take up to 40 s to wake). A `walk_report` that arrives after Continue without the check is accepted: a pass upgrades the caveat to verified, a fail makes the check disagree. A report for a check that is not awaiting and was never awaiting is refused.
- **Close-out.** When no to-do or skipped check is left, or the operator picks End walk, the pane shows the rail (one row per check: its glyph and how it was verified, for example "verified, Done plus the check", "verified, you confirmed, nothing to check from here", "caveat, you confirmed, my check disagreed", "skipped"; a verified check shows "criterion open" or "criterion settled" read live from the mission record), a `⚑ you` block that always prints (what is still owed: skipped, failed, followed unverified, "re-check N after #PR merges", or "nothing, you're clear"), the links of what is owed, and a summary of at most three lines. **The pane is the report.** The same text goes to the session as one `closed` turn so the agent has it, and the agent answers it with at most three lines: offers of cards for what is owed, nothing else.
- **Settle (D-2).** The close-out offers one button, "Settle N criteria", counting the checks that closed verified whose criterion is `operator` or `session` and not yet settled. A `person` criterion needs that person, so it is listed as owed ("approval by <person>"); a fact criterion is never ticked; a caveat or a skipped check never counts. The click writes each through the operator door with the evidence "Walk, check cN, confirmed by the operator" and changes nothing else in the mission.

### Events and verbs: how the pane and the session talk

The operator never types to drive the pane, and the agent never presses its buttons. Two directions:

**Pane to session: `[harnu-walk]` user turns.** They use the existing user-turn route with a new `walk` source and its own toast title (it needs i18n keys in both locales, so it is S-1's), so a parked session is woken and a turn waits while the operator types. Delivery goes to the walk's owner session; when the owner was released by a hand-off it falls back to the mission's current leader, then to the folder's selected session, as page events do. An undeliverable turn is **kept in the record's outbox** (not in memory) and replayed when a session can take it, including after a restart. Only an outcome the agent must act on sends a turn; Back, Skip and a Done with nothing to check do not, and the next turn carries a progress line so the agent is never behind.

```
[harnu-walk] Search box on the notes list — check 3 of 9 · done
walk: wlk-5d2e91ab · check: c3 · session: <owner session id>
The operator pressed Done. Run the read-only check of this check, then answer with walk_report.
progress: ✓ 2 · ! 0 · ✗ 0 · - 7
```

Kinds: `done` (a check with an agent check), `failed` (carries the operator's line verbatim and the saved screenshot's absolute path), `explain`, `treat-as-failed` (carries the agent's own evidence), `closed` (the close-out text). A failure line is the operator's own typing and is delivered as theirs; control characters and look-alike delimiters are stripped as `sanitizeUntrusted` does. The turn's first line carries the kind and never a score (the lesson precedent).

**"Test it" to the session: `[harnu-walk-request]`** (S-4), one turn naming the mission, the step and whether a walk already exists, plus a self-sufficient brief of at most 1,500 characters (the sources to read, the contract in eight lines, "open it with `walk_open`"). It does not depend on the skill being switched on.

**Session to pane: four verbs**, run free like `open_file`, recorded in the audit log, absent from the Scheduler `observe` allowlist.

| Verb          | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `walk_open`   | `{ folder, sessionId, script, missionId?, stepId? }`. Validates the whole script, copies its images, writes the record, asks the folder's helper stack to open the pane in the background. ACK: `walkId`, `checks`, `rejected` (each violation with its JSON path and rule), `opened` (false until the pane type exists, S-2). A second open for a step with a live walk is refused `WALK_EXISTS` with its id; once a walk has ended, `walk_open` for the same step starts a new one (a re-walk after "re-check N after #PR merges"). |
| `walk_extend` | `{ walkId, checkId, more?, extra? }` (Explain more) or `{ walkId, append }` (new checks at the end). Only grows; refused on an ended walk; `expectRev` guards a stale write.                                                                                                                                                                                                                                                                                                                                                          |
| `walk_report` | `{ walkId, checkId, kind: "check", result: "pass" or "fail", evidence }` or `{ walkId, checkId, kind: "correction", text }`. Refused when the check is not awaiting a report or has no failure to correct.                                                                                                                                                                                                                                                                                                                            |
| `walk_get`    | `{ walkId }` or `{ folder, stepId }`. Progress, the cursor, each check's glyph, the last failure, what is awaiting the agent, the outbox, `rev`. Enough for a session with no memory of the walk to carry on: the read to make after a compaction.                                                                                                                                                                                                                                                                                    |

No verb takes a command to run, presses Done, Back, Skip or Failed, or settles a criterion.

### Where things live

- The walk record: `<main checkout>/.harnu/walks/<walkId>/` (`walk.json`, `images/`), next to the missions record, shared by every worktree, written only by main (D-8).
- The pane type `walk` in the helper stack, persistable like a Markdown pane (it stores `walkId`, never content), so a restart restores it from the record. It is registered in `lib/pane-registry.ts` and `lib/pane-components.ts` and added to the `HelperPane` type (S-2).
- The entry: a compact **Test it** control in the open step of the Mission dropdown, drawn only when the step has something to hand-check (an `operator` or `person` criterion, or a `session` criterion the verifier left open). It sends `[harnu-walk-request]` to the mission's leader; with a live walk for the step it focuses that pane instead (its label then reads "Continue test").

### Recommendation for D-1: a native Vue pane, fed by the same JSON

A live-panel template can render the data, but six consequences of the facts in the table of the Problem section make it the wrong host for this walk:

1. It cannot open a link by itself: while its network switch is off (the default) a page may go only to its own folder host and open no popup, so a PR, a URL, a file in the viewer or a folder would each need an emit, a round trip through the agent, and an agent verb to open them. Turning the switch on would let the page navigate anywhere, which is worse for a page that renders agent-supplied text.
2. It cannot settle a criterion or call any Harnu function; its only door out is an emit that reaches the agent as data (D-2 needs an app-side door).
3. It can lose an answer: emits are capped at 1 per second and 20 per minute, and what the cap drops reaches the agent only as a count. A quick Done, Back, Skip sequence would lose events the record must keep.
4. It cannot save a pasted screenshot into the walk's folder: an emit carries at most 8 KiB of payload.
5. The visual system is a page's own CSS, so the tokens would be copied into the template and drift from `design.md`; a native pane uses `themes.css`, i18n and the theme switch as every other pane does.
6. State in a 256 KiB sidecar keyed by a page path is a worse record than a versioned `WalkRecord` that main owns, with an outbox that survives a restart.

What a live panel does better is that it needs no new pane type and no new IPC. If D-1 flips to a live panel, the spec is amended: S-1 shrinks to the schema validator and a helper that writes the page's sidecar, the verbs and the `walk` turn source disappear in favour of `browser_set_data` and `[harnu-page-event]`, and S-2 becomes a template file. That is why S-1 and S-2 are both gated by D-1.

### Proposed `design.md` section

To be inserted in §6 after "Diagram pane (canvas viewer, non-PTY)" (a pane of the helper stack, same family). The icon table of §5 gains the icons that are not yet listed (`minus`, `list-checks`, `circle-help` and any of `list`, `arrow-left`, `flag`, `triangle-alert` that lacks the walk's row). It adds **no colour, radius, easing or row height**, and every size is on the type scale of §3 (`text-body`, `text-ui`, `text-caption`, `.eyebrow`, Code-sm). It reuses `Button`, the code-block copy control of the Markdown renderer, `ImageLightbox`, the warning-callout pattern and the row anatomy of the Links popover. What it **defines new** is two small pieces: the inline copy chip and the strip of pasted-screenshot thumbnails.

```markdown
#### Guided test walk pane (helper stack — T765)

A fixed template that walks the operator through a hand check of a delivered step, one check at a
time. **The agent sends data; the template draws it.** Component `WalkPane.vue` (with
`WalkCheck.vue`, `WalkRoadmap.vue`, `WalkCloseOut.vue`, `WalkFailure.vue`); the pure rules are in
`src/shared/walk-machine.ts` and `lib/walk-view.ts`. Principle: every element earns its place.
Progress is `Check 3 of 9` and nothing else.

**Pane.** A helper-stack pane (`type: 'walk'`) with the standard 24px header: icon `list-checks`
(12px, `--color-text-3`), the walk title (truncated), expand, maximize, close. Body: a column,
the check in the one scroller (thin scrollbar on `border-border-2`), the outcomes pinned under it.
Padding `12px 14px`. It is never inside a dropdown: it lasts minutes while the operator clicks around.

**Progress row.** `Check 3 of 9` (`text-caption`, `tabular-nums`, `text-text-2`), at the right a `list`
icon button (the roadmap, `L`) and a `more-horizontal` menu (End walk). No bar, no percentage.

**The check card.**

- **Title** `text-body` at weight 600, wraps, never truncates. Under it, `why` (`text-ui`,
  `text-text-2`), then **More** (the same, `text-text-3`) when Explain more added some.
- **Where**: the `.eyebrow` utility (default colour) and the text (`text-ui`). An approximate path
  carries a muted chip "path approximate" (`bg-surface-2`, `border-border`, `text-text-3`,
  `text-caption`) so it is never read as fact.
- **Do**: a numbered list (`text-ui`), the number in `tabular-nums text-text-3`. Under each item its
  `see` line (`text-caption`, `text-text-3`, a leading `eye` icon at 11px). A `block` is a code block
  with the copy control of the Markdown renderer. **Variant for this pane:** the control is always
  visible, not hover-revealed (a walk is read once and driven by keyboard and touch). Link chips of an
  item sit after its text.
- **Copy chip (new).** Every backtick span is an inline chip (Code-sm, `bg-surface-2`,
  `border-border`, `--radius-sm`, `padding: 0 4px`); one click copies its exact text and the chip
  shows `check` (`text-green`) for about 1.5s, `aria-label` swaps in step. A pointer click does not
  take keyboard focus from the pane (so Enter after a copy is still Done). Paths, ids, branch names,
  URLs and error text are all chips. No value is shown that cannot be copied.
- **You should see / Does not work if**: one card (`bg-surface-2`, `border-border`, `--radius`,
  `padding: 8px 10px`): `check` icon in `text-green` and the `passes` text, then `x` icon in
  `text-red` and the `fails` text. The image sits under the first row, `max-width: 100%`,
  `--radius-sm`, `border-border`, a caption (`.eyebrow`: "Mockup frame" or "Capture, 14 Nov"); a click
  opens `ImageLightbox`.
- **Table** (when present): item, what it must show, its source. `text-caption`, `border-border` rows.
- **Check line**: `bot` icon 11px and "Checked from here: …" or "Nothing from here: …"
  (`text-caption`, `text-text-3`).
- **Links**: a heading "Links" (`.eyebrow`) and one row per link in the anatomy of the Links popover
  (kind icon, label, trailing copy button 12px, always visible). Kinds and icons: `pr`
  `git-pull-request`, `file` `file-text`, `url` `globe`, `folder` `folder`. A click opens the real
  thing: a PR or a URL in a browser pane of this folder, a file in the viewer, a folder selected in
  the sidebar. A link whose target no longer exists is not drawn. A URL that was not checked says
  "not checked"; one behind a login says "behind a login, not opened". No absolute home path is ever
  drawn.

**Outcomes (pinned, `border-t border-border`, `padding: 8px 14px`).** `Done` (`Button` primary; the
chord is in its `title` as for every shortcut, no `<kbd>` in the button), `Failed` (soft), `Back`
(ghost, `arrow-left`), `Skip` (ghost), `Explain more` (ghost, `circle-help`). Under **420px** of pane
width the row wraps: Done and Failed take the first row (halves), the other three the second. Every
button keeps its label; none is hidden to make room. Back is disabled on the first check. Done is the
only primary in the pane at any moment.

**States of the foot.**

- **Failed**: an inline form above the foot: a one-line field ("What did you see?"), a paste target
  ("Paste a screenshot"), pasted thumbnails (new strip: 64px, `--radius-sm`, removable), Send (soft;
  Enter) and Cancel (ghost; Esc). Send is disabled until there is a line or an image. A line that
  looks like a secret shows `SettingHint` "This looks like a secret. Describe it instead."
- **Awaiting the agent's check**: the foot becomes "Checking from here…" with the spinner of the
  pane's loading state. Thirty seconds after the turn was delivered a soft button "Continue without
  the check" appears (D-7).
- **The check disagrees**: a warning callout (`triangle-alert` in `text-warning`, `bg-surface-2`,
  `border-border-2`) "Your side says done, mine doesn't:" plus the evidence in a chip, and the foot
  offers Re-check, Treat as failed and Back (and Follow anyway when the check is not blocking).
- **A correction** from the agent after a failure: a neutral callout above the check (`bg-surface-2`,
  `border-border-2`) with the one correction, copy chips live; the five outcomes stay as they are.

**Roadmap (the `list` button, `L`).** A popover under the progress row in the anatomy of the Links
popover: one row per check with its glyph as an icon (`minus`, `check`, `x`, `triangle-alert`; the
current one has the accent halo of the Mission tree) and its title, "added" on a check found mid-walk,
a pre-closed row with its evidence; the "left out" lines under a divider. A click on a row does nothing:
the walk is not random access. Esc closes it.

**Close-out.** Replaces the check. Rows as in the roadmap, each with how it was verified and, for a
verified check, "criterion open" or "criterion settled"; a `flag` block "You" that always prints
("Nothing owed, you're clear" when empty); the links of what is owed; a summary of at most three
lines; when a verified check answers an unsettled `operator` or `session` criterion, one button
"Settle N criteria" (soft; D-2), then Close.

**Keyboard.** Enter is Done when the focus is on the pane or the Done button; on a copy chip or a
link Enter keeps its own meaning, and in a field Enter sends. A second Done within 400ms of a new check
appearing is ignored, so a double press never closes two checks unseen. `F` Failed (focuses the field),
`B` or `Left` Back, `S` Skip, `E` Explain more, `L` roadmap, `Esc` closes the form or the roadmap. The
shortcuts are plain keys, so they are off while a field has focus. The pane is `role="region"` with
`aria-label` the walk title; the current check is `aria-live="polite"` when it changes.

**Motion and small panes.** A new check enters with `.anim-fade-in` (none under reduced motion);
nothing else animates but the spinner and the 1.5s copied state. Every width rule is on the pane's own
width: below **360px** the Do numbers drop into the text line, the table scrolls inside its own box
and nothing scrolls the pane sideways. Text wraps with `overflow-wrap: anywhere`.

**Don'ts.** ❌ Show more than one check. ❌ Show a bar, a percentage or a second counter. ❌ Open a
dialog for an outcome. ❌ Draw a value that cannot be copied or a link that opens nothing. ❌ Print
an absolute home path. ❌ Settle a criterion on Done. ❌ Add a colour, radius, easing or size off the
scale. ❌ Let the agent supply markup, a class, a colour or an icon name. ❌ Two primary buttons.
```

Two product hooks exist and are honoured only when `!app.isPackaged`: a dev door to open a walk without a session, and `HARNU_WALK_CHECK_WAIT_MS` to shorten the 30 s wait of D-7 (case W-14).

**Output:** one line per case and a tally, evidence (screenshots, the stub's received file, a `results.json`) in the evidence folder whose path is the last line. The rows in brackets are the ones the matrix says the case proves:
