# Agent control

Harnu runs a small MCP (Model Context Protocol) server that a Claude session can talk to from inside its own conversation. In plain terms: a session isn't limited to just editing files and running shell commands in its own folder anymore — it can also reach out and act on Harnu itself, like spinning up another session, creating a worktree for a task, checking on the rest of your fleet, or reading and writing your project's shared notes.

## Agents act freely by default

**The server is on out of the box, agents can act in every folder, and their actions do not stop to ask you.** A session that decides to create a worktree and start another session in it just does it — no per-folder switch to flip first, no Allow/Deny prompt in between.

This is a deliberate reversal of how Harnu used to work. Before, every folder was fail-closed and every state-changing action stopped at a confirmation. In practice that meant a session would create a session, get an id back, and then be refused when it tried to check on it — and your machine sat idle until you came back and flipped a switch by hand. The friction was buying very little: you had already decided to point Harnu at that folder, and a session can pin folders on its own anyway.

Everything a session does is still written to the **audit log** (Settings → Control server), which is now your main record of what ran while you weren't watching.

### The three ways to say no

1. **Ask before agent actions** (Settings → Control server, off by default). Turn it on and every state-changing action goes back to asking you first, in every folder. This is the old behavior, one toggle away.
2. **Block a folder.** Right-click a folder → **Block agent control**. Agents are refused in that folder _and everything under it_ (so blocking a repo blocks its worktrees too). This refusal is absolute — no mission grant or "always allow" can reach into a blocked folder. A blocked folder shows a small crossed-out-bot marker in the sidebar. The same on/off switches are listed in Settings → Control server.
3. **Turn the server off.** The master switch in Settings → Control server. Nothing gets through, not even reads.

If a session tells you it was refused, it hit #2 or #3 — those are the only things that can stop it.

**Turning the server off and back on doesn't break sessions that were already running.** The credential a session uses to reach Harnu is stored on disk and reused across restarts, so a session that was working before you toggled the server keeps working after — no need to resume it just because you flipped the switch. The one thing that can still leave a session stranded is if Harnu has to bind a different network port on that restart (rare — it only happens if the port it used before got taken by something else in the meantime); in that case a session spawned before the restart can't reach the server anymore and does need to be resumed to reconnect.

**The server's name is `harnu`.** Inside a session, its tools show up as `mcp__harnu__<verb>` (for example `mcp__harnu__create_session`), and its resources use `harnu://` addresses. If you wire the server into your own `claude` config by hand, **Settings → Control server → Copy config** gives you a snippet that registers it under the `harnu` key. Older notes, memory files and scripts may still say `mcp__capy__<verb>` or `capy://`; the rename changes the label, not what a verb does. Harnu still understands the old resource address, and you don't have to touch anything you've already set up.

**Your saved "always allow" choices keep working.** A rule you saved earlier, such as `mcp__capy__create_session` in a folder's `.claude/settings.local.json`, still lets that verb run without asking, so nothing re-prompts after the rename. New "always allow" choices are saved under the new `mcp__harnu__` name. Scheduler workers in read-only mode stay as locked down as before: the list of verbs they may and may not call covers both names.

## What a session can actually do

**Look.** A session can check on the rest of your fleet — which sessions exist, what they're doing, whether they need you — list your git worktrees, list the Docker containers your projects left running (see "Watching Docker containers" below), and read your project's shared memory (see [Project memory](project-memory.md)). A session it just started shows up in that same check immediately, even before the new session has actually written anything to disk — it's marked as still-starting rather than being invisible until it catches up, so a session checking its own work doesn't have to guess whether "no result yet" means "starting up" or "never happened."

**Act.** Without stopping to ask (unless you turned on "Ask before agent actions"), a session can:

- Start a new session in a folder, optionally with a starting prompt
- Create a git worktree for a task (seeded from the repo's `WORKTREE.md`, same as if you'd made it by hand — see [Folders and worktrees](folders-and-worktrees.md)). By default the new branch forks from the remote default branch, but a session can name an explicit base branch to **stack one task's worktree on top of another** — e.g. a dependent PR that needs to build on a branch that hasn't merged yet. Naming a base that doesn't actually exist is refused outright rather than quietly falling back to the default. If a branch or worktree already exists whose name looks like it's for the same task (e.g. a stale attempt from an earlier dispatch), the session is told so — a warning, not a refusal, since starting fresh is sometimes exactly right, but it gives the session a chance to notice duplicate work before spawning a second one. If the repo's setup step fails instead (a missing tool, a failing command), the half-made worktree and its branch are always cleaned up automatically — and, whether it's a session or you creating it, the error now says exactly what failed, whether the tool was simply missing or actually ran and errored, and confirms the cleanup happened, instead of a bare, hard-to-read error line.
- Spawn a plain shell in a folder
- Pin an existing folder into your sidebar
- Clean up a "ghost" folder — one whose directory is already gone but whose entry (and its now-broken session) still lingers in your sidebar
- Write an entry to project memory (a decision, a session summary, or a refreshed "where we left off" note)
- Open a file — a report, a draft, a snippet, an image — in a read-only viewer pane inside Harnu, so it can hand you something to look at without you leaving the app. Sessions are told to use this for anything you'd want to **copy or keep** (a drafted message, a PR description, a config, a longer code snippet) instead of printing it into the terminal, where it scrolls away and is awkward to select. The pane has a copy button on every code block and a "Copy file" action for the whole file, so the handoff is one click. Conversation — explanations, answers, status — still stays in the terminal where it belongs
- Post a short notice into your Activity history that any session's window can see — see "Session says" below
- Say one short line out loud through your speakers, if you've turned voice on — see "Sessions talking out loud" below
- Draw on a canvas — an infinite whiteboard that opens in a pane beside the session and that you can edit back. See "Drawing on a canvas" below
- Send a message to another Harnu session — see "Sessions talking to each other" below
- Create a Scheduler worker in `observe` mode — see "Creating a Scheduler worker" below
- Keep track of a larger piece of work as a **Mission** — see "Tracking a mission's progress" below

**Starting a session means it actually started.** When a session asks Harnu to launch a new session, Harnu waits (up to about a minute) to confirm a real process came up and wrote its transcript before telling the requesting session "done" — it no longer reports success the instant it accepted the request. If a launch doesn't come up in that time, the requesting session is told so plainly (and if that action was covered by a mission grant, the budget it spent gets handed back, since Harnu can't yet confirm anything happened) — but the new session itself is left running rather than killed, since a launch that's merely slow can still land a few minutes later, and Harnu has seen that tail run as long as ~14 minutes. The requesting session is told the new session's id so it can check on it directly instead of guessing. Harnu also refuses a second launch into a folder that already has one in progress — including one that's still catching up after a slow-launch report like this — rather than risking two sessions racing in the same folder; that refusal clears on its own once the slow one is confirmed running (or is given up on after sitting unconfirmed for about an hour).

**A pane always opens in the session's OWN folder — never wherever you happen to be looking.** If you're viewing a different folder when the pane lands, that folder's row gets a small accent pill in the sidebar (distinct from the green/amber/red session dots) counting what's waiting, and Harnu pops a native notification — clicking it jumps straight to that folder's most recently active session. Open the folder yourself and the pill clears. A folder Harnu doesn't actually track (an unrecognized path) never gets a phantom pane — the session is told the folder didn't resolve instead.

**Organize the roadmap board directly.** A session can create, edit, and move cards on your [roadmap board](roadmap-board.md) — the same way it can append to project memory. Editing covers both a quick note appended to a card and a full rewrite of its whole spec, the same full-replace a card's Edit button gives you in the app. A session can also set a card's PRD and ADR doc paths, alongside its spec — the board uses these to show per-artifact badges (a green check when a required doc is there, an amber warning when it's expected but missing) instead of one anonymous "gaps" count. What a session can never do on the board is close a card (that's always your call) or actually launch work against one without a further step — see "Getting from a card to a running session" below.

A session can also attach a pasted screenshot to a card it's creating or editing — the same image you'd see in the footer's pasted-images gallery. It hands over the image's path, and Harnu copies the bytes into the board's own storage and drops the picture into the card's body, so you never have to describe a bug in words when a screenshot already shows it.

A session can also archive or delete a card. Archiving is treated the same as every other board organizing action above — it happens directly, no asking — because it's reversible: the card just moves off the board, the same as the app's own Archive button, and you (or the session) can bring it back. Deleting is different: unlike everything else a session can do to the board, it always stops to ask you first, since there's no undo once the file is gone. Either one is refused outright while the card is In progress — a session has to move it to Review first.

**Cleaning up ghost folders — sidebar bookkeeping only, never disk.** If a folder's directory gets deleted — by Reaper's sweep, by a manual worktree removal, or by something outside Harnu entirely (an `rm -rf` you ran yourself) — but Harnu's sidebar hasn't caught up yet, a session can reconcile it directly: it un-pins the folder and drops it (and its sessions) from the sidebar, no restart needed. This ONLY ever touches Harnu's own bookkeeping — it's refused outright if the directory is actually still there, so it can never be used to hide a folder whose data is still real and reachable. There's still no way for a session to delete a worktree, branch, or file on disk; that stays something only you (or Reaper, which you configure) does.

**"Session says" — a notice from any session, without switching tabs.** A session can post a short notice ("Session says") into the same Activity history the [Activity bell](approval-inbox.md#activity-bell) already keeps — visible from whichever window you're actually looking at, not just the one that sent it. It's meant for something worth a heads-up (a finding, a progress update) that doesn't need your Allow/Deny. The notice stays in the bell's list until you clear it — clicking it (or its **Go to session** action, when the sending session included its own id) jumps you straight there and removes it; hovering it lets you dismiss it without navigating anywhere. Either way, it's always your call — nothing switches on its own.

## Sessions talking out loud

A session can say one short line through your speakers — "the migration finished, zero conflicts" — for the times you're not at the screen. This is **not** a notification: it's heard once and then it's gone. Nothing lands in the Activity bell, nothing pops a toast, and there's nothing to come back to later. That's deliberate: if every read-aloud also filed a notice, your Activity history would fill up with sentences you'd already heard. A session that wants you to be able to find the message later posts a "Session says" notice instead (or does both).

**It's off until you turn it on.** Nothing an agent does can make your machine talk on its own — speech reaches everyone in the room, including whoever you're on a call with, so it starts silent. You turn it on in Settings → Voice, and there are two levels:

- **The global switch** covers every folder you have and every folder you'll ever make — including worktrees that don't exist yet. You don't have to enumerate anything, now or later.
- **A per-folder switch** overrides the global for that one folder, in _both_ directions. Turn voice on globally and mute one noisy repo; or leave it off globally and turn it on for the one project you're actually babysitting.

The important half: **an explicit per-folder mute beats the global.** If you silence a folder today and turn the global on next month, that folder stays silent — turning the global on never writes anything into your folders, so a decision you made on purpose isn't quietly undone. A folder you never touched simply inherits whatever the global says, which is what makes "and all future worktrees" work.

> **Where this stands today.** The `speak` verb, the gate and both switches are
> live; the **Settings → Voice** panel that exposes them is the next piece of the
> voice work and is not in the app yet. Until it lands, nothing has been turned
> on — which is the safe default: every folder is silent.

**There's also the engine's own switch.** Voice as a whole has a master switch (the same one that reads things aloud when _you_ ask), plus a mute, plus a choice of engine — your own TTS command or the downloadable offline voice. All of that sits above everything described here: agent speech needs the engine on and unmuted **and** the folder allowed. If a session tells you it spoke and you heard nothing, that's the usual reason — the session is told so explicitly ("the engine is off") rather than being left to assume it was heard. See [Voice](voice.md) for the engines themselves.

**Blocking a folder for agents outranks all of it.** A folder you've blocked (right-click → the folder's agent setting) is silent no matter what any voice switch says. Voice is never a way into a folder you closed.

**What a session hears back when it can't speak.** A refusal is normal here, not a failure, and it names the reason — "voice isn't on for this folder" versus "this folder is deliberately muted" are different answers, and sessions are told not to lobby you to undo a mute you set on purpose. They're also told to use a notice instead, so a message you needed doesn't just vanish because the speakers were off.

**Three limits that keep it bearable:**

- **It won't read you a paragraph.** Anything past ~300 characters is cut at a word boundary — the session is told it was cut, and is asked to say the headline and leave the detail on screen. Audio can't be skimmed.
- **It won't tell you what you're already reading.** If you're looking at Harnu with that very session selected, its speech is dropped — you can see it. Speech from a session in another folder, or while Harnu is in the background, still comes through. (This applies to a session speaking on its own initiative; if you ask to be read to, you get read to.)
- **One session can't hold the speakers.** There's a small per-minute allowance per session, so a looping agent can't talk over everything else. Utterances also queue rather than overlap — with several sessions running, two voices at once would be unusable.

## Drawing on a canvas

Some answers are a picture, not a paragraph. A session can draw one directly: an **architecture map, a flow, a dependency graph, a plan laid out in boxes** — on a canvas that opens in a pane next to the session, where you can grab a box and move it, rename it, wire two boxes together, delete what's wrong, and Save.

By default a session draws on that folder's own board, stored inside the folder at `.harnu/out/canvas/board.harnucanvas.json`. That file is gitignored and lives in the worktree, so each branch gets its own scratch board and nothing lands in a commit by accident. A session can also name a different canvas — but only under `.harnu/out/canvas/` or `docs/canvas/`; anywhere else is refused rather than quietly redirected. `docs/canvas/` is the one to ask for when the diagram is a deliverable you want committed with the branch.

**It opens itself.** A session's drawing call opens the pane for you in the background — it doesn't steal focus, and if you're looking at another folder you get the same sidebar pill and native notification any pane gets. That matters here more than usual: the default board lives under `.harnu/`, which the file browser hides along with everything else gitignored, so the pane the session opens is normally how you see it at all. If you closed the pane and want it back, ask the session to open it again.

**The board has two authors, and it remembers which is which.** Every box and every arrow records who first drew it — the session or you. Three things follow from that:

- When a session redraws its diagram, it only clears **its own** work. Boxes and notes you added survive. (An arrow you drew survives too, unless one of the boxes it connects was the session's and just got removed — an arrow can't outlive a box it's attached to.)
- A session can't claim it was you. It's refused outright from stamping anything as yours, rather than being trusted not to.
- After you edit the board and Save, the session can read it back and tell exactly what you changed — "you deleted three of my boxes, drew two of your own, and renamed this one" — instead of seeing an undifferentiated pile of shapes. That round trip is the point of the feature: the canvas is a place you and a session work on the same thing, not a picture it hands you.

Deleting a box also deletes the arrows attached to it, whoever drew them — an arrow with nothing on one end isn't a thing the board can store.

**Nothing lands half-done.** A drawing call is a batch of edits, and it's all-or-nothing: if any single edit in the batch is wrong, the file is left exactly as it was, byte for byte. You will never open a board and find half a diagram.

**Screenshots.** A session can put an image on the board — the same paths it can use for card screenshots (a pasted image from the footer gallery — in either of Claude Code's cache locations — or a file inside the folder), up to 6 at a time and 2 MB each. The bytes are copied into an `assets/` folder next to the canvas rather than being stuffed into the canvas file itself, so a board with screenshots on it stays small and fast to open.

Drawing is treated like opening a file or posting a notice: it happens directly, no asking, because it writes a scratch file inside the folder the session is already working in and can't reach outside it. With "Ask before agent actions" on, it confirms like everything else.

## Watching Docker containers

A session can list the Docker containers on your machine with the same verdicts Harnu's Containers view uses: each compose project or standalone container, which of your folders it belongs to, and whether it's in use, protected, or left behind — a **zombie** still running for a worktree nobody has touched in days, or an **orphan** whose worktree is gone. It also sees the memory, ports and volumes each one holds, and the recent stops, starts and removals, including which ones you did and which ones an agent did. It can ask for everything, or just one repo and its worktrees.

Reading the list is never something you're asked about, and it changes nothing. Folder paths are shortened the same way the fleet view shortens them. Containers that belong to a folder you blocked for agents still show up in the list, marked as off-limits, so a session can tell you about them without touching them. If Docker isn't installed or isn't running, the session is told exactly that, with Docker's own error — it never gets an empty list it could mistake for a clean machine.

A read-only (`observe`) [Scheduler worker](scheduler.md) is allowed to use it, so you can have a worker check for zombie containers on a schedule and notify you when it finds some.

### Stopping, starting and removing containers

A session can also act on those containers, through the same Stop, Start and Remove the Containers view gives you — the same code path, so the same safety rules hold for an agent as for you:

- **Stop** runs without asking, because it's reversible: a stopped container can be started again. A session can stop a zombie or an orphan on its own. It can't stop one a session is working in, or one running from a repo's main checkout, unless it explicitly forces the stop — and a forced stop always asks you first.
- **Start** runs without asking. It's refused for an orphan (its worktree is gone, so nothing would use it).
- **Remove** always asks you, every time, whatever your settings are — no mission grant or "always allow" checkbox can skip it, because a removed container can't be brought back. It removes one stack per request, never several at once. It's refused while the stack is still running (the session has to stop it first), while a session is working in its folder, for a main checkout, and for a stack that isn't a zombie yet. The confirmation names the stack, the folder it runs from, and whether its volumes would be deleted too. Volumes are only removed when the session asks for it, always after the containers, and a volume another stack also uses is never removed.

A container Harnu can't tie to one of your folders is never touched by any of the three, and neither is one in a folder you blocked for agents. Every stop, start or removal a session makes is recorded in the Containers view's history, marked as done by an agent, so you can always see what it did. Read-only Scheduler workers can watch containers but can't do any of this.

## Watching workspace cleanup

Harnu's Cleanup surface sorts every worktree into **corpse** (its branch is proven merged, it's clean, nothing is running in it, and its grace period is over), **decide** (it needs you, with a one-line reason) or **alive**. A session can read the same list — each worktree's bucket, the reason, how much disk it holds, any orphan Docker volumes, the totals, whether the automatic cleanup is on, and when the next cycle runs. It can ask for everything or just one repo and its worktrees. Reading the list never asks you and changes nothing, and folder paths are shortened to names the same way the fleet view shortens them. Worktrees in a folder you blocked for agents still show up, marked as off-limits.

A read-only (`observe`) [Scheduler worker](scheduler.md) can use it, so you can have a worker report how many corpses have piled up and how much space they hold.

### Telling Harnu a worktree is finished

When a session's pull request has merged, it can **release** the worktree it worked in. That skips the grace period, so the worktree becomes a corpse at the next scan instead of waiting a couple of days. It runs without asking, because it deletes nothing — you (or the automatic cleanup, if you turned it on and acknowledged its first report) still do the cleaning.

A release is only a hint about timing; it never overrides a safety rule. A worktree with uncommitted changes or unpushed commits, one with a session still open, one whose Docker stack another worktree also uses, and one you marked Keep or never-clean all stay out of the corpse list, and the session is told which rule held it back. It's refused for a worktree whose branch isn't proven merged, for a repo's main checkout, for a folder Harnu doesn't know, and for a worktree in a folder (or a repo) you blocked for agents. A session can name the worktree by its folder or by the name the list gave it. Read-only Scheduler workers can't release anything.

These two verbs never remove anything, and no session can clean a worktree. (A session can remove Docker containers, but only through a separate action that always asks you first — see "Stopping, starting and removing containers" above.)

## Tracking a mission's progress

When a session owns work that spans several sessions or a long stretch of time — coordinating a multi-part delivery, say — it can keep a **Mission**: one structured record of where that work stands, instead of a loose notes file only the session itself understands. (Despite the name, this has nothing to do with the **mission grant** in "Batching approvals" below — a grant is a batch of pre-approved actions; a Mission is progress tracking. They just share a word.)

Missions live in your repo's main checkout under `.harnu/missions/`, one file per mission, and every worktree of the repo sees the same ones. Like the rest of `.harnu/`, they stay on your machine and out of git. Everything below happens directly, without asking you, the same as organizing the roadmap board — and a folder you blocked for agents is off limits here too.

What a session can do with one:

- **Start a mission** (`mission_create`). It has to say up front what "done" means — what kind of deliverable it is (code, UI, research, a decision, or something else), the concrete thing it will deliver, and what will prove it. A mission without all three is refused; there's no "we'll figure out the goal later". There's no draft and nothing for you to approve before work starts: the finish line you agreed with the session in chat is the agreement, and the mission starts **active**. The session declares its plan in the same call — one step per deliverable — and Harnu adds a fixed last step, "Delivered and verified". The session can also attach the documents that fix the scope — the spec, the PRD, an ADR, as paths inside the repo. Scope is an attachment, not a step: it never counts toward progress, and Harnu just reports whether each document exists. A document that hasn't been written yet (or that lives on a branch for now) is attached anyway; a path pointing outside the repo — including through a symlink, even one whose target doesn't exist yet — the whole repo itself, Git's and Harnu's own folders (`.git`, `.harnu`, `.capy`, at any depth) or a worktree checkout (a linked worktree, a nested clone, or anything under `.claude/worktrees` — a folder Harnu isn't allowed to look into is treated as one) are refused, and the mission isn't created. Harnu stores each document under the path it actually points to, so what's recorded is exactly what was checked. The same rules apply when a session attaches another scope document later. Harnu re-checks this every time it reads the mission, so if one of those documents is later replaced by a link to somewhere outside the repo — or turns into anything else refused here, such as a new git checkout — it reads as unresolved again. Missions created before this change keep their old "Scope confirmed" first step on disk; Harnu treats that step's documents as scope and leaves the step out of the count — in what sessions read and in the topbar alike.
- **Add a step** (`mission_add_step`) before the final one. Each step says how it will be proven: Harnu checking that something exists, another session verifying it, or you confirming it yourself — and it can come with its links already attached. While the session is still planning, it can add steps freely. Once work has started (any step has a session, path, card or PR linked, or a proof), a session can't quietly grow the mission — every new step needs a written reason, which stays on the mission.
- **Update a step** (`mission_update_step`): rename one it added, or mark it "claimed" — "I believe this is done, but nobody has verified it yet". A session can never mark a step verified by saying so; that field is off limits to this action.
- **Link a step to the work behind it** (`mission_link_child`): a session, a path (a worktree, or any file or folder in the repo), a roadmap card, or a pull request. The same verb attaches a scope document to the mission itself. Linking the sessions it dispatched also keeps the coordinating session from being parked by hibernation while those sessions are still running (see "Parked and hibernated sessions" below).
- **Ask for your sign-off on a step** (`mission_add_check`). Some work is only done once a person has looked at it — a design check, "validated visually", a designer's sign-off. A session records that as a **check** on the step that produced the work, instead of inventing a separate step for it. A verifying session that finds everything met except the part only a human can judge does the same: the step counts as done and the human part becomes a check. Only you can tick a check off or delete one — no session can — and checks never change where the mission stands. An unticked check on work that's been reached is listed as something waiting on you, and you tick, untick or delete it right on its step in the progress popover (see below).
- **Write in the mission's log** (`mission_log`): a timestamped note — a report a helper sent back, a decision it made. The log is a narrative for humans; it never changes the mission's actual state.
- **Read a mission** (`mission_get`) or **list them** (`mission_list`). Reading one always includes what the mission needs from you, as an ordered list — a new finish line to approve, a close to make, a blocker that's yours, checks waiting for your tick, a step that's yours to confirm, an imported finish line to review, a linked session waiting on an approval or a question — or "nothing, you're clear". It also says where the work is, computed once by Harnu on its side, so every session that reads a mission — and the topbar pill, the popover and the sidebar — get the same numbers: which step it's on ("Step 8 of 9", or a range when several run at once), how many steps are done and how many of those were independently verified, which steps were skipped and left behind, and which ones can never be proven automatically because nothing they could be checked against is linked. Each read also works out, fresh, how the linked work is doing: whether each linked session is working, idle or parked, what's on each linked worktree (its branch, latest commit and pull requests), where each linked card sits on the board, which branch each linked pull request merges into, and whether a step that Harnu checks automatically is actually proven. It also says whether asking you to close the mission would be accepted right now — and if not, why (final step not verified, something blocked, or a new finish line waiting for you). Pull-request details need the GitHub CLI (`gh`); without it that part is simply left empty. Proof doesn't flicker with GitHub: once a linked pull request has been seen open or merged, a read that can't reach GitHub (or no longer finds that pull request among the recent ones) keeps the last known state and marks it as not re-checked, instead of un-proving the step. Likewise, a worktree that was cleaned up after its pull request merged still counts. Only a real change — a pull request closed without merging, a card moved back — takes the proof away.
- **Notice a stalled mission.** If a running mission has had no new activity for over an hour and none of its linked sessions is working, reading it flags it as **stalled** — something probably needs a look (a stuck helper, a report that never arrived). The flag is worked out fresh on every read and never changes the mission itself, so any new activity clears it on its own. This is a fixed rule, not a model's judgment.
- **Flag a blocker** (`mission_set_blocker`) on the whole mission or on one step, and **clear it** again (`mission_clear_blocker`). Each blocker says why the work is stuck, what would unstick it, and whose move it is — the session's or yours. One that's waiting on you shows up in the "what this needs from you" line. A blocker is just a flag: it doesn't change the mission's status.
- **Propose a new finish line** (`mission_set_end`) when the goal genuinely changes. The session has to give a reason, and the change doesn't take effect on its own: it waits for your approval, with the old and new goal side by side in the mission's log. Once you approve it, the final "Delivered and verified" step goes back to unproven — whatever proof it had was about the old goal.
- **Verify a step** (`mission_verify_step`) — the "another session verifies it" kind. This never fails; instead it labels the result honestly. If the verifying session is not one of the sessions linked to the step as having built it, the step counts as **verified**. If it is one of them — or nobody was linked at all — it counts as **self-verified**, which Harnu never treats as proven. The final "Delivered and verified" step is built by the whole mission, so the sessions linked to any step count as its builders: once each piece of work has its session linked, the coordinating session — which built none of them — can verify the final step and it counts as **verified**. If no step has a linked session, the final step stays self-verified and the mission can't be closed. Harnu can't confirm which session is really calling (sessions identify themselves), so this relies on sessions being honest, with a record of who claimed what for you to check. Steps you confirm yourself and steps Harnu checks automatically can't be verified this way.
- **Bring an old goal file over** (`mission_import_legacy`). Before Missions existed, coordinating sessions kept their state in free-form notes files under `.harnu/goals/`. A session can turn one of those into a new mission instead of starting from scratch: it picks out what it recognizes — the goal, what "done" looks like, the helpers or units listed, pending gates, open questions and the log — and keeps a byte-for-byte copy of the whole original file inside the mission, so nothing is lost even when the file used headings Harnu doesn't know. The old file itself is only read: never changed, moved or deleted. When the file didn't clearly say what "done" means, the mission's finish line is marked **needs review** with a placeholder — the mission tells you it's waiting on you to review it — and the session should propose a real one for you to approve. The same file can't be imported twice, and files that aren't plain UTF-8 text (or are over 1 MB) are refused rather than copied imperfectly.
- **Ask you to close the mission** (`mission_request_close`). Only possible once the final step is verified by a session that built none of the steps — self-verified doesn't count — nothing is blocked, and no new finish line is waiting for your approval. The mission is then marked delivered and waits for you.

These decisions stay yours, and no session can make any of them: **approving a new finish line**, **confirming a step** that's marked as yours to confirm, **ticking or deleting a check**, and **ending** a mission — closing it as delivered, or discarding it. You can end any mission that isn't closed yet, whenever you like; open matters (a finish line nobody verified, steps left behind, unticked checks, blockers, a pending new finish line) are shown as warnings, never as a reason you can't. Every one of these lands in the mission's log, so the session that owns it sees what you did; once a mission is closed, its session can no longer change it. Where you see and do all this:

- **The topbar pill.** When the session you have selected owns a mission, a small pill sits next to its title saying where the work is: **Step 8 of 9** — the step the work is on now, not a count of finished steps. When several steps run at once it reads **Steps 4–7 of 9**, and only when every step is done does it read **Step 9 of 9 ✓**. These are the same numbers every session reads; nothing in the topbar counts on its own. An older mission's "Scope confirmed" step isn't counted. Its color is a quick "worth a glance?": blue while it's moving, amber when something's blocked, stalled, waiting on you (including checks due for your tick) or proposing a new finish line, green once it's delivered. A session with no mission shows nothing; a mission with no steps yet shows the pill's icon alone.
- **The popover.** Click the pill. The header repeats the headline and adds the counts — "6 done · 6 verified", plus "· 1 left behind" when a step was skipped — and the documents that fix the scope, each marked "on a branch" when it isn't on this checkout. Every step is listed with one of seven marks: a filled green check (verified), a hollow check (done, not verified yet), a pulsing dot (running), a half-filled circle (waiting — a helper finished or paused, nobody has graded it yet), a warning triangle (blocked), an empty circle (still to do) and an amber return arrow (left behind — skipped while later steps moved on). Hover a mark to read its name. The step the headline names is highlighted. Steps also show how they'll be proven and badges for "claimed" (a session says it's done, nobody has verified it — a step a session verified on its own work shows the same way, never as proven), "proven", "added" (with the reason it was added after the mission started) and "re-scope pending". Blockers, a stall ("no evidence in 2h 15m") and the proposed new finish line (old and new side by side) appear right under the step they belong to. The final step always shows the finish line — what will be delivered and what proves it.
- **Helper sessions.** A session linked to the mission appears once: on the step it's running, or else the last step it's linked to. Other steps it touches show "+1 session". The go-to button at the end of its row opens that session inside Harnu; if the sidebar hasn't loaded it yet, Harnu tells you so instead of doing nothing.
- **Checks.** A step's checks are listed under it with a checkbox. Once the step has been reached, an unticked check is marked **due** — and it counts as something the mission needs from you. Tick or untick it with the checkbox, delete it with the × that appears on hover, or add one with **+ check** (shown on the current step, and on any step when you hover it): type what to check and press Enter. A label the step already has, in any capitalization, isn't added twice. Checks never move the headline.
- **The You line.** At the bottom, it says the first thing the mission needs from you — a new finish line to approve (with **Approve re-scope**), a close to make (with **Close mission**), a blocker that's yours, checks to tick, a step to confirm, an imported finish line to review, a helper waiting on an approval or a question — and "+N more" opens the rest. With nothing owed it reads "Nothing — you're clear." A step that's yours to confirm also shows **Mark verified** (and **Unmark** if you change your mind) on the step itself.
- **Ending a mission.** **End mission…** is always at the bottom of the popover, and **Close mission** on the You line opens the same dialog. Choose **Close as delivered** or **Discard** (for a mission that's dead, duplicated or abandoned), and optionally write a reason — it goes to the mission's log. Anything still open is listed as a warning, counted where it can be — "The end is not verified", "2 steps left behind", "1 check not ticked", "1 blocker still open", "A re-scope is staged" — with the steps (and check labels) it concerns named under each, but you can always go ahead. Opening the dialog plays a sound and nudges your taskbar or dock, because an ended mission can't be reopened; Cancel, Esc or a click outside keeps it. Once Harnu confirms, the mission leaves the topbar and the sidebar at once — you don't wait for the next refresh — and its file stays on disk as the record. If something goes wrong, the dialog closes and a message tells you why. There is no "Approve mission": missions start active, because the finish line you agreed in chat is the agreement.
- **The sidebar.** The session's row carries the same headline in short form at its right edge — **8/9**, **4–7/9**, or **9/9 ✓** — in the same color as the pill. It's shown on hover normally, and stays visible with a warning mark while the mission needs something from you.
- **A sound when a mission starts needing more from you.** When a mission begins needing something only you can give — a blocker that's yours (a merge, a key, a decision), a new finish line to approve, a close to make, checks due for your tick, a step to confirm, an imported finish line to review — Harnu plays the confirm chime, asks for your attention (taskbar flash / dock bounce) and adds one entry to the Activity bell; clicking it opens the session that owns the mission. It rings when something new appears or a count grows (one due check becoming two), and never when you tick something off or a count goes down. If the mission is still waiting 30 minutes later, you get the same reminder again, every 30 minutes until nothing is owed. When you open Harnu with several missions already waiting, you get one combined reminder ("2 missions need you"), not one per mission. Pending approvals and a session waiting on your answer are left out here — the Approval Inbox and the session's own notification already ring for those. An old draft that went quiet never rings: it shows as stalled, not as waiting on you. Harnu checks missions every 20 seconds, so a blocker raised and cleared within that window never reaches you. Like the safety confirms, this reminder sounds even when session notification sounds are switched off in Settings, and the 30-minute interval is fixed.

## Batching approvals (only matters if you turned confirmations on)

With "Ask before agent actions" on, approving every action one at a time gets tedious when a session is doing a lot of related work at once — say, setting up three worktrees for three tasks. Instead of asking three separate times, a session can request one **mission grant**: a single approval that names a goal, the folders and specific actions it covers, a budget (how many actions), and a time limit. Say yes once, and everything within that scope runs on its own until the budget or the clock runs out; anything outside the scope still asks you individually. You can see any live grant's remaining budget and time in the Approval Inbox, and revoke it early if you change your mind. A grant can never reach into a folder you blocked.

Separately, when you approve an individual action, you'll sometimes see an **"always allow this verb here"** checkbox — checking it means that specific kind of action never asks again in that folder, persisted across restarts, independent of any grant.

With confirmations off (the default), none of this comes up — actions simply run, and mission grants are redundant.

## Getting from a card to a running session

A session can freely draft and reorganize roadmap cards, but actually dispatching a batch of them as real running sessions still needs one extra, deliberate step: a session has to submit a **manifest** — a named, ordered list of exactly which ready cards it wants to run and where. Moving cards to Ready is your consent to have them run; the manifest is what turns that standing consent into an actual batch of running machines, so it's a door a session opens on purpose, not something it stumbles into.

With "Ask before agent actions" off (the default) and the folder not blocked, submitting a manifest dispatches it right away — no confirmation, and no per-card unchecking, since there's no prompt to uncheck anything from. Harnu still marks the moment: a note lands in the audit log naming the folder and every card in the batch, and you get a notification the instant it happens, so a batch that self-approved while you were away is still something you can see after the fact, not something that just silently ran.

If you turn "Ask before agent actions" on, submitting a manifest goes back to showing up in your Approval Inbox as an explicit checklist — listing each card's title, its readiness, and the exact prompt it would boot with. You can approve the whole batch, or uncheck individual cards to leave them alone; only your Allow marks the checked cards as cleared to run, and those additionally need a live mission grant to auto-dispatch (otherwise each one waits for you to click Dispatch on the board).

Either way, once a card is marked cleared to run it dispatches itself in the declared order. If a card was edited after being cleared, its approval is void and it always waits for a per-card Dispatch click — the toast names the card and the reason.

Which model and effort level a card actually launches with is controlled by a routing table you configure yourself (per card kind — scout, bug, feature, chore, review) in a folder's launch settings, not by whatever the session suggests when it drafts the card — a session's suggestion is shown to you as a hint, but the table decides.

## Creating a Scheduler worker

A session can mint a [Scheduler worker](scheduler.md) — the one thing that keeps running on its own cadence after the session that made it is gone. This matters most for a session that's coordinating other work: it's the backstop that keeps checking in even if the coordinating session itself ends, instead of that heartbeat only existing when you remember to build one by hand.

**An `observe` worker is created the same way as everything else in this section — directly, no asking.** It's read-only by an explicit allowlist (the same one described in [the Scheduler doc](scheduler.md#observe-vs-act--read-this-before-you-flip-the-switch)), so an unattended one is no more consequential than a session starting another session.

**An `act` worker is different, and always stops to ask you first — one of the few exceptions to "acts freely" in this whole document.** An `act` worker runs with permissions bypassed and doesn't stop at the Approval Inbox, which means minting one unattended would be the session handing itself a second, permanently unsupervised body. So no matter what "Ask before agent actions" is set to, creating one shows up as a confirmation naming the folder, the cadence, and the exact prompt it would run — the same standing as a mission grant or deleting a card.

Either way, a worker made by a session arrives already switched on — unlike the Scheduler's own New worker button, which leaves a fresh worker off until you fill in the form and arm it yourself. If the session's prompt names a skill that resolves to nothing on this machine, it's told so in its own result rather than getting back a worker that will quietly never stage it. Naming a bundled skill that's merely switched off for the folder is not this case — it stages anyway, the same as in a Scheduler tick.

A session can also **list the workers that already exist**, either everywhere or just in one folder, so it can check whether the heartbeat it needs is already running before minting a second one. It gets back each worker's name, folder, cadence, mode, whether it's switched on, and how its last run ended — the same summary you'd read off the Scheduler list yourself, with folder paths shortened the same way the fleet view shortens them. Reading the list is never something you're asked about.

A worker a session creates starts at the **Silent** notify setting, exactly like one you create by hand — so a session can't quietly sign you up for a notification on every tick. If you want to hear about its runs, you turn that up yourself in the Scheduler.

**A session can also fix a worker it already made, or remove one.** Minting a worker used to be one-way: if the prompt had a mistake, or the operator flipped it to `act` and the prompt still said "don't modify anything," the only fix was to hand you a corrected string and ask you to retype it into the Scheduler yourself. Now a session can edit any subset of an existing worker's fields directly — name, prompt, cadence, mode, model, effort, timeout, whether it's on, and a few more — by referring to the worker's id (from when it created it, or from the listing above). That edit runs freely, the same as creating an `observe` worker, **unless the edit itself raises the risk**: flipping the worker to `act`, or touching either of its prompts at all — the instructions it runs, or the system prompt behind them. The prompt rule is deliberately unconditional and covers both, because both are the body the worker runs unattended — a session editing a worker's prompt can't tell you whether that worker is currently `observe` or `act` without asking, so any prompt edit stops to confirm with you, the same standing as minting an `act` worker in the first place. An edit never reaches a tick that's already running; it only takes effect from the next one.

**Deleting a worker is different, and always asks you.** Unlike editing, permanently removing a worker — its definition and its run history, and stopping a live tick if one is running — always shows up as a confirmation, no matter how "Ask before agent actions" is set: there's no undo, the same standing as permanently deleting a roadmap card. Pausing it instead (asking a session to disable it, rather than delete it) is the reversible alternative if you might want it back.

**A session can also mint a worker with a longer timeout from the start.** A tick whose own instructions chain several slow steps together — spinning up a worktree, installing dependencies, starting another session — can need more than the built-in 5-minute limit, and a session can now say so when it creates the worker instead of you having to raise it by hand afterward.

## Promoting a session to orchestrator

You can promote any session to an **Orchestrator** role (from its right-click menu). This is the deliberate gesture that gives a session its coordinator framing from the moment it starts: it arms a guard that stops that session from editing files directly outside its own notes, and shifts its focus to planning and delegating — spinning up other sessions and worktrees to do the actual work rather than doing it itself. A promoted session is visibly marked with a badge and a topbar pill so it's obvious when a session is meant to be coordinating rather than coding. The guard itself isn't exclusively yours to grant, though — see below.

Promotion is really two things bundled together: a note added to the session's own instructions when it starts (which only ever happens at the moment you launch it, or when a skill boots it straight into the role), and a live guard that blocks it from editing files directly. That second half doesn't have to wait for you — any session Harnu spawned for agent work can arm it for **itself**, mid-conversation, the moment it realizes it should be coordinating rather than coding. When that happens you'll see the exact same badge and topbar pill appear, with no click from you. It can also arm or disarm that guard on **another** session — any session Harnu spawned for agent work, not only one it personally dispatched — but never a session you opened by hand yourself; and a session you opened by hand can't arm the guard on itself either, only an agent-spawned session can. Think of it as the session pulling its own emergency brake, not as it granting itself a new role behind your back: the guard only ever adds friction to what that session can do: it fails safe, so if anything about the arming goes wrong the session just behaves like an ordinary one, never a broken one.

**Making a whole folder default to Orchestrator.** If you find yourself promoting every new session in the same repo by hand, the folder's right-click menu has a toggle for that: **"New sessions start as Orchestrator"** (off by default). Turn it on and every plain session you start there afterwards — "+ New session", the New session dialog, the keyboard shortcut — is born already promoted, badge and all, from its very first turn. The folder row gets a small crown to remind you the default is on.

This toggle belongs to that **one exact folder**, never its worktrees — turning it on for a repo does not turn it on for the worktrees you cut off it. That's deliberate: an Orchestrator's whole job is dispatching _executor_ sessions into those worktrees to do the actual editing, and an executor born with the same guard armed would be blocked from writing the code it was sent there to write. For the same reason, a session an agent starts on its own — through the MCP tools, a board dispatch, a Scheduler tick, or a read-only review companion — is never armed by this default, no matter how the toggle is set; it only ever applies to a session **you** started by hand.

Turning the toggle on or off never reaches back into sessions that already exist — it only decides what a _future_ "+ New session" click does. And a session the default did arm keeps its role through being parked and resumed later; only an explicit demote (turning the role off from that session's own menu) ever takes it away for good.

## Parked and hibernated sessions

If a session goes idle for a while, Harnu may kill its underlying process to free up memory — but this doesn't lose anything, and it isn't the same as a session getting stuck. Clicking the session resumes it exactly where it left off. If you're watching your fleet through the tools above (or a session is), a quiet or "parked" session should be read as dormant, not failed.

**A message can wake a parked session.** If one session messages another that Harnu has parked, Harnu brings it back first and then delivers — the same resume you'd get by clicking it, except it happens in the background and never moves your view to it. Harnu keeps a record of that: the wake is logged as agent-driven rather than as one of your clicks, so "who woke this session" stays answerable. If the resume takes too long, the message is **not** sent and the sending session is told so — Harnu never quietly drops it, and never starts a second process to force the delivery.

## Sessions talking to each other

Claude Code has its own cross-session inbox — one session can send another a message, and the message waits until the recipient finishes what it's doing rather than interrupting it. Harnu adds a door onto that: a session can call `message_session` with another Harnu session's id, and Harnu figures out which actual process that is and delivers the message.

**Why bother, when the sessions could already do this themselves?** Two reasons, and they're the honest limits too. Harnu knows _exactly_ which process a session id maps to, so there's no name-guessing; and every message sent **through Harnu** lands in the audit log and posts a row in your Activity history, so you can see it. What Harnu cannot do is see traffic that doesn't go through it — sessions can reach each other directly, with or without Harnu, and nothing in Harnu can close that. Harnu is one recorded door, not the only door.

**Who a session can message.** Only sessions Harnu started _for an agent_ — one a session launched itself, or one dispatched from the board — and only in a folder you haven't blocked. Everything else is refused: a session **you** opened in Harnu, a `claude` you're running in your own terminal, a teammate pane, and an old transcript with nothing running. The refusal names the reason — `RECIPIENT_NOT_HARNU_SPAWNED` when Harnu holds no process for that session, `RECIPIENT_OPERATOR_OWNED` when it is one you opened yourself. (Before the Harnu rename the first code was spelled with `CAPY` in place of `HARNU`; the spelling was changed with no alias, because it is a status code an agent reads, not a saved setting.) So an agent can't put words in front of you in your own session; if it needs your attention it has to use the Activity notice instead, which waits for you to read it rather than landing in a live turn.

**What the sender is told.** That the message was _queued_ — not that it was read, agreed to, or acted on. Harnu has no way to hear back what the recipient did with it, and it says so rather than implying more. Every refusal is specific enough for the sending session to know what to do next instead of retrying blindly.

**One thing worth knowing.** Claude Code itself treats an incoming message from another session as _input_, never as your approval — it's explicitly told that relaying an action it was refused permission for is not a workaround. Harnu is careful not to weaken that: it never claims a permission level on the sender's behalf, which is what would let a message slip past the recipient's own check. But Harnu sees text, not intent. Logging a message makes it attributable, not harmless.

## A session whose starting prompt never arrived

When a session is started with a message already queued up for it (a starting prompt from `create_session`, or a card's boot prompt), Harnu normally waits until the session's chat composer is genuinely ready before typing it in — pasting too early risked the message landing somewhere other than the chat, like a first-run "do you trust this folder?" prompt. If that ready signal never arrives, Harnu no longer guesses: it holds the message back rather than risk it landing in the wrong place, and marks the session failed with "prompt not delivered" instead of leaving it sitting there silently. This also means a session checking on its own dispatch (or another session checking on it) can now actually see that something went wrong, rather than being told the session is still `active` indefinitely. A healthy session is unaffected by this — it still gets its message immediately, with no extra wait.
