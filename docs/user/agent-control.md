# Agent control

Harnu runs a small MCP (Model Context Protocol) server that a Claude session can talk to from inside its own conversation. In plain terms: a session isn't limited to just editing files and running shell commands in its own folder anymore — it can also reach out and act on Harnu itself, like spinning up another session, creating a worktree for a task, checking on the rest of your fleet, or reading and writing your project's shared notes.

## Agents act freely by default

**The server is on out of the box, agents can act in every folder, and their actions do not stop to ask you.** A session that decides to create a worktree and start another session in it just does it — no per-folder switch to flip first, no Allow/Deny prompt in between.

This is a deliberate reversal of how Harnu used to work. Before, every folder was fail-closed and every state-changing action stopped at a confirmation. In practice that meant a session would create a session, get an id back, and then be refused when it tried to check on it — and your machine sat idle until you came back and flipped a switch by hand. The friction was buying very little: you had already decided to point Harnu at that folder, and a session can pin folders on its own anyway.

Everything a session does is still written to the **audit log** (Settings → Control server), which is now your main record of what ran while you weren't watching.

### The three ways to say no

1. **Ask before agent actions** (Settings → Control server, off by default). Turn it on and every state-changing action goes back to asking you first, in every folder. This is the old behavior, one toggle away.
2. **Block a folder.** Right-click a folder → **Block agent control**. Agents are refused in that folder _and everything under it_ (so blocking a repo blocks its worktrees too). This refusal is absolute — no mission grant or "always allow" can reach into a blocked folder. A blocked folder shows a small crossed-out-bot marker in the sidebar. The same on/off switches are listed in Settings → Control server.
3. **Turn the server off.** The master switch in Settings → Control server. Nothing gets through, not even reads.

If a session tells you it was refused, it hit #2 or #3 — those are the only things that can stop it.

**Turning the server off and back on doesn't break sessions that were already running.** The credential a session uses to reach Harnu is stored on disk and reused across restarts, so a session that was working before you toggled the server keeps working after — no need to resume it just because you flipped the switch. The one thing that can still leave a session stranded is if Harnu has to bind a different network port on that restart (rare — it only happens if the port it used before got taken by something else in the meantime); in that case a session spawned before the restart can't reach the server anymore and does need to be resumed to reconnect.

**The server's name is `harnu`.** Inside a session, its tools show up as `mcp__harnu__<verb>` (for example `mcp__harnu__create_session`), and its resources use `harnu://` addresses. If you wire the server into your own `claude` config by hand, **Settings → Control server → Copy config** gives you a snippet that registers it under the `harnu` key. Older notes, memory files and scripts may still say `mcp__capy__<verb>` or `capy://`; the rename changes the label, not what a verb does. Harnu still understands the old resource address, and you don't have to touch anything you've already set up.

**Your saved "always allow" choices keep working.** A rule you saved earlier, such as `mcp__capy__create_session` in a folder's `.claude/settings.local.json`, still lets that verb run without asking, so nothing re-prompts after the rename. New "always allow" choices are saved under the new `mcp__harnu__` name. Scheduler workers in read-only mode stay as locked down as before: the list of verbs they may and may not call covers both names.

## What a session can actually do

**Look.** A session can check on the rest of your fleet — which sessions exist, what they're doing, whether they need you — list your git worktrees, list the Docker containers your projects left running (see "Watching Docker containers" below), and read your project's shared memory (see [Project memory](project-memory.md)). A session it just started shows up in that same check immediately, even before the new session has actually written anything to disk — it's marked as still-starting rather than being invisible until it catches up, so a session checking its own work doesn't have to guess whether "no result yet" means "starting up" or "never happened."

**Act.** Without stopping to ask (unless you turned on "Ask before agent actions"), a session can:

- Start a new session in a folder, optionally with a starting prompt
- Create a git worktree for a task (seeded from the repo's `WORKTREE.md`, same as if you'd made it by hand — see [Folders and worktrees](folders-and-worktrees.md)). By default the new branch forks from the remote default branch, but a session can name an explicit base branch to **stack one task's worktree on top of another** — e.g. a dependent PR that needs to build on a branch that hasn't merged yet. Naming a base that doesn't actually exist is refused outright rather than quietly falling back to the default. If a branch or worktree already exists whose name looks like it's for the same task (e.g. a stale attempt from an earlier dispatch), the session is told so — a warning, not a refusal, since starting fresh is sometimes exactly right, but it gives the session a chance to notice duplicate work before spawning a second one. If the repo's setup step fails instead (a missing tool, a failing command), the half-made worktree and its branch are always cleaned up automatically — and, whether it's a session or you creating it, the error now says exactly what failed, whether the tool was simply missing or actually ran and errored, and confirms the cleanup happened, instead of a bare, hard-to-read error line.
- Spawn a plain shell in a folder — see "Terminals a session opens" below
- Pin an existing folder into your sidebar
- Clean up a "ghost" folder — one whose directory is already gone but whose entry (and its now-broken session) still lingers in your sidebar
- Write an entry to project memory (a decision, a session summary, or a refreshed "where we left off" note)
- Open a file — a report, a draft, a snippet, an image — in a read-only viewer pane inside Harnu, so it can hand you something to look at without you leaving the app. Sessions are told to use this for anything you'd want to **copy or keep** (a drafted message, a PR description, a config, a longer code snippet) instead of printing it into the terminal, where it scrolls away and is awkward to select. The pane has a copy button on every code block and a "Copy file" action for the whole file, so the handoff is one click. Conversation — explanations, answers, status — still stays in the terminal where it belongs
- Post a short notice into your Activity history that any session's window can see — see "Session says" below
- Write a guided walk for you — a list of things to check by hand, saved in Harnu — see "Guided walks" below
- Say one short line out loud through your speakers, if you've turned voice on — see "Sessions talking out loud" below
- Draw on a canvas — an infinite whiteboard that opens in a pane beside the session and that you can edit back. See "Drawing on a canvas" below
- Send a message to another Harnu session — see "Sessions talking to each other" below
- Open a browser pane on your dev server or a site, navigate it, read what is on the page, click, type, fill forms and run scripts in it, list and close its panes — see "Browser panes a session opens" below
- Create a Scheduler worker in `observe` mode — see "Creating a Scheduler worker" below
- Keep track of a larger piece of work as a **Mission** — see "Tracking a mission's progress" below

**Starting a session means it actually started.** When a session asks Harnu to launch a new session, Harnu waits (up to about a minute) to confirm a real process came up and wrote its transcript before telling the requesting session "done" — it no longer reports success the instant it accepted the request. If a launch doesn't come up in that time, the requesting session is told so plainly (and if that action was covered by a mission grant, the budget it spent gets handed back, since Harnu can't yet confirm anything happened) — but the new session itself is left running rather than killed, since a launch that's merely slow can still land a few minutes later, and Harnu has seen that tail run as long as ~14 minutes. The requesting session is told the new session's id so it can check on it directly instead of guessing. Harnu also refuses a second launch into a folder that already has one in progress — including one that's still catching up after a slow-launch report like this — rather than risking two sessions racing in the same folder; that refusal clears on its own once the slow one is confirmed running (or is given up on after sitting unconfirmed for about an hour).

**A pane always opens in the session's OWN folder — never wherever you happen to be looking.** If you're viewing a different folder when the pane lands, that folder's row gets a small accent pill in the sidebar (distinct from the green/amber/red session dots) counting what's waiting, and Harnu pops a native notification — clicking it jumps straight to that folder's most recently active session. Open the folder yourself and the pill clears. A folder Harnu doesn't actually track (an unrecognized path) never gets a phantom pane — the session is told the folder didn't resolve instead.

**Organize the roadmap board directly.** A session can create, edit, and move cards on your [roadmap board](roadmap-board.md) — the same way it can append to project memory. Editing covers both a quick note appended to a card and a full rewrite of its whole spec, the same full-replace a card's Edit button gives you in the app. A session can also set a card's PRD and ADR doc paths, alongside its spec — the board uses these to show per-artifact badges (a green check when a required doc is there, an amber warning when it's expected but missing) instead of one anonymous "gaps" count. What a session can never do on the board is close a card (that's always your call) or actually launch work against one without a further step — see "Getting from a card to a running session" below.

A session can also attach a pasted screenshot to a card it's creating or editing — the same image you'd see in the footer's pasted-images gallery. It hands over the image's path, and Harnu copies the bytes into the board's own storage and drops the picture into the card's body, so you never have to describe a bug in words when a screenshot already shows it.

A session can also archive or delete a card. Archiving is treated the same as every other board organizing action above — it happens directly, no asking — because it's reversible: the card just moves off the board, the same as the app's own Archive button, and you (or the session) can bring it back. Deleting is different: unlike everything else a session can do to the board, it always stops to ask you first, since there's no undo once the file is gone. Either one is refused outright while the card is In progress — a session has to move it to Review first.

**Cleaning up ghost folders — sidebar bookkeeping only, never disk.** If a folder's directory gets deleted — by Reaper's sweep, by a manual worktree removal, or by something outside Harnu entirely (an `rm -rf` you ran yourself) — but Harnu's sidebar hasn't caught up yet, a session can reconcile it directly: it un-pins the folder and drops it (and its sessions) from the sidebar, no restart needed. This ONLY ever touches Harnu's own bookkeeping — it's refused outright if the directory is actually still there, so it can never be used to hide a folder whose data is still real and reachable. There's still no way for a session to delete a worktree, branch, or file on disk; that stays something only you (or Reaper, which you configure) does.

**"Session says" — a notice from any session, without switching tabs.** A session can post a short notice ("Session says") into the same Activity history the [Activity bell](approval-inbox.md#activity-bell) already keeps — visible from whichever window you're actually looking at, not just the one that sent it. It's meant for something worth a heads-up (a finding, a progress update) that doesn't need your Allow/Deny. The notice stays in the bell's list until you clear it — clicking it (or its **Go to session** action, when the sending session included its own id) jumps you straight there and removes it; hovering it lets you dismiss it without navigating anywhere. Either way, it's always your call — nothing switches on its own.

## Terminals a session opens

When a session spawns a shell in a folder, the shell now starts immediately — even if you aren't looking at that folder — and the session gets a `terminalId` it can use to refer to it again. The session can also say which session the terminal belongs to (its own); that is a label for you and for the audit trail, not a permission.

A session can list every terminal Harnu knows about: who opened it (the agent or you), which session it belongs to, whether it is still running or has exited, and its size. Folder paths are shortened to the folder's name, and a terminal in a folder you blocked is left out. An exited terminal stays in the list for ten minutes. The title a program sets on its terminal is shown to the session as program text it shouldn't trust. A session's own details also list the terminals it owns.

Because the shell belongs to Harnu and not to the pane, nothing is lost when you look away or reload. If you open the folder later, the pane picks up the shell that is already running, with everything it printed so far. If you reload the window, the terminals a session opened keep running and their panes come back by themselves. Closing the pane ends the shell, even if you never opened the pane. A shell that exits on its own after a couple of seconds closes its pane; one that exits right away stays in the stack, showing what it printed and a "Process exited" line, until you remove it or reload the window (a reload only brings back terminals that are still running). These panes are not saved when you quit Harnu — after a restart they are gone, along with their shells.

A few limits keep this from running away: a folder holds at most four live agent terminals (a fifth is refused until one is closed), and opening two terminals in a row really opens two.

A session can now **read** a terminal it opened. What it gets is the screen as you would see it, not the raw stream: a progress bar that redraws on one line comes back as its final state, colours are plain text, and a line the terminal wrapped is one line. It can ask for the last few lines, only what is on screen right now (the right choice for a prompt, `vim` or `htop`), or everything since a point it noted earlier — so it can run something, come back, and read just what is new. Harnu keeps the last 2,000 lines of each terminal for this. A read never types anything.

**Terminals you open yourself are private until you say otherwise.** Right-click a folder in the sidebar and choose **"Let agents read terminals I open"** to let sessions read the shell panes you open in that folder (the entry then reads **"Stop agents reading terminals I open"**, which closes the door again at once). It is off by default and it applies to that exact folder only — a worktree of an opted-in repo is _not_ opted in; give it its own switch if you want it. Until you turn it on, a session that tries gets a refusal that tells it to ask you, and the terminal still appears in its list, marked as not readable, so it can say so instead of guessing. The switch is about looking only; it says nothing about typing. Terminals a session opened itself never need it. If a terminal in that folder was already running with a lot of output before the first read, the first reads may miss the oldest lines and say so (`approximate`).

**What a session sees is scrubbed.** Before any terminal text reaches a session — the screen and the terminal's title, on your terminals and on the ones the session opened — Harnu replaces your home folder with `~` and hides AWS key ids, `Bearer` tokens and `Authorization` values, secret-looking `NAME=value` pairs and private-key blocks as `<redacted>`. That is a best-effort filter, not a security boundary: a secret in a shape it doesn't know gets through, and something that merely looks like a secret is hidden even if the session printed it itself. Don't rely on it to make it safe to show a session a terminal you wouldn't otherwise show it. Read-only scheduled workers can list and read terminals under the same rules.

Two things to keep in mind when you opt a folder in. A `claude` session you run _inside_ one of those shells is just a terminal as far as Harnu is concerned, so an agent that can read the shell can read that session's screen too. And the scrubbing works on what is on screen at the moment of the read, so a secret the read window cuts in half — the middle of a private-key block, say — is not recognised and can come through. A terminal you haven't opted in still appears in the list, but without its title, when it last printed, or its exit code, since those would show what you are doing in it.

While a terminal is open but you haven't looked at it, Harnu answers the questions programs like `nvim` and `fzf` ask their terminal ("where is the cursor?", "what are you?") so they don't freeze waiting. Once you open the pane, the pane answers instead — never both. If the window reloads or crashes, Harnu takes over answering until a pane picks the terminal up again. A program that prints a flood of output is slowed down rather than allowed to starve the app.

**Typing into a terminal.** A session can now type into a terminal it opened itself: text, plus named keys such as Enter, Tab, Esc, the arrows, `Ctrl+C` (interrupt) and `Ctrl+D` (end of input). It then gets back what the screen shows from that point, scrubbed like every terminal read. A scheduled read-only worker can never type at all. Typing into a terminal _you_ opened needs your say-so, described just below.

A session can also ask to **wait for the result** instead of taking a snapshot a split second after typing: it names text it expects the program to print (for example `passed|failed` after `npm test`), a quiet period, or a time limit, and gets back everything printed since the send as soon as the first of those happens, or when the terminal ends or you disconnect it. The text it waits for is matched against what the program prints, Harnu skips the shell's echo of what the session typed (even with a right-hand prompt or an autosuggestion on that line), so typing `grep failed log` doesn't count as having seen "failed". If something the session waits for looks like a secret, what it gets back for the matched text is hidden the same way the rest of the output is. A wait never lasts longer than the limit it set (at most 90 seconds, 15 seconds if it names none), and running out of time isn't an error; it just gets what is on screen so far. Waiting for text is bounded too: a pattern that is too long, doesn't parse or would match nothing at all is refused before anything is typed, and one that takes too long to evaluate is switched off for that call.

A few things keep this orderly. Every send goes to the terminal as one piece, so your own typing can't land in the middle of it (the one exception is `Esc` followed by more input, which goes out as two pieces a split second apart). Sends to one terminal run one at a time; a send that has to wait more than ten seconds behind others gives up without typing anything, and a terminal accepts at most 60 sends a minute. The session is told whether you typed in the pane while its call was running, and whether another session wrote to the same terminal, so it knows the screen may not show only what it sent. Input with hidden control characters, absurdly long lines and unknown key names are refused straight away, before any approval prompt. Each send is recorded in the audit log: which terminal, which session owns it, the text (scrubbed and cut to 200 characters) and the keys. Quotes and control characters in what was typed are escaped, so typed text can't pass for another field of the record.

If the terminal ends, you disconnect it or you block its folder while a send is waiting its turn, nothing is typed; if that happens between the two pieces of an `Esc` send, the session is told exactly which part went out. **On Windows**, `Ctrl+D` does not end input in `cmd` or PowerShell (the terminal layer there has no end-of-input key), and this has not been checked by hand on Windows yet — `Ctrl+C` and the other keys are only verified on Linux.

**Typing into a terminal you opened.** If you let sessions read a folder's terminals (the switch above), an agent may also ask to type into one of them — but only with your approval, once per terminal. The first time it tries, Harnu asks you: the question names the terminal (its name and working directory), the folder, and exactly what the session wants to type, and it never repeats the title a program has set on the terminal, because that text isn't trustworthy. **Allow does not type anything.** It lets agents type into that terminal, and the agent that asked is told to look at the screen and send again — so a request that sat unanswered for ten minutes can never type its old keystrokes into whatever is on screen by the time you press Allow. The permission belongs to the terminal, not to that one session: any agent connected to Harnu can use it while it lasts, so approve it only if you are happy with that. The question also shows how long the text is and spells out invisible or direction-changing characters, so it can't be made to look shorter than it is. After that, sends to that terminal run without asking until it has had no typing for ten minutes, or the terminal ends (a pane reopened under the same name is a new shell and asks again), or you block the folder, or you turn the read switch off, or you quit Harnu — then the next send asks again. **Deny** refuses the send, and every further send to that terminal is refused for five minutes without bothering you again. An approval is for one terminal only; with "Ask before agent actions" on, the same ask-once rule covers terminals a session opened itself. If the question is still waiting in the Approval Inbox after thirty minutes, it is denied.

**What a session types runs with your permissions.** A shell can do anything you can, including things the session's own tools would be blocked from doing. Harnu's model is that sessions act freely in terminals they opened themselves unless you block a folder or turn on "Ask before agent actions" — with that on, a send asks you first. You have two one-click ways to take this away:

- **"Allow agents to type into terminals"** in **Settings → Control server** (on by default). Turn it off and every attempt by a session to type into any terminal — yours or its own — is refused straight away, before any approval prompt. Sessions can still read the terminals you allow, and any typing permission you had given ends. A send already under way finishes. The session is told the switch is off, so it asks you instead of retrying.
- **Disconnect** cuts one terminal off from agents, for good: no session can read it or type into it again — not even after a window reload brings the pane back — and it disappears from the list of terminals a session owns. The shell itself keeps running and stays yours. If a session was waiting for output from it, that wait ends immediately and the session gets what the screen showed at that moment. You press it on the terminal's pane header — see the connection chip below.

**The connection chip.** A terminal a session opened shows who is connected right in its pane header: a small pulsing accent **icon** (a robot). Point at it, or Tab to it, and a tip reads "Connected to ‹session name›" (with "(parked)" if that session is at rest, or "a closed session" if it is gone); while the session reads or types, a second line says **Reading** or **Typing**. Click the icon to jump to that session. The pulse is the same whether the session is idle or working; with reduced motion on there is no pulse. Next to the icon, the **Disconnect** button (a plug icon) cuts the session off at once — no confirmation, since taking access away is the safe direction — and a small notice confirms it. After that the icon and the button are gone and the pane looks like any other terminal. If Harnu cannot apply the Disconnect, the icon stays and an error notice says the session still has access, so you know to try again. On a terminal you opened yourself the icon only appears while a session you allowed can type in it ("An agent can type here", with Disconnect) or is reading it ("An agent is reading", with no button — turn the folder switch off from the folder's right-click menu instead).

Blocking a folder from its right-click menu also stops a session typing there, along with everything else.

## Browser panes a session opens

A session can open a **browser pane** in a folder's split stack — a real page, so it can show you the dev server it just started, or look something up — and then move it around. The verbs are `browser_open`, `browser_navigate`, `browser_list` and `browser_close`, plus five that read the page (`browser_snapshot`, `browser_screenshot`, `browser_console`, `browser_wait_for`, `browser_network`) five that act on it (`browser_eval`, `browser_click`, `browser_type`, `browser_fill`, `browser_press`) and three that change how the page is shown or move files (`browser_emulate`, `browser_upload`, `browser_download`). What you see yourself is described in [Browser pane](browser-pane.md); this section is what a session can and can't do.

- **Opening.** `browser_open` takes an `http` or `https` address (a dev server on `localhost` is the usual one). The pane opens in the background in the folder the session works in, never steals your focus, and gets the same unseen badge and notification as any other pane a session opens in a folder you are not looking at. The session can name itself as the pane's owner, so the pane header says "Connected to ‹session›"; that is a label, not a permission. A folder holds at most four panes a session opened, and a fifth is refused with the panes to reuse; the panes you open yourself never count toward that. A session can also open a pane already showing a phone, tablet or desktop device (see below). A session can also open one of your project's `.html` files as a live panel (below).
- **Tabs.** A pane a session opened can hold up to eight tabs, all in that pane's own cookie jar (a session never adds a tab to a pane you opened, or to a live panel; it is told so). `browser_open` with a pane's id adds a tab to it instead of opening another pane; the tab loads in the background, so the page you are watching does not jump, and it doesn't count toward the four panes. Every verb that works on a page can name a tab by its `tabId`, which `browser_open` and `browser_list` hand out, and otherwise acts on the active tab; an id the pane doesn't have is refused, and so is a ninth tab. Reading (a snapshot, the console, a script, waiting for an element) and navigating work on a tab you aren't looking at, without switching. A screenshot, a click or any typing brings its tab to the front first, and the session is told it did (`activated`), so you may see the pane switch. If a tab's page failed to load, reading it returns a `loadError` instead of a page. `browser_close` with a `tabId` closes that tab; closing the last tab closes the pane. Your approval to drive a site belongs to one tab: it doesn't carry over to another tab of the same pane, and the first time a session works in another tab it asks again.
- **Navigating.** `browser_navigate` goes to a new address or back, forward, reload or stop, waits for the page to load (up to the limit the session sets, at most 90 seconds), and tells the session what happened: the title, the status, and a network error if the address didn't load. Running out of time isn't an error. Opening or navigating to a site the pane hadn't shown before sets an amber **"opened by agent · host"** badge in the address bar until you dismiss it or navigate yourself.
- **Paused to save memory.** A pane nobody has looked at for ten minutes lets go of its page, which can hold a few hundred megabytes; the pane stays where it is and says so. `browser_list` shows it as discarded, and the next time a session needs the page (to read it, click in it, run something) Harnu loads it again first and tells the session it did (`revived`). A page that was being used, recording its network, downloading or that you touched in the last minute is never paused. Panes also come back after you restart Harnu, paused, at the same address.
- **Looking and closing.** `browser_list` shows the panes Harnu knows about: which are open, who opened them, whether a session may read or drive each one, and, for a pane a session may read, its address (without the query string) and title, plus each tab with its `tabId`, whether it is in front and whether its page is loaded or paused. Folder paths are shortened, and a pane in a folder you blocked is left out. `browser_close` closes a pane.
- **Reading the page.** `browser_snapshot` returns the page as an outline of what a person perceives (headings, links, buttons, fields), one line each with a short name like `s4e12` that the session can use to point at that element later; the names stop working when the page navigates, and the session is told to take a new snapshot. `browser_screenshot` returns a picture of the viewport, the whole page or one element (never wider than 1568 px), and can save it under the folder's `.harnu/out/browser/shots/`; it works even when you aren't looking at the pane. `browser_console` returns what the page logged and any errors, from the moment the pane opened (the last 500 entries). `browser_wait_for` waits for an element or text to appear or disappear, for the address to match, or for the network to go quiet, up to 90 seconds; running out of time isn't an error. All of it is scrubbed of secrets as well as Harnu can, and marked to the session as untrusted: what a page says is never an instruction. These keep working while the session is paused or agent control is switched off, work on a pane you opened yourself only after you turn on **Let agents read browser panes I open** for the folder, and are refused for good once you disconnect the session. A Scheduler worker in `observe` mode may use them.
- **Network capture.** `browser_network` is **off by default**. A session must ask to start it, for up to 30 minutes (10 by default); you see a red **Network 4:12** counter in the pane header the whole time, and it stops by itself, when the pane closes, when you disconnect the session, or when you switch agent browser control off. What it records is addresses with every query value hidden, status, type, size and timing; never cookies or sign-in headers; and response text only if the session asked for it (text only, 64 KB each, 2 MB in all). Because starting it is a change to the pane, it is refused while the session is paused or agent control is off. Recording a site that isn't your own machine asks you first, the same way driving one does (next bullet); while paused the session can still read what was recorded and stop it, and stopping never asks.
- **Driving the page.** `browser_eval` runs a script in the page and returns the result (up to 64 KB; a script that throws still comes back as a normal answer with the error). `browser_click`, `browser_type`, `browser_fill` (up to 20 fields) and `browser_press` send real mouse and keyboard input to elements named by a snapshot; each waits up to five seconds for the element to be visible and not covered, and tells the session what it hit. Calls on one pane run one at a time, in order. A pane ignores clicks and key presses on the first page it loads, after it moves to another site, and after a page redirects itself, so until it is navigated again on the same site (a reload is enough) `browser_click`, `browser_press` and key-by-key typing are refused with `PANE_INPUT_NOT_READY` and the session is told to reload; filling, plain typing and scripts work from the start. **On a page on your own machine** (a dev server, or a host you listed under **Trusted dev hosts…**) a session does this freely. **On any other site, and on any pane you opened**, the first attempt asks you; **Allow** performs nothing and grants a ten-minute-idle lease on that pane, after which the session is told to look and try again; **Deny** blocks the pane for five minutes. The prompt says plainly that what a session types or runs there acts as you on that page, which may be signed in to your mail or bank. A mission grant or "always allow" never covers this, and a Scheduler worker in `observe` mode cannot use these verbs at all. Every call is audited with the pane, the site and, for scripts and typed text, a scrubbed copy cut to 200 characters.
- **Device, zoom, upload and download.** `browser_emulate` zooms the page (remembered for that site, as your own Ctrl +/− is) or shows it as a device: one of seven classes (`phone-s`, `phone-m`, `phone-l`, `tablet`, `tablet-landscape`, `laptop`, `desktop`) or a free width, height and pixel ratio, with touch, a mobile user agent, light or dark and reduced motion. It is real emulation, not a narrower window, and the pane's device picker shows and edits the very same setting. Zoom is off while a device is on; asking for both is refused. While touch is emulated a session's clicks are taps, like a finger's (a right or middle click does not exist there). `browser_upload` attaches up to 10 files to a page's file field, each a regular file inside the pane's folder (not through a link out of it, not over 50 MB, never anything in `.git` or `.harnu`, `.env*` files, `.git-credentials`, `.npmrc`, `.netrc`, `.pypirc`, `*.pem`, `*.key` or `id_*`); one bad path refuses the whole call. `browser_download` allows one download for the length of the call and saves it into `.harnu/out/downloads/` in the folder, never replacing a file and never opening it; downloads a page starts by itself are always cancelled, and one you start with a click asks you first. Changing the device and downloading by address are free on a pane the session opened and need your lease on a pane you opened. Downloading by clicking an element is a click, so on any site that is not your own machine it needs your lease too, like `browser_click`; uploading needs it as well. A Scheduler worker in `observe` mode cannot use these verbs.
- **Live panels.** `browser_open` can also take a `path` (a `.html` file inside the folder) or inline `html` with a `name` (Harnu writes `.harnu/out/panels/<name>.html` and opens it). Then `browser_set_data` replaces or merges the panel's saved state (up to 256 KiB, kept in `.harnu/out/browser/state/`, shared by every pane on that file) and pushes it to the page, and `browser_patch` changes one element of the live page by CSS selector (it is not kept across a reload). Both work **only on a panel pane**, for every caller, and refuse on a dev server or an external site, which is also why a read-only Scheduler worker is allowed to call them. A panel is offline unless you turned on its **Network on** switch, which no session can touch. A button in the panel can send a `[harnu-page-event]` message to the owner session (else the folder's selected one) only when you really clicked or pressed a key; it is marked as page data, not you. If no session can take it, a notice says so and the event is kept on the pane. Details: [Browser pane](browser-pane.md#live-panels-your-own-files-kept-fresh-by-a-session).
- **What it can't do.** It can't open `file:`, `chrome:`, `devtools:`, `view-source:` or `javascript:` addresses; the session is told plainly. It can't read or drive **a pane you opened yourself** unless you turn on **Let agents read browser panes I open** in the folder's right-click menu (off by default, this folder only): until then such a pane shows in the list as not readable, with no address or title, and every attempt to use it is refused. With it on, reading is allowed and driving still needs your lease. The page itself is untrusted: everything a session reads from a page is labelled as data written by whoever controls it, never as instructions.
- **Its own cookies.** Panes a session opens use a separate cookie jar from the panes you open yourself, and start logged out of every site. A login made inside a session's pane stays in that jar.

**Taking it away.** Three one-click controls, all yours (a lease ends with any of them):

- **"Allow agents to drive browser panes"** in **Settings → Control server** (on by default). Turn it off and every session attempt to open a pane or navigate one is refused straight away, before any approval prompt, whatever the "Ask before agent actions" setting says. Listing and closing keep working, and a call already under way finishes. The session is told the switch is off, so it asks you rather than retrying.
- **Disconnect** (the unplug button next to the agent icon in the pane header) cuts one pane off from sessions for good: no read, no write, not even closing it, and nothing reconnects it. The pane stays and stays yours; the chip turns red and reads "Disconnected". No confirmation, since taking access away is the safe direction.
- **Pause agent for 10 min** (the pane's ⋯ menu). For ten minutes, or until you press **Resume**, every change a session tries on that pane is refused and the chip counts down; reading still works. A pause doesn't remove anything, and it doesn't survive a restart.

Blocking a folder from its right-click menu also stops every browser verb there.

## Telling you the ball is yours

When you turn on [Your move](settings.md#your-move), a session can file a card in your
queue the moment it knows something only you can unblock, instead of waiting for its turn to
end. It does that with the `your_move` verb: a decision with options and a recommendation, a
go or no-go, something only you hold, a manual step, or a check. It runs free and never asks
you first, because all it does is add one line to your list.

- **A card says what it asks on its own.** The session is told to write it so you never have
  to open the session to learn what it wants, and to say what stays stuck until you answer.
- **A session can refresh a card, but it cannot close one.** It can sharpen a card it filed before
  and the clock on it keeps running, but no action a session can take closes a card you can still
  see. A card leaves when you deal with it, or when whatever raised it stops being owed (a mission
  card closes when the mission stops owing you anything, and Harnu also closes cards left behind:
  replaced by a newer turn, idle for 7 days, or pointing at a folder or session that is gone). So Harnu also refuses a session's
  request to archive a session, or to remove a folder, while one of your cards is open for it. A
  card checked only in Observe mode shows in no queue, so it does not block anything. A session
  cannot tell Harnu you handled something.
- **It is capped.** A session can make at most 30 calls per hour, refreshes included. Past that, the call is
  refused and recorded in the audit log, so a looping session cannot bury the queue.
- **With Your move **Off** (the default), or switched off for that folder, it files nothing.**
  The session is told so and says what it needs in its reply instead.
- **It is not what makes sure you hear about it.** With Your move on, Harnu inspects every
  turn that ends on its own, two detector runs and one more call to write the card clearly,
  and files what only you can unblock whether or not the session knows about the verb. The
  verb, and the optional `your-move` skill under [bundled skills](bundled-skills.md), make
  the cards better and earlier. Until the queue ships in the sidebar, a card from the verb
  shows in the list under **Settings → Your move**.

## Sessions talking out loud

A session can say one short line through your speakers — "the migration finished, zero conflicts" — for the times you're not at the screen. This is **not** a notification: it's heard once and then it's gone. Nothing lands in the Activity bell, nothing pops a toast, and there's nothing to come back to later. That's deliberate: if every read-aloud also filed a notice, your Activity history would fill up with sentences you'd already heard. A session that wants you to be able to find the message later posts a "Session says" notice instead (or does both).

**It's off until you turn it on.** Nothing an agent does can make your machine talk on its own — speech reaches everyone in the room, including whoever you're on a call with, so it starts silent. You turn it on in Settings → Voice, and there are two levels:

- **The global switch** covers every folder you have and every folder you'll ever make — including worktrees that don't exist yet. You don't have to enumerate anything, now or later.
- **A per-folder switch** overrides the global for that one folder, in _both_ directions. Turn voice on globally and mute one noisy repo; or leave it off globally and turn it on for the one project you're actually babysitting.

The important half: **an explicit per-folder mute beats the global.** If you silence a folder today and turn the global on next month, that folder stays silent — turning the global on never writes anything into your folders, so a decision you made on purpose isn't quietly undone. A folder you never touched simply inherits whatever the global says, which is what makes "and all future worktrees" work.

> **Where this stands today.** The `speak` verb, the gate and both switches are
> live; the **Settings → Voice** panel that exposes them is the next piece of the
> voice work and is not in the app yet. Until it lands, nothing has been turned
> on — which is the safe default: every folder is silent.

**There's also the engine's own switch.** Voice as a whole has a master switch (the same one that reads things aloud when _you_ ask), plus a mute, plus a choice of engine — your own TTS command or the downloadable offline voice. All of that sits above everything described here: agent speech needs the engine on and unmuted **and** the folder allowed. If a session tells you it spoke and you heard nothing, that's the usual reason — the session is told so explicitly ("the engine is off") rather than being left to assume it was heard. See [Voice](voice.md) for the engines themselves.

**Blocking a folder for agents outranks all of it.** A folder you've blocked (right-click → the folder's agent setting) is silent no matter what any voice switch says. Voice is never a way into a folder you closed.

**What a session hears back when it can't speak.** A refusal is normal here, not a failure, and it names the reason — "voice isn't on for this folder" versus "this folder is deliberately muted" are different answers, and sessions are told not to lobby you to undo a mute you set on purpose. They're also told to use a notice instead, so a message you needed doesn't just vanish because the speakers were off.

**Three limits that keep it bearable:**

- **It won't read you a paragraph.** Anything past ~300 characters is cut at a word boundary — the session is told it was cut, and is asked to say the headline and leave the detail on screen. Audio can't be skimmed.
- **It won't tell you what you're already reading.** If you're looking at Harnu with that very session selected, its speech is dropped — you can see it. Speech from a session in another folder, or while Harnu is in the background, still comes through. (This applies to a session speaking on its own initiative; if you ask to be read to, you get read to.)
- **One session can't hold the speakers.** There's a small per-minute allowance per session, so a looping agent can't talk over everything else. Utterances also queue rather than overlap — with several sessions running, two voices at once would be unusable.

## Drawing on a canvas

Some answers are a picture, not a paragraph. A session can draw one directly: an **architecture map, a flow, a dependency graph, a plan laid out in boxes** — on a canvas that opens in a pane next to the session, where you can grab a box and move it, rename it, wire two boxes together, delete what's wrong, and Save. Besides plain boxes it can draw ellipses (for states, starts and ends) and diamonds (for decisions in a flow), so a flowchart reads like one. It can also colour and style the shapes it draws — a tone, a dashed outline, a heavier stroke, a font size, an opacity — and when it edits a box later, your colours and styles stay put. It can colour and dash the arrows it draws too — green, amber, red or muted, solid, dashed or dotted — and an arrow's style survives its label being edited. It can also put one shape in front of or behind another; arrows always stay behind the boxes they connect. If you have restacked the board, a session adding to it is told to give new shapes a layer above the highest one in the file, so they land on top rather than underneath.

By default a session draws on that folder's own board, stored inside the folder at `.harnu/out/canvas/board.harnucanvas.json`. That file is gitignored and lives in the worktree, so each branch gets its own scratch board and nothing lands in a commit by accident. A session can also name a different canvas — but only under `.harnu/out/canvas/` or `docs/canvas/`; anywhere else is refused rather than quietly redirected. `docs/canvas/` is the one to ask for when the diagram is a deliverable you want committed with the branch.

**It opens itself.** A session's drawing call opens the pane for you in the background — it doesn't steal focus, and if you're looking at another folder you get the same sidebar pill and native notification any pane gets. You can also find the board in Browse files under `.harnu/out/canvas/`. If you closed the pane and want it back, ask the session to open it again.

**The board has two authors, and it remembers which is which.** Every box and every arrow records who first drew it — the session or you. Three things follow from that:

- When a session redraws its diagram, it only clears **its own** work. Boxes and notes you added survive. (An arrow you drew survives too, unless one of the boxes it connects was the session's and just got removed — an arrow can't outlive a box it's attached to.)
- A session can't claim it was you. It's refused outright from stamping anything as yours, rather than being trusted not to.
- After you edit the board and Save, the session can read it back and tell exactly what you changed — "you deleted three of my boxes, drew two of your own, and renamed this one" — instead of seeing an undifferentiated pile of shapes. That round trip is the point of the feature: the canvas is a place you and a session work on the same thing, not a picture it hands you.

**It shows up live.** If the board is already open when a session draws on it and you have no unsaved edits, the pane redraws by itself and your view stays where it is — no Reload. If you do have unsaved edits, the pane leaves them alone and shows the "This canvas changed on disk" strip instead, so you decide. Either way your next Save can't silently undo the session's change — with one narrow exception: a Save you press in the fraction of a second (roughly 100–250 ms) before the pane has heard about the session's write still wins, and the session's change is overwritten (last writer wins).

Deleting a box also deletes the arrows attached to it, whoever drew them — an arrow with nothing on one end isn't a thing the board can store.

**Nothing lands half-done.** A drawing call is a batch of edits, and it's all-or-nothing: if any single edit in the batch is wrong, the file is left exactly as it was, byte for byte. You will never open a board and find half a diagram.

**Screenshots.** A session can put an image on the board — the same paths it can use for card screenshots (a pasted image from the footer gallery — in either of Claude Code's cache locations — or a file inside the folder), up to 6 at a time and 2 MB each. The bytes are copied into an `assets/` folder next to the canvas rather than being stuffed into the canvas file itself, so a board with screenshots on it stays small and fast to open.

Drawing is treated like opening a file or posting a notice: it happens directly, no asking, because it writes a scratch file inside the folder the session is already working in and can't reach outside it. With "Ask before agent actions" on, it confirms like everything else.

## Guided walks

Some things only your eyes can prove: that a feature does what it should, that a colleague's pull request really works, that a mission's step is done. A **guided walk** is how a session asks you to check them one at a time. You start one by saying it in any session — "walk me through what we just built", "test PR #48 with me" (in your own language, or with `/harnu:walk`) — and the session, which knows the work, writes the list of checks: for each one, what to do, where, and what you should see.

A walk is its own thing, not a part of a mission. It has a title, a **source** (a feature you describe, a pull request, a branch, a board card, or a mission step, milestone or the whole mission), a list of checks, and a history of the times you walked it. It is saved on this machine, per repo, in the repo's `.harnu/walks/` folder (private, never committed, and shared by every worktree of the repo). Only a walk with a mission source ever relates to a mission, and even then Harnu never ticks a criterion for you: that stays your **Mark done** in the Mission.

**What a session can do with one.** It can open a walk (and the script is checked whole: if any check breaks a rule, the session is told every rule that was broken and where, and nothing is saved); add to it (an answer to your **Explain more**, a simpler way to say a step, or a check it found along the way); answer one of your outcomes (what its own read-only check found, or one correction after you pressed Failed); and read the walk back, which is what a session does after a compaction to pick up where you are. It cannot press your buttons, run a command for you, re-run, export or delete a walk, or settle anything: your answers are yours.

**What reaches the session.** When you answer a check in a way the session has to act on, it gets one short message that starts with `[harnu-walk]`, names the walk, the run and the check, and ends with how many checks are done. Pressing **Done** on a check the session can verify by itself, **Failed** (with your own line, and your screenshot if you pasted one), **Explain more**, **I didn't get this step**, **Treat as failed**, the escalation door after a second failure, and the close-out each send one; **Back**, **Skip** and a Done with nothing to check send none, and the next message tells the session where you are. These messages are delivered the way any message to a session is: a parked session is woken first. If no session can take one, it is kept with the walk on disk, so closing the app does not lose it, and it is sent again when a session can.

**Where this stands.** The session side and the pane are in place: a session can write, grow and read a walk, your answers reach it, and the walk opens beside the session, in the background, like a report or a canvas, where you walk it one check at a time (see [Guided test walk](guided-test-walk.md)). A session that opens a walk is told whether the pane was put in the folder's split stack (`opened`), so it never claims you are looking at a walk that was only saved. The library of past walks, re-running a walk from it and exporting one are not built yet.

Like opening a file, these four verbs run without asking (unless you turned on "Ask before agent actions"): a walk is written inside the repo's own `.harnu/` folder. A folder you blocked refuses them, and a Scheduler worker cannot use them.

## Watching Docker containers

A session can list the Docker containers on your machine with the same verdicts Harnu's Containers view uses: each compose project or standalone container, which of your folders it belongs to, and whether it's in use, protected, or left behind — a **zombie** still running for a worktree nobody has touched in days, or an **orphan** whose worktree is gone. It also sees the memory, ports and volumes each one holds, and the recent stops, starts and removals, including which ones you did and which ones an agent did. It can ask for everything, or just one repo and its worktrees.

Reading the list is never something you're asked about, and it changes nothing. Folder paths are shortened the same way the fleet view shortens them. Containers that belong to a folder you blocked for agents still show up in the list, marked as off-limits, so a session can tell you about them without touching them. If Docker isn't installed or isn't running, the session is told exactly that, with Docker's own error — it never gets an empty list it could mistake for a clean machine.

A read-only (`observe`) [Scheduler worker](scheduler.md) is allowed to use it, so you can have a worker check for zombie containers on a schedule and notify you when it finds some.

### Stopping, starting and removing containers

A session can also act on those containers, through the same Stop, Start and Remove the Containers view gives you — the same code path, so the same safety rules hold for an agent as for you:

- **Stop** runs without asking, because it's reversible: a stopped container can be started again. A session can stop a zombie or an orphan on its own. It can't stop one a session is working in, or one running from a repo's main checkout, unless it explicitly forces the stop — and a forced stop always asks you first.
- **Start** runs without asking. It's refused for an orphan (its worktree is gone, so nothing would use it).
- **Remove** always asks you, every time, whatever your settings are — no mission grant or "always allow" checkbox can skip it, because a removed container can't be brought back. It removes one stack per request, never several at once. It's refused while the stack is still running (the session has to stop it first), while a session is working in its folder, for a main checkout, and for a stack that isn't a zombie yet. The confirmation names the stack, the folder it runs from, and whether its volumes would be deleted too. Volumes are only removed when the session asks for it, always after the containers, and a volume another stack also uses is never removed.

A container Harnu can't tie to one of your folders is never touched by any of the three, and neither is one in a folder you blocked for agents. Every stop, start or removal a session makes is recorded in the Containers view's history, marked as done by an agent, so you can always see what it did. Read-only Scheduler workers can watch containers but can't do any of this.

## Watching workspace cleanup

Harnu's Cleanup surface sorts every worktree into **Ready to clean** (its branch is proven merged, it's clean, nothing is running in it, and its grace period is over), **Needs review** (it needs you, with a one-line reason) or **In use**. A session can read the same list — each worktree's bucket, the reason, how much disk it holds, any orphan Docker volumes, the totals, whether the automatic cleanup is on, and when the next cycle runs. It reads the picture from Harnu's most recent scan, and the list says when that was; asking never starts a new scan or writes anything. It can ask for everything or just one repo and its worktrees. Reading the list never asks you, and no folder path ever appears in it: worktrees are shown by name, and a reason is a short fixed sentence, never a raw error message. Worktrees in a folder you blocked for agents still show up, marked as off-limits.

A read-only (`observe`) [Scheduler worker](scheduler.md) can use it, so you can have a worker report how many worktrees are ready to clean and how much space they hold.

### Telling Harnu a worktree is finished

When a session's pull request has merged, it can **release** the worktree it worked in. That skips the grace period, so the worktree becomes ready to clean at the next scan instead of waiting a couple of days. It runs without asking, because it deletes nothing — you (or the automatic cleanup, if you turned it on and acknowledged its first report) still do the cleaning.

A release is only a hint about timing, and it belongs to the commit the worktree was at when the session released it: if more commits land afterwards, the session has to release again after the next merge. It never overrides a safety rule. A worktree with uncommitted changes or unpushed commits, one with a session still open, one whose Docker stack another worktree also uses, one with another worktree sitting inside it, one git has locked, one you marked Keep or never-clean, and one whose folder Harnu couldn't resolve all stay out of Ready to clean, and the session is told which rule held it back. It's refused for a worktree whose branch isn't proven merged, for a repo's main checkout, for a folder Harnu doesn't know, and for a worktree in a folder (or a repo) you blocked for agents. A session can name the worktree by its folder or by the name the list gave it. Read-only Scheduler workers can't release anything.

These two verbs never remove anything, and no session can clean a worktree. (A session can remove Docker containers, but only through a separate action that always asks you first — see "Stopping, starting and removing containers" above.)

## Reading the GitHub budget

Every `gh` call Harnu makes spends the same personal GitHub quota your own scripts use. A session can ask Harnu how much is left with `github_budget`: it gets the REST and GraphQL buckets (limit, remaining, when they reset, how fast they are being spent), which bucket is tighter, whether Harnu is slowing down (`normal`, `low`, `exhausted`), and how many of the calls in the current window were Harnu's own, per feature, against everything else on your login. Sessions are told to check it before they poll `gh` in a loop, to back off when it reads `low`, and, when GitHub's secondary limit has paused reads, to wait until the time the answer gives (`pausedUntil`). If `gh` is not installed or not signed in, the answer says `unavailable` instead of failing.

The verb only reads what Harnu already tracks: it makes no GitHub call of its own. A read-only (`observe`) [Scheduler worker](scheduler.md) can use it too, so a worker can slow its own polling.

## Tracking a mission's progress

When a session takes on work that will need several steps or several sessions (more than one pull request, or an objective it would otherwise keep in a to-do list), it keeps a **mission**: one record of what "done" means, the plan, who is working on it and what is waiting on you. It starts the mission by itself, before the first step, without asking you. What you see and what you press is on the [Missions](missions.md) page; this section is what the session can do.

Missions live in your repo's main checkout under `.harnu/missions-v4/`, one file each, and every worktree of the repo sees the same ones. Like the rest of `.harnu/`, they stay on your machine and out of git. Everything below happens directly, without asking you first, except what the page says is yours. A mission has a title, a **Done when** sentence, optional **milestones**, and **steps** that each carry **criteria**: one sentence each, saying what is true when the step is done and who settles it (Harnu reads a fact, a second session, you, or another person you name).

What a session can do with one:

- **Start a mission** (`mission_create`, with a Done when, optional milestones and steps that carry criteria). The session that creates it leads it, with nothing for you to approve, and it shows in the Mission dropdown at once.
- **Add to the plan** (`mission_add_milestone`, `mission_add_step`, `mission_add_ac`, `mission_link`). A plan only grows: a session adds, and never removes or rewrites. A step added after work started says why, and **adding a step takes back a close request** the session had already made: the new step isn't done, so you are not told the mission is ready. Linking a pull request, a page or a report to a step or to the mission is `mission_link`.
- **Write in the mission's log** (`mission_log`): a timestamped note, a decision or a surprise. The log is a narrative for humans; it never changes the mission's state.
- **Read a mission** (`mission_get`) or **list them** (`mission_list`). Reading one gives how far it has got, the next step, what is waiting on you and a summary. Any session in the folder can list the open missions as one-line rows; only a session that is attached can read the detail.
- **Flag a blocker** (`mission_set_blocker`) on the mission or on one step, and **clear it** again (`mission_clear_blocker`). A blocker says the exact thing that is needed and what starts once it is done. One that waits on you is the only kind a session cannot clear: you press **Done, continue** in the Mission dropdown. A blocker that is yours also makes Harnu play its attention sound and remind you at 30 minutes, 1, 2 and 4 hours, then stop.
- **Settle a criterion** (`mission_settle_ac`). A session that did _not_ build the step settles a criterion with the evidence it saw. The session that built the step can only record a self-check, which never counts. Harnu settles fact criteria itself, and only you settle yours and another person's.
- **Propose a new Done when** (`mission_set_done_when`). It never changes the sentence: it waits for you in the Mission dropdown, with the text it proposes.
- **Ask you to close it** (`mission_request_close`). It is refused while a required step is not done, and it never closes the mission: closing is yours.
- **Ask to join a mission** (`mission_attach`). A session that isn't attached to a mission can't read it; it asks, and you allow or deny the request in the Mission dropdown. A request is only ever to join, never to lead: who leads changes only by a hand-off, which is yours and which the app has no button for for now. A session a hand-off starts uses your own permission mode, not the previous leader's.
- **Rebase a step's branch** (`rebase_stack`), once a parent branch has landed. It belongs to the leader: it rewrites only the **local** branch of the step it is working on, with `git rebase --onto`, in the worktree that belongs to that step. It never pushes, never touches another branch or the main checkout, and on a conflict it stops, puts the tree back exactly as it was and tells the agent, which should flag the step as blocked. A session that only worked a step, or one that isn't attached to the mission, is refused.

**Commands an earlier version had are gone.** Six mission commands no longer exist, and a session that still sends one is told the tool is not found and nothing changes. Each has a replacement: linking a session, a pull request or a worktree to a step is now `mission_link`; setting a new end is `mission_set_done_when` (it waits for your approval); verifying a step is `mission_settle_ac`, one criterion at a time; a sign-off you owe is a criterion that only you settle, added with `mission_add_ac`; replacing the session that leads a mission is the hand-off in the Mission dropdown (a session can only ask to join, with `mission_attach`); and importing an old goal file has no replacement, because a mission an earlier version wrote opens as it is. The same goes for plans made of chapters: the commands that created and managed them are gone, and a session now plans a large piece of work as **one mission with milestones**, with `mission_create` and `mission_add_milestone`. A `mission_create` that still carries an older argument (an end of the old kind, a chapter, a steward, a step's `verification`) is refused and nothing is written.

One command is listed but cannot do its job yet: `mission_update_step` (change a step's title, milestone, wait or optional mark) is refused, and nothing is written. A session adds to the plan instead.

No session can merge a pull request, close or discard a mission, approve a new Done when, mark your criteria or choose who leads: those stay yours. The routine moves a background helper once did are done by the session that leads the mission.

**Sessions Harnu starts for a step have their own key.** When an agent starts a session for one step of a mission (`create_session` with a mission and a step), Harnu gives that session a credential of its own, kept in a private file the session reads and never shown to the model. The session is offered only the commands of its role: a **worker** can read its mission and, on its own step, link something, write to the log and set a blocker; a **verifier** can also settle a criterion; the Scheduler's **observer** can read the missions of its folder. Which session it is comes from that key, not from what the session says, so a verifier that built a step is always recognised as the builder and its check counts only as a self-check. A worker writes only its own step: another step, another mission or another folder is refused with a message that says what it may do, and it can never lead a mission, attach itself, change the plan or touch another mission. When it needs something from the leader or from you, it says so in the log or as a blocker. Starting such a session does not attach it to the step: that happens when the work is dispatched. The Scheduler's **observe** workers use the same kind of key. Each tick is bound to its worker's folder: it can read that folder's missions (without being attached to them), and it can call the same read commands an observe worker could always call (the fleet, sessions, worktrees, memory and the rest of that list), but nothing that writes to a mission, and it can't read another folder's missions; a folder it names that isn't its own is refused, and so is a browser pane or a terminal that belongs to another folder. It is not read-only, though: an observe worker can still create and update cards, send notifications and update a live panel, each only in its own folder. If Harnu can't write the key (agent control is off, or it isn't running yet when a worker that runs at startup first ticks), the tick runs without Harnu commands rather than with your main key. Act workers keep what they had.

**A nudge to start a mission.** When an agent that leads no mission starts real work, Harnu reminds it once. The work that counts is starting a second session, cutting a worktree, or sending a dispatch batch of cards (each card is a session). The reply to that command then carries one sentence, `missionHint`, telling the agent to create a mission with its steps. It is only a reminder: the command still does what the agent asked, it comes once per session, and Harnu never creates a mission itself, so nothing appears in the Mission dropdown until the agent makes it. An agent that already leads or works on a mission, and every session Harnu started for a step, never gets it. The three commands (`create_session`, `create_worktree`, `submit_manifest`) accept an optional `sessionId` so Harnu can tell which agent is asking. An agent that doesn't send one is counted as a single caller of its repo, and is left alone in a repo where a mission already has a leader. The count starts again from zero when Harnu restarts.

**A step handed to its own session gets a card and a worker.** A step the leading session does itself has no board card. When the leader hands a step to a session or worktree of its own, Harnu does the bookkeeping at that moment, with nothing for you to approve: the step gets a card in **Backlog** (or the card it already had), marked with the mission, the milestone and the step, and carrying the step's criteria in a block Harnu keeps up to date (change the criteria on the step, not in the card); the new session is attached to the mission as a worker and linked to that step, so its own key reaches that step and no other. This happens when the leader starts the session itself, and when the leader submits a dispatch batch that names the step for a card: the card is marked for the step when the batch is approved, and the session the board starts for it is attached once it has booted. A verifier started for a step is attached too, but gets no card and is not linked to the step it checks, so what it settles is never a self-check. Harnu never moves a card to Done: closing a card stays yours. The mission's Log records each of these in words, such as `Harnu attached a worker to step "Add the CSV exporter"`, and what you do (attaching a session from the Mission dropdown, allowing or denying a request) names the mission by its title, never a session id. The board's own Dispatch button does the same for a card that is already the work of a step: the session is attached once it has booted, and a card dispatched into its own folder gets the step's key. A card the board cuts into a new worktree is attached, but keeps the full set of commands. If a key is not ready in time (about two minutes), the session is still attached, with the full set.

A leader that did a step itself, with no other session linked to it, is the builder of that step: when it settles a criterion there, the result is a self-check and the criterion stays open for another session or for you.

A session you started yourself has no key of this kind, and still tells Harnu which session it is by passing its own session id. That id is **not checked**: it names a session and nothing more. It can't make a session you, can't make it Harnu, and doesn't let it do what only you can do from the app. A Harnu system worker (a background helper that is not a session) only reads a mission. What a step's pull request or checks say is read by Harnu; a session never supplies it.

### What a new mission remembers

When a session starts a mission, Harnu looks through project memory for decisions that watch the same files or words (the files its links name, and the words in its title and steps) and hands the session the matching ones, up to five, in its reply. A decision that was later replaced is not offered; its replacement is. See [Project memory](project-memory.md#decisions-that-replace-each-other).

### Missions an earlier version wrote

Old missions and delivery plans still open in the Mission dropdown, and every command above reads them. The first change to one writes a copy beside it, and the old file is never touched: it stays as it was, byte for byte. If a mission file can't be read (it was damaged, or it isn't a mission file), Harnu says so in the notification bell and names the file, instead of leaving the mission out without a word. The page [Missions](missions.md#records-from-earlier-versions) has the details.

## Batching approvals (only matters if you turned confirmations on)

With "Ask before agent actions" on, approving every action one at a time gets tedious when a session is doing a lot of related work at once — say, setting up three worktrees for three tasks. Instead of asking three separate times, a session can request one **mission grant**: a single approval that names a goal, the folders and specific actions it covers, a budget (how many actions), and a time limit. Say yes once, and everything within that scope runs on its own until the budget or the clock runs out; anything outside the scope still asks you individually. You can see any live grant's remaining budget and time in the Approval Inbox, and revoke it early if you change your mind. A grant can never reach into a folder you blocked.

Separately, when you approve an individual action, you'll sometimes see an **"always allow this verb here"** checkbox — checking it means that specific kind of action never asks again in that folder, persisted across restarts, independent of any grant.

With confirmations off (the default), none of this comes up — actions simply run, and mission grants are redundant.

## Getting from a card to a running session

A session can freely draft and reorganize roadmap cards, but actually dispatching a batch of them as real running sessions still needs one extra, deliberate step: a session has to submit a **manifest** — a named, ordered list of exactly which ready cards it wants to run and where. Moving cards to Ready is your consent to have them run; the manifest is what turns that standing consent into an actual batch of running machines, so it's a door a session opens on purpose, not something it stumbles into.

With "Ask before agent actions" off (the default) and the folder not blocked, submitting a manifest dispatches it right away — no confirmation, and no per-card unchecking, since there's no prompt to uncheck anything from. Harnu still marks the moment: a note lands in the audit log naming the folder and every card in the batch, and you get a notification the instant it happens, so a batch that self-approved while you were away is still something you can see after the fact, not something that just silently ran.

If you turn "Ask before agent actions" on, submitting a manifest goes back to showing up in your Approval Inbox as an explicit checklist — listing each card's title, its readiness, and the exact prompt it would boot with. You can approve the whole batch, or uncheck individual cards to leave them alone; only your Allow marks the checked cards as cleared to run, and those additionally need a live mission grant to auto-dispatch (otherwise each one waits for you to click Dispatch on the board).

Either way, once a card is marked cleared to run it dispatches itself in the declared order. If a card was edited after being cleared, its approval is void and it always waits for a per-card Dispatch click — the toast names the card and the reason.

Which model and effort level a card actually launches with is controlled by a routing table you configure yourself (per card kind — scout, bug, feature, chore, review) in a folder's launch settings, not by whatever the session suggests when it drafts the card — a session's suggestion is shown to you as a hint, but the table decides.

## Creating a Scheduler worker

A session can mint a [Scheduler worker](scheduler.md) — the one thing that keeps running on its own cadence after the session that made it is gone. This matters most for a session that's coordinating other work: it's the backstop that keeps checking in even if the coordinating session itself ends, instead of that heartbeat only existing when you remember to build one by hand.

**An `observe` worker is created the same way as everything else in this section — directly, no asking.** It's read-only by an explicit allowlist (the same one described in [the Scheduler doc](scheduler.md#observe-vs-act--read-this-before-you-flip-the-switch)), so an unattended one is no more consequential than a session starting another session.

**An `act` worker is different, and always stops to ask you first — one of the few exceptions to "acts freely" in this whole document.** An `act` worker runs with permissions bypassed and doesn't stop at the Approval Inbox, which means minting one unattended would be the session handing itself a second, permanently unsupervised body. So no matter what "Ask before agent actions" is set to, creating one shows up as a confirmation naming the folder, the cadence, and the exact prompt it would run — the same standing as a mission grant or deleting a card.

Either way, a worker made by a session arrives already switched on — unlike the Scheduler's own New worker button, which leaves a fresh worker off until you fill in the form and arm it yourself. If the session's prompt names a skill that resolves to nothing on this machine, it's told so in its own result rather than getting back a worker that will quietly never stage it. Naming a bundled skill that's merely switched off for the folder is not this case — it stages anyway, the same as in a Scheduler tick.

A session can also **list the workers that already exist**, either everywhere or just in one folder, so it can check whether the heartbeat it needs is already running before minting a second one. It gets back each worker's name, folder, cadence, mode, whether it's switched on, and how its last run ended — the same summary you'd read off the Scheduler list yourself, with folder paths shortened the same way the fleet view shortens them. Reading the list is never something you're asked about.

A worker a session creates starts at the **Silent** notify setting, exactly like one you create by hand — so a session can't quietly sign you up for a notification on every tick. If you want to hear about its runs, you turn that up yourself in the Scheduler.

**A session can also fix a worker it already made, or remove one.** Minting a worker used to be one-way: if the prompt had a mistake, or the operator flipped it to `act` and the prompt still said "don't modify anything," the only fix was to hand you a corrected string and ask you to retype it into the Scheduler yourself. Now a session can edit any subset of an existing worker's fields directly — name, prompt, cadence, mode, model, effort, timeout, whether it's on, and a few more — by referring to the worker's id (from when it created it, or from the listing above). That edit runs freely, the same as creating an `observe` worker, **unless the edit itself raises the risk**: flipping the worker to `act`, or touching either of its prompts at all — the instructions it runs, or the system prompt behind them. The prompt rule is deliberately unconditional and covers both, because both are the body the worker runs unattended — a session editing a worker's prompt can't tell you whether that worker is currently `observe` or `act` without asking, so any prompt edit stops to confirm with you, the same standing as minting an `act` worker in the first place. An edit never reaches a tick that's already running; it only takes effect from the next one.

**Deleting a worker is different, and always asks you.** Unlike editing, permanently removing a worker — its definition and its run history, and stopping a live tick if one is running — always shows up as a confirmation, no matter how "Ask before agent actions" is set: there's no undo, the same standing as permanently deleting a roadmap card. Pausing it instead (asking a session to disable it, rather than delete it) is the reversible alternative if you might want it back.

**A session can also mint a worker with a longer timeout from the start.** A tick whose own instructions chain several slow steps together — spinning up a worktree, installing dependencies, starting another session — can need more than the built-in 5-minute limit, and a session can now say so when it creates the worker instead of you having to raise it by hand afterward.

## Promoting a session to orchestrator

You can promote any session to an **Orchestrator** role (from its right-click menu). This is the deliberate gesture that gives a session its coordinator framing from the moment it starts: it arms a guard that stops that session from editing files directly outside its own notes, and shifts its focus to planning and delegating — spinning up other sessions and worktrees to do the actual work rather than doing it itself. A promoted session is visibly marked with a badge and a topbar pill so it's obvious when a session is meant to be coordinating rather than coding. The guard itself isn't exclusively yours to grant, though — see below.

Promotion is really two things bundled together: a note added to the session's own instructions when it starts (which only ever happens at the moment you launch it, or when a skill boots it straight into the role), and a live guard that blocks it from editing files directly. That second half doesn't have to wait for you — any session Harnu spawned for agent work can arm it for **itself**, mid-conversation, the moment it realizes it should be coordinating rather than coding. When that happens you'll see the exact same badge and topbar pill appear, with no click from you. It can also arm or disarm that guard on **another** session — any session Harnu spawned for agent work, not only one it personally dispatched — but never a session you opened by hand yourself; and a session you opened by hand can't arm the guard on itself either, only an agent-spawned session can. Think of it as the session pulling its own emergency brake, not as it granting itself a new role behind your back: the guard only ever adds friction to what that session can do: it fails safe, so if anything about the arming goes wrong the session just behaves like an ordinary one, never a broken one.

**Making a whole folder default to Orchestrator.** If you find yourself promoting every new session in the same repo by hand, the folder's right-click menu has a toggle for that: **"New sessions start as Orchestrator"** (off by default). Turn it on and every plain session you start there afterwards — "+ New session", the New session dialog, the keyboard shortcut — is born already promoted, badge and all, from its very first turn. The folder row gets a small crown to remind you the default is on.

This toggle belongs to that **one exact folder**, never its worktrees — turning it on for a repo does not turn it on for the worktrees you cut off it. That's deliberate: an Orchestrator's whole job is dispatching _executor_ sessions into those worktrees to do the actual editing, and an executor born with the same guard armed would be blocked from writing the code it was sent there to write. For the same reason, a session an agent starts on its own — through the MCP tools, a board dispatch, a Scheduler tick, or a read-only review companion — is never armed by this default, no matter how the toggle is set; it only ever applies to a session **you** started by hand.

Turning the toggle on or off never reaches back into sessions that already exist — it only decides what a _future_ "+ New session" click does. And a session the default did arm keeps its role through being parked and resumed later; only an explicit demote (turning the role off from that session's own menu) ever takes it away for good.

## Putting finished sessions away

A session can archive other sessions for you, the same as choosing **Archive** from a session's right-click menu, instead of you doing it row by row after a clean-up. It names between 1 and 100 sessions, and each one moves out of the normal list into its folder's **Show N archived** row, with its terminal closed. Nothing is deleted: the conversation and the worktree stay exactly where they were, and the session can restore them (or you can choose **Unarchive** yourself) whenever it likes. It runs without asking, and calling it twice changes nothing the second time.

Harnu keeps the archived list itself now, not the window, so a session can archive while Harnu's window is closed and the same sessions show as archived the next time you open it. When it happens while the window is open, the sidebar updates on the spot. The first time you start a version with this change, the sessions you had already archived are carried over automatically; nothing is lost, and the old copy is left in place so going back to an older version still finds it.

Each session is judged on its own, and the answer lists one result per session: archived, already archived, restored, already active, not found, or refused. A session is refused when its folder is one you blocked for agents, when it is working right now, when it is waiting on an approval from you, or when it still has a [Your move](settings.md#your-move) card open in your queue (only you can close a card); those stay as they are until you or the agent come back to them. The call is recorded in the audit log like the other actions that run without asking.

## Hiding finished folders

A session can hide folders and worktrees from the sidebar for you, the same as choosing **Hide** from a folder's right-click menu, instead of you doing it row by row once a body of work is finished. It names between 1 and 100 folders by their full path, and each one moves out of the sidebar into the hidden-folders view, where you (or the session) can show it again. Nothing is deleted or moved: the folder, its worktree, its branch and its conversations stay exactly where they were, the folder stays pinned if you had pinned it, and the only thing that changes is the same hidden flag the menu action writes. It runs without asking, and calling it twice changes nothing the second time.

When Harnu's window is open the sidebar updates on the spot; the menu's Hide and Unhide, and the hidden-folders view, work exactly as before.

Each folder is judged on its own, and the answer lists one result per folder: hidden, already hidden, shown, already visible, not found, or refused. A folder is refused when you blocked it for agents, when a session in that exact folder is working right now, or when one of its sessions is waiting on an approval from you (showing a folder is only refused for a blocked one). "Not found" means Harnu has never seen that path: it is not pinned, not hidden and has no sessions. If two actions touch the same folder at the same moment, the results are consistent with one of them having happened first, and the answer always matches what was saved. The call is recorded in the audit log like the other actions that run without asking.

This is not the same as cleaning up a folder whose directory is already gone: that is a separate action that removes the leftover sidebar entry for a deleted folder, and it refuses while the folder still exists, and while one of your [Your move](settings.md#your-move) cards is open for that folder in your queue (only you can close a card). Hiding is for folders that are still there and can be undone at any time.

## Parked and hibernated sessions

If a session goes idle for a while, Harnu may kill its underlying process to free up memory — but this doesn't lose anything, and it isn't the same as a session getting stuck. Clicking the session resumes it exactly where it left off. If you're watching your fleet through the tools above (or a session is), a quiet or "parked" session should be read as dormant, not failed.

**A message can wake a parked session.** If one session messages another that Harnu has parked, Harnu brings it back first and then delivers — the same resume you'd get by clicking it, except it happens in the background and never moves your view to it. Harnu keeps a record of that: the wake is logged as agent-driven rather than as one of your clicks, so "who woke this session" stays answerable. If the resume takes too long, the message is **not** sent and the sending session is told so — Harnu never quietly drops it, and never starts a second process to force the delivery.

## Sessions talking to each other

Claude Code has its own cross-session inbox — one session can send another a message, and the message waits until the recipient finishes what it's doing rather than interrupting it. Harnu adds a door onto that: a session can call `message_session` with another Harnu session's id, and Harnu figures out which actual process that is and delivers the message.

**Why bother, when the sessions could already do this themselves?** Two reasons, and they're the honest limits too. Harnu knows _exactly_ which process a session id maps to, so there's no name-guessing; and every message sent **through Harnu** lands in the audit log and posts a row in your Activity history, so you can see it. What Harnu cannot do is see traffic that doesn't go through it — sessions can reach each other directly, with or without Harnu, and nothing in Harnu can close that. Harnu is one recorded door, not the only door.

**Who a session can message.** Only sessions Harnu started _for an agent_ — one a session launched itself, or one dispatched from the board — and only in a folder you haven't blocked. Everything else is refused: a session **you** opened in Harnu, a `claude` you're running in your own terminal, a teammate pane, and an old transcript with nothing running. The refusal names the reason — `RECIPIENT_NOT_HARNU_SPAWNED` when Harnu holds no process for that session, `RECIPIENT_OPERATOR_OWNED` when it is one you opened yourself. (Before the Harnu rename the first code was spelled with `CAPY` in place of `HARNU`; the spelling was changed with no alias, because it is a status code an agent reads, not a saved setting.) So an agent can't put words in front of you in your own session; if it needs your attention it has to use the Activity notice instead, which waits for you to read it rather than landing in a live turn.

**What the sender is told.** That the message was _queued_ — not that it was read, agreed to, or acted on. Harnu has no way to hear back what the recipient did with it, and it says so rather than implying more. Every refusal is specific enough for the sending session to know what to do next instead of retrying blindly.

**One thing worth knowing.** Claude Code itself treats an incoming message from another session as _input_, never as your approval — it's explicitly told that relaying an action it was refused permission for is not a workaround. Harnu is careful not to weaken that: it never claims a permission level on the sender's behalf, which is what would let a message slip past the recipient's own check. But Harnu sees text, not intent. Logging a message makes it attributable, not harmless.

## A session whose starting prompt never arrived

When a session is started with a message already queued up for it (a starting prompt from `create_session`, or a card's boot prompt), Harnu normally waits until the session's chat composer is genuinely ready before typing it in — pasting too early risked the message landing somewhere other than the chat, like a first-run "do you trust this folder?" prompt. If that ready signal never arrives, Harnu no longer guesses: it holds the message back rather than risk it landing in the wrong place, and marks the session failed with "prompt not delivered" instead of leaving it sitting there silently. This also means a session checking on its own dispatch (or another session checking on it) can now actually see that something went wrong, rather than being told the session is still `active` indefinitely. A healthy session is unaffected by this — it still gets its message immediately, with no extra wait.
