# T104 — Dispatch Manifest: one disclosed batch, one go, stamped drain

**Status:** PRD v1 (2026-07-09) · **Effort:** L · **Card:** [[T104]] · **Dep:** T96 (verbs/schema) · T80-S2 (grant plumbing) · T44 §0 (grant invariants)
**Base:** epic `T82-agent-task-manager.md` §10.3 (concept, Q15 decision) + §11.1 door 1 (relocation of the `approved` stamp). Operator's conceptual sign-off: 2026-07-09. **This PRD locks the mechanics; implementation only becomes Ready after this doc is read by the operator OR the reading is explicitly delegated.**

## 0. ⚠️ What this PRD protects

The manifest is **the single door between "organizing" and "executing."** After the
§11 pivot (free creation/movement), all defense against (a) unauthorized spending
and (b) prompt-injection via card body concentrates HERE: no body becomes a boot
prompt without passing through human eyes — at per-card confirm OR at manifest
reading. Invariants inherited in full: T44 §0 (grant bounded/disclosed/audited/
revocable/escalation-not-denial) and T80 §0 (agent never → Done; provenance
fail-closed).

## 1. Concept

A **manifest** is an ephemeral document, generated by the orchestrator, that
declares ONE dispatch batch: which cards, in what order, substrate + model/effort
per card, file-conflict analysis, estimated cost. The operator reads it and gives
**one go**. The go:

1. **Stamps `approved: <ISO>` server-side** on each listed card (controlled field —
   no verb writes it; only the manifest flow).
2. Authorizes draining **that batch**: with a live grant covering (folder,
   create_session/worktree), the manifest's cards dispatch from Ready with no
   per-card confirm, in the declared order, respecting WIP.
3. **Is not a permanent license:** new cards = new manifest. The manifest doesn't
   "stay open" — it's exhausted when its cards dispatch (or expires with the
   grant).

## 2. Mechanics

### 2.1 Generation (orchestrator → Capy)

New verb `submit_manifest({folder, cards: [{slug, substrate?, model?, effort?}],
note?})` (mutates, but **not** auto-allowed — it IS the gate request):

- The server validates: cards exist, none `done`, readiness lint (T96
  `lintCardReadiness`) runs and the gaps enter the disclosure (warning, not a
  block).
- The server builds the disclosure from the **files on disk** (never from the
  agent's text): title + kind/complexity + resolved substrate/model (routing table
  as default, args as override) + **body hash** per card + boot prompt that will
  be generated + cost estimate (T47 heuristic when available; otherwise "no
  history").
- Lands in the **Approval Inbox** as a manifest item (its own UI: list of cards
  with checkboxes, not a text blob).

### 2.2 The go (human, in the Inbox)

- **Partial-go is native:** the operator unchecks cards before Allow — the
  unchecked ones simply are NOT stamped (no denial involved; they remain
  organizable and can enter another manifest). Inherits the spirit of Q7 (list +
  accept all).
- Allow stamps `approved` + **`approvedBodyHash`** per card (see 2.3) and logs the
  manifest in the shadow log (T30): who, when, which slugs, which hashes.
- A pending manifest is revocable/ignorable; expires with its own TTL (default: the
  active grant's TTL; without a grant, 24h) — expired, it evaporates from the
  Inbox (zero clutter, Q6).

### 2.3 Invalidation by edit (anti-bypass — the heart of the PRD)

- The stamp holds `approvedBodyHash` (sha256 of the body + fields that enter the
  boot prompt: title, spec path). At dispatch time, the gate **recomputes the
  on-disk file's hash and compares**. Diverged ⇒ stamp invalid ⇒ card falls to
  per-card confirm with reason `manifest-stale` (disclosure shows a summarized
  diff).
- Comparison AT DISPATCH TIME (not by watcher): eliminates the "edited after the
  watcher but before the spawn" race. The watcher may, additionally, clear the
  stamp on detecting an edit (visual hygiene on the board), but the TRUTH is the
  check at the gate.
- `update_card`/`memory_append` on a stamped card: allowed (zero friction), with
  an ACK warning: "this card had manifest approval; the edit returns it to
  confirm".

### 2.4 The extended gate (`decideDispatchGate` v2)

```
auto ⇐ live grant covers (folder, verb)
       ∧ ( author = human                     — original T80 rule, intact
         ∨ (approved present ∧ hash matches) ) — the new manifest path
else ⇒ confirm (new reasons: 'no-manifest' | 'manifest-stale')
```

Pure, branch-unit-tested, like v1. Human-provenance cards keep working as today
(grant is enough) — the manifest is additive, it replaces nothing.

### 2.5 Drain

- Order: as declared in the manifest (not column priority — an explicit decision;
  auto-ordering is autonomy nobody asked for).
- WIP: the drain PAUSES at the ceiling (5) and resumes when a card leaves
  In-Progress — never overflows the ceiling per batch.
- Worktree substrate: `create_worktree` + grant scope inheritance
  (`addDynamicFolder`) + spawn inside — the T80 §3.4/T102 path.
- Spawn failure: budget refund (existing `releaseDispatch` mechanism), stamp
  PRESERVED (the failure wasn't an edit) — manual retry or next drain tick.

## 3. UI (design.md §6 before coding)

- Manifest item in the Inbox: list of cards (checkbox · title · kind/complexity ·
  substrate · model · lint gaps) + total estimated cost + Allow/Deny button.
- On the board: discreet "manifest ✓" badge on a stamped card; the existing grant
  strip (T80 S2) gains a drain counter ("3 of 6 dispatched").
- i18n en+pt-BR; no new token.

## 4. ACs

- **AC-1:** `submit_manifest` validates against disk, builds the disclosure
  server-side, parks it in the Inbox; the agent cannot stamp anything through any
  path.
- **AC-2:** partial-go stamps only the checked ones; unchecked ones stay intact.
- **AC-3:** body edit post-go ⇒ that card's dispatch requires confirm with
  `manifest-stale` + diff; the rest of the batch's cards keep going auto.
- **AC-4:** drain respects declared order + WIP-pause + refund on failure.
- **AC-5:** gate v2 pure with the full matrix tested (human/agent × grant
  live/dead × stamp valid/stale/absent).
- **AC-6:** shadow log records the manifest, the go, each dispatch and each
  invalidation.
- **AC-7:** capy-features v9 (the agent learns: "assemble a manifest with
  `submit_manifest`; editing post-go drops the stamp") + CHANGELOG + design.md §6
  - i18n.

## 5. Out of scope

Auto-manifest (orchestrator self-approving a batch — never) · cross-repo manifest
(v1: one manifest = one board; cross-repo = N manifests) · automatic re-approve
after a "trivial" edit (there's no such thing as a trivial edit in a boot prompt) ·
drain scheduling/cron.
