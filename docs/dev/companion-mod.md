# The companion mod: layout, authoring rules and the test harness

The companion is a small Claude Code **mod** (a plugin of function hooks) that Harnu loads into every
`claude` session it spawns, with a second `--plugin-dir`. It is the **sensor** of epic T389. Specs:
`docs/specs/T389-companion-mod/` (this page is the working summary of P1W2). The skeleton registers
one pass-through `session.start` and makes no network call; with the default mode `off` a spawn's
argv and env are byte-identical to before.

## Layout

```
resources/companion/                 source of the plugin `harnu-companion`
  .claude-plugin/plugin.json         name, version (= the mod version), "types": "./types/index.d.ts"
  types/index.d.ts                   the plugin's contract: `interface PluginState` (each wave declares its keys)
  hooks/hooks.json                   { "modules": ["./register.ts"] }  (exactly one module)
  hooks/register.ts                  the hooks module; EVERY function that takes `$` is declared here
  hooks/contract.ts                  wire types and constants, zero imports (P1W1)
  hooks/coords.gen.ts                GENERATED by staging, gitignored, never hand-edited
  hooks/lib/*.ts                     `$`-free pure helpers; relative imports only
  hooks/lib/secret-rules.gen.ts      GENERATED from secret-rules.json (checked in, staged): the wire redaction's rules
  secret-rules.json                  the ONE source of those rules (a copy of T450's table; not staged)
  api-surface.json                   the checked-in surface manifest (hooks, `$` calls, env reads, state keys)
  tests/*.test.ts                    `claude plugin test` suites (import `claude-code/testing`)
  .gitignore                         not staged
  tsconfig.json                      NOT checked in: the engine lays it (next to .claude-plugin/types/) on load
src/main/companion/                  staging-core (pure), staging (fs), version-gate, spawn-inject, sideload-retry-core
scripts/ci/mod-step.mjs              the `mod` step; render-coords.mjs is the twin of `renderCoords`
scripts/ci/render-secret-rules.mjs   renders secret-rules.gen.ts (`--check`: fail when it is stale)
tests/cli/                           real-`claude` suites; support/{fake-host,run-claude}.ts; fixtures/probe-mod
```

Staging copies only the allowlist (`.claude-plugin/plugin.json`, `types/`, `hooks/`) into
`<userData>/companion/<stageKey>/harnu-companion/`, with `hooks/coords.gen.ts` rendered from the data
directory. A staged tree is **never rewritten**: a write would hot-reload the mod in every live
session. A changed source or coordinate stages a sibling `<modVersion>.<hash8>` instead, and the
tree is re-hashed on every spawn. `ensureStaged()` is the one function other code calls for the
directory.

## The runtime (P1W3)

`hooks/register.ts` holds the handshake: `ensureHello($)` (lazy, idempotent, single flight, bounded by
`HELLO_WAIT_MS`), the event ring and its pump, the heartbeat, the re-hello after a reload or a `STALE_CONN`, the
rebound rules and `bye`. Helpers other waves call, all declared at the top of the module: `ensureHello($)`,
`emit($, event)`, `enabled(feature)`, `boundSid()` and `reportModError(where, err, cmd?)`.
`reportModError` takes no `$`: `$` may not be stored in a module variable (`claude plugin validate` refuses it),
so the event goes into the ring and the next pump or heartbeat sends it. Pure helpers live in `hooks/lib/`
(`ring.ts`, `rendezvous-parse.ts`). The L3 tests (`resources/companion/tests/*.test.ts`) run against a scripted
host from `tests/support/rig.ts`: a held clock, an in-memory `$.state`, the rendezvous file and `$.http.fetch`
answered by a script. The L4 suite `tests/cli/handshake.cli.test.ts` runs a real `claude` against the real host.

## Authoring rules that make a module silently not load

Hot reload and a bad module look alike from the terminal: the CLI runs without the mod and says
nothing (one stderr line under `-p`). The first three are enforced by `claude plugin validate`, the
rest by `tests/companion/api-surface.test.ts` on the source.

- `$` is passed only to functions declared **at the top of `register.ts`**. A `$` handed to a helper in
  another file makes the module not load. Helpers under `hooks/lib/` are `$`-free.
- `$.env.get` takes a **literal** name. `$.state` keys are declared in `types/index.d.ts`.
- JSX needs `.tsx`. No bundler: relative imports only, inside `hooks/` or `types/` (tests, fixtures
  and `api-surface.json` are never staged). `hooks/contract.ts` has no imports at all.
- No `tool.call` hook whose matcher can match `Bash` (it breaks `Agent(isolation: "worktree")`,
  #92533). No `'*'` event, no `turn.step`, no `$.process`, no `$.mcp.call`.
- Every hook returns `next(e)` on failure and never spins (a hook that blocks 5 s is unloaded).
- The source scan reads a bare `$` anywhere outside a string or comment of a `hooks/lib/` file as a
  use of the engine interface, regex literals included: spell an end-of-input anchor
  `(?![\s\S])` there.

## The live row (T455 W1, `sense.row`)

The mod folds every row the conversation keeps (`session.append`, the row **as stored**, so a
rewriting mod beneath such as T450's scrubber is honoured) into a compact row and sends it as
`session.row`. Spec: `docs/specs/T455-live-sidebar-from-session-append/` (`00-spec.md` §5, with the
amendments of `04-w0-findings.md` §8). Host side: T455 W2; until it lands no host enables
`sense.row`, so the mod folds in memory and sends nothing.

- `hooks/lib/row-fold.ts` is the pure fold: first and last prompt, last assistant text, title, tool
  calls (main loop and subagents apart), user rows, last row time and uuid. `lastPrompt` takes only
  `composer` rows (a typed prompt, a typed slash command); every other origin is skipped, and the
  ones never observed (`bridge`, `plugin`, `sdk`, …) are skipped by default and untested. A `claude
-p` prompt is one of them, so a headless session sends `lastPrompt: null`. `firstPrompt` mirrors
  the legacy reader's header scan (`claude-reader.ts`), so it carries what the reader shows.
- `hooks/lib/redact-wire.ts` runs every text through T450's deterministic rules before it leaves
  the fold. To change a rule, edit `secret-rules.json` and run `node
scripts/ci/render-secret-rules.mjs`; `tests/companion/secret-rules-staged.test.ts` fails on a stale
  or diverging copy. Until T450 lands, the source lives here and T450 adopts it.
- The coalescer is one `$.clock.after` at a time (`ROW_DEBOUNCE_MS` trailing, `ROW_MAX_WAIT_MS`
  max), plus immediate flushes at `session.start`, a main-loop `turn.complete`, after a hello, a
  resync, a `flush` and a rebound. An unchanged row is not sent again.
- `$.state` key `row` holds counts only: any co-loaded mod can read `$.state`.
- `classic.SessionStart` records `{ source, transcriptPath }` before its first await, because the
  engine starts `session.start` before that handler gets there (W0 M8). The hello's snapshot carries
  it as `start`; when the hello went out first, a `probe` snapshot follows with it.
- Every text is bounded twice before it ships. The row's raw text is cut at `RAW_MAX` (64 KiB) on a
  whole word before any parsing; the wrapper scans are linear `indexOf` loops, not lazy regexes, so
  a 1 MB row of unclosed tags folds in milliseconds (a lazy regex took 2–26 s, and a hook that
  blocks 5 s is unloaded). Then redaction runs on `REDACT_WINDOW` (8 KiB), cut on a whole word too:
  a token the cut would split is dropped whole, so nothing past the window ever ships, however much
  redaction shrinks what precedes it. A text with no word boundary to cut at is withheld (`null`).
- Where the bounds make the first prompt differ from the legacy reader (which reads a line under
  its 2 MiB head cap and shows the first 120 characters):
  - **one first word longer than 8 KiB** (or longer than 64 KiB in the raw text), even well under
    the raw cap: the mod sends `null`, the reader shows the word's start;
  - **a row the raw cap cuts so that what it keeps reads as meta-only or leaves a meta wrapper
    open** (`<system-reminder>`, `<command-message>`, `<command-args>`, `<local-command-stdout>`,
    `<local-command-caveat>`): the mod sends `null` and still counts that row as the first, so the
    next row is never taken in its place; the reader strips the wrapper and shows the text past
    the cut. Three shapes are pinned by tests: a wrapper closing just before the cut with the
    prompt's first word straddling it; a 60 KiB wrapper followed by 8 KiB of newlines, then the
    prompt; a wrapper ending at the cut with a second one opening past it. A wrapper that is never
    closed in a row over `RAW_MAX` gives `null` too (the reader would show the raw tag text): the
    same harmless `null` class;
  - **a `<command-name>` first appearing past `RAW_MAX`**: no divergence, the mod looks for the
    command name in the whole text (one linear scan) and names the command as the reader does.
    A W2 parity rule can class the first two as explained: in both the mod's value is `null`,
    never another row's text and never a wrapper's content. Below the cap nothing is withheld for
    a wrapper: a short prompt that merely contains a literal, unclosed tag keeps its text, as the
    reader's does.
- Overlapping rule matches are merged and the union is redacted under the rule that matched first.
  T450's `detect` skips the later match instead, which leaves the rest of a larger secret raw; the
  merge is a deliberate hardening for T450 to adopt. The rule sources are T450's, unchanged.
- Each text is capped at 240 16-bit code units AND `ROW_TEXT_MAX_BYTES` (300) UTF-8 bytes as JSON writes
  it, after control characters are stripped and lone surrogates replaced, so a `session.row` stays
  at or under ~1.5 KB in any script.
- The `classic.SessionStart` body runs the identity step (P1W3) in a block of its own; no T455 step
  can skip the rebound or the fleet reset.

### Known engine effect: hooking `attachment` rows slows a subagent

A `session.append` hook routes every row its matcher takes through the module's worker before the
row is stored (the fold costs 0.3–1.8 ms per row, `03-prototype.md` §P.3), and that can shift a race
between loops. The reproducible case is `tests/cli/fleet-state.cli.test.ts` › "teammate is not a
subagent" (`claude -p`, a scripted endpoint, one `Agent` call whose subagent answers at once). With a
hook on every door, a bare `($, e, next) => next(e)` included, it fails 3 of 3; with no hook it passes
3 of 3. Hooking one door at a time, only `attachment` reproduces it (a bare `{ door: 'attachment' }`
fails 3 of 3; `response` alone and `tool-result` alone pass):

- without the hook: `turn.started → subagent.started → subagent.stopped → turn.completed (sub) →
turn.completed (main, backgroundSubagents 0) → turn.started → turn.completed (main, 0)`;
- with it: `turn.started → subagent.started → turn.completed (main, backgroundSubagents 1) →
subagent.stopped → turn.completed (sub) → turn.started → turn.completed (main, 0)`.

With the hook on attachments, the subagent finishes a few ms after the main turn ends instead of
before it. The order the mod reports is the engine's: the subagent really was still running. The taskState map then does what
D12 prescribes. A main `turn.completed` with `backgroundSubagents > 0` holds 'working' (`heldIdle`),
and the last `subagent.stopped` releases it with a Stop. The companion's shadow fold is therefore
'working' for as long as the subagent outlives the turn (milliseconds here), where it went idle
before. A legacy fold that idles at the main Stop disagrees for that window: parity noise of the
same kind every long background subagent already produces. A subagent that runs for minutes outlives
the turn with or without the hook, so only near-simultaneous endings change. The stuck timer is
not reached in a window of milliseconds.

**What the registration does about it.** The one `session.append` registration takes every door
but `attachment` (a `door` array: `prompt`, `command`, `response`, `tool-result`, `tool-message`,
`delivery`, `hook-context`, `note`, `compaction`, `notice`). With it the CLI suite passes 3 of 3 (and
the handshake suite 8 of 8). An earlier attempt with a RegExp `door` matcher failed like the
all-doors hook, consistent with a RegExp not narrowing that key.

**Its cost.** The fold reads nothing from an attachment but its uuid and time, so attachments no
longer move `lastUuid` or `lastRowAt`. Both stop at the last non-attachment row:

- **Alignment.** `lastUuid` is still a row of the transcript, but it can sit behind the file's
  last row (attachments the engine adds right after a prompt or a tool result, until the next
  response). **The host's alignment (W2) must therefore treat a `lastUuid` BEHIND the file's tail
  as "not yet aligned", exactly as spec M1 treats one ABSENT from the file**: never a divergence.
  The next non-attachment row realigns it.
- **Activity.** `lastRowAt` can lag the file's mtime by the time between that row and the trailing
  attachments, normally milliseconds (they are written in the same burst), inside the activity
  group's ±2,500 ms match window. A long stretch in which the engine appends only attachments
  would show as a later `modified` in the legacy value; none was observed.
- Counts, prompts and the assistant text are unaffected: an attachment is never a user row (its
  type is `attachment`) and carries no prompt.

**Doors the engine adds later.** The fold reads only the doors in `FOLDED_DOORS` (`row-fold.ts`,
also the registration's matcher). CLI 2.1.299 appends a queued `claude -p` prompt on a new `queue`
door before `session.start` and never writes it (the prompt row that follows is the one the
transcript keeps); counting it would put `userRows` one above the transcript. The engine raises
that row only when a registration matches `{ door: 'queue' }` (its code checks for one first), and
the `door` array does not name it, so it does not reach the hook; a verifier's four runs with the
array saw none. The fold's own skip of any door it does not know is defence in depth for a door a
later CLI adds. (One run of mine counted such a row; it was not reproduced, and the array alone
accounts for the verifier's result.)

Tests: `resources/companion/tests/row.test.ts` (the kit, with the golden traces of
`tests/fixtures/row-traces.ts`), and in `npm test` `tests/companion/row-fold.test.ts`,
`redact-wire.test.ts`, `row-hook.test.ts` (the real `register()` under a fake engine: ordering and
fail open) and `row-host-compat.test.ts` (the W1 events against the current host). Every row in
them is synthetic, and every token in the redaction tests is built at runtime.

## Running the checks

```bash
# unit tests: staging, version gate, retry, scanner, notes parser, mod-step
npm test

# the `mod` step: `claude plugin validate --strict --json` and `claude plugin test`, offline,
# in a temp copy with generated coordinates; fails if `claude` is missing or older than minCli
node scripts/ci/mod-step.mjs

# the whole pipeline; `mod` runs after `lint`. `--skip mod` is recorded as `skipped`, never as a pass.
scripts/ci/local-pipeline.sh --base <branch below> --labels no-changelog,no-user-docs

# real `claude` against the skeleton (hermetic: temp HOME, config dir and cwd; zero model calls)
scripts/ci/local-pipeline.sh --with-cli ...      # or: HARNU_WITH_CLI=1 npx vitest run tests/cli
```

`mod` exits `3` (state `blocked-by-policy`, a **failing** step) when the validate output says hooks
modules are turned off by policy. `--with-cli` needs no sign-in: the zero-model driver
(`tests/cli/fixtures/probe-mod`, command `/harnu-probe`) answers from `command.run`, and a run that
needs one fails as `blocked-by-auth`. No credential is ever copied into the temp HOME.

## Developing the mod with hot reload

Launch an **unpackaged** Harnu with `HARNU_COMPANION_DEV=1`: `ensureStaged()` then returns
`resources/companion/` itself and writes the gitignored `hooks/coords.gen.ts` once, so editing a hook
reloads it in every live session of that instance within about a second. The variable is ignored in
a packaged build. Two instances must not share the folder: a lock file (`resources/companion/.dev-lock`
holding the owner's pid) makes the second one log a warning and stage normally.

## The tested CLI window and how to move it

`api-surface.json` holds `minCli` (2.1.287) and `lastVerifiedCli` (the tested ceiling, 2.1.292). Below
`minCli`, or with the version unknown, Harnu injects nothing. Above the ceiling it injects and the
session is forced to `shadow` (P1W4). To move the ceiling, change `lastVerifiedCli` by hand in a PR
of its own, and attach: the `mod` step log, the `--with-cli` log (both print `claude --version`) and
recipe LV-P1W2-a on the new version. The three drift checks are: way 1 the static scan in
`npm test`, way 2 the validate notes in the `mod` step, way 3 `tsc` against the types the engine
writes after a real load (`--with-cli`).

## Relation to the host (P1W1)

The spawn path talks to P1W1's host only through `companionHost.mintSpawnToken(meta)` /
`releaseSpawn(owner, reason)` / `spawnRecord(owner)`, `getCompanionMode()` and the `SpawnOwner` /
`TrustClass` types. With the mode `off` none of them is called. To watch the ledger from a live
instance use `window.api.companionDiagnostics()` (`pendingSpawns` is 1 while a minted token has not
been released, 0 after the PTY exits); see `live-verify-second-instance.md`.

## The Harnu mod state, the probe and the kill switch (P1W4)

`companion-prefs.json` (in `<userData>`) holds the kill switch (`enabled`), the per-family modes (`families`), the
developer default (`mode`), the ramp escape hatch (`allFolders`) and the feature keys (`keys`); only overrides are
written, and the shipped default is `shadow` for every family behind the one-time notice. `projects.json` carries the
per-folder ramp (`companionActive`). `parity/<stream>.ndjson` under `<userData>/companion/` is the persisted parity
ledger; `scripts/dev/companion-parity-export.mjs --user-data <dir> --stream <name>` turns it into a scrubbed fixture.

To drive an isolated instance from a recipe, launch `electron <repo>` (the repository as the app path), not
`electron out/main/index.js`: with the latter `app.getAppPath()` is `out/main` and the mod cannot be staged. Rebuild
with `npx electron-vite build` after a main-process change, because the instance runs `out/`.

`claude-policy-probe.ts` runs `claude plugin test <staged dir>` once per boot and CLI binary, lazily, and only when a
spawn carried the mod and never said hello; `classifyPolicyProbe` maps its output (smoke addendum §15.1). In dev mode
the staged directory is the repository folder, whose `tests/` the probe would run when mods load.
