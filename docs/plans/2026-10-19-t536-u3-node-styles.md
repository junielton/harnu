# T536 U3 — Node styles and the properties panel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the operator colour and style canvas nodes (P1–P6: tone, stroke style, stroke width, corners, text size and align, opacity) from a floating properties panel, and let the agent set the same styles through a merging `style` field on `draw_canvas`, without any board losing data in this build or the previous release.

**Architecture:** Style lives in one nested object, `node.props.style`, holding fixed enum values only, never colours. The agent catalog in `src/main/mcp/canvas-shapes.ts` declares, per shape, which style keys it takes and their allowed values. `canvas-ops.ts` validates a new `style` op field against that table and merges it per key. A new pure renderer module, `canvas/canvas-style.ts`, mirrors the table (a parity test pins the two together) and turns a style into X6 attrs through palette tokens. `toX6Node` applies the style, so a theme switch, which already re-renders from the working state, recolours styled nodes for free. In the pane, the style is the only thing written to history: attrs are re-derived from `data` on every `cell:change:data` and kept out of the undo stack, so undo after a theme switch never brings back the old theme's colours. A new presentational `CanvasPropertiesPanel.vue` shows the controls the selected nodes share.

**Tech Stack:** Vue 3 + TypeScript, AntV X6 core `2.19.2` + 2.x plugins (pinned, do not upgrade), vitest + jsdom, Playwright `_electron`, lucide-vue-next 1.0.0 icons. **Depends on:** U1 and U2 merged (`CanvasToolbar.vue`, `canvas-tools.ts`, ellipse/diamond kinds, `toolbarOwnRow`).

**Spec:** `docs/specs/2026-10-19-t536-canvas-toolbar.md` (in the repo since U1). §3 (C1–C6), §7.0, §7.1, §7.2, §7.4, §7.5, §7.6, §9.3 item 9, §9.4, §9.5.

## Global Constraints

- Everything in U1's and U2's Global Constraints still holds (no new npm dependency, no X6 upgrade, tokens only, `$t()` with keys in **both** `en.json` and `pt-BR.json`, English everywhere outside i18n files, focus-gated shortcuts).
- **No schema version bump, and `src/main/canvas-core.ts` is not modified in U3.** That keeps the existing reader (the one the previous release ships) as the thing every compatibility test runs against (C1, C3).

- **Style only in `node.props.style`** (spec §7.5). No new top-level node key. No style key loose beside a shape's own props.
- **Tone names only, never colour values, in the file and in every component** (C5). Every colour comes from `CanvasPalette`, which reads existing §9 tokens. **No new §9 token**: the six tones fit the tokens already in `themes.css` (`--color-warning-soft` included).
- `design.md` is edited **before** the code that implements it (Task 1).
- **Agent parity (C6):** every key and value the panel can write is in the `draw_canvas` catalog in the same PR; `docs/harnu-features.md` updated and its `<!-- harnu-features vN -->` marker bumped (v96 at U2's head, so v97 unless main has moved; take the next number at rebase); `docs/user/agent-control.md` updated. ## Review Focus

The five failure modes most likely to bite a user that no existing test covers. Each has a test in its owning task.

1. **Undo after a theme switch paints the old theme's colours.** If the attrs a style change writes enter the undo stack, ⌘Z after a theme switch restores colours resolved for the previous theme. Test in Task 5.
2. **An agent edit silently wipes the operator's colour.** `update_node` `props` replaces the whole object; a `props: { src }` on a styled image must keep `props.style`. Test in Task 2.
3. **A board carrying a style value this build does not know** (`tone: "purple"`, `fontSize: 40`, `style: "red"`, an extra key from a newer build) must still open, draw the default, and survive a Save byte-for-byte. Test in Task 3.
4. **A mixed selection applies a key to a node that does not take it.** A rubberband catches edges and nodes of several kinds; the panel must show only the keys every selected node takes, ignore edges, and never write `corners` onto an ellipse or anything onto a mockup card. Test in Task 5.
5. **Using the panel disturbs the board.** A click on a swatch must keep the selection, start no rubberband, and leave the pane clean when the clicked value is already active; `Space` on a focused panel button must not pan. Test in Task 5.

  Rules: `OP_KEYS.add_node` and `.update_node` gain `'style'`; `update_node`'s "at least one field" list gains `'style'`. `style` must be a non-empty plain object (`BAD_ARGS` when empty, `BAD_PROPS` when not an object). A key the shape does not declare is `BAD_PROPS` naming the keys it takes ("takes no style" for an empty table). A value outside the key's list, including the wrong JSON type (`"50"` for opacity), is `BAD_PROPS` listing the allowed values. `null` is always allowed and removes the key. **A value equal to the key's default also removes it**, so a reset node is byte-identical to one never styled. Keys already in the file and not named in the patch are kept verbatim, even ones this build does not know. An empty `style` is deleted; `props` is deleted only if it became empty because of that. `checkProps` refuses a `style` key inside `props` with `BAD_PROPS` and the hint `set it with the "style" field, which merges per key`. **`update_node` `props` replace keeps the node's existing `props.style`**: the new `props` is the checked object plus the old `style`. Style is applied after `props` within the same op.

## Open points

Decisions this plan makes where the spec is silent or disagrees with itself or the code. Each becomes an "Implementation notes (U3)" entry in the spec if the PR keeps it.

1. **`props.tone` or `props.style.tone`.** §7.1's table says `node props.tone`, `props.stroke` …; §7.5 says one nested `props.style`. The plan follows §7.5, because it is the later and reasoned rule (it survives `update_node`'s replace).
2. **Text tone.** §7.2's Label column is `--text` for four of the six tones, so with "label colour only" (§7.6) a coloured text node would not change colour. Call: a text node's label takes the Stroke column (`default` keeps today's `--text-2`, `muted` `--text-3`).
3. **Edges in the selection.** §7.4 says "controls that apply to every selected element". Edges take nothing until U5, so read literally, every rubberband that catches an arrow would hide the panel. Call: U3 ignores selected edges; an edge-only selection shows no panel.
4. **Value spellings the spec leaves open:** `align` is `left|center|right` (US spelling, which matches CSS and SVG; the spec says "centre"); `fontSize` is `s|m|l|xl` = 11/12/15/20px, with M = today's 12px so no existing board changes; `opacity` is the JSON numbers 25/50/75/100; `strokeWidth` is 1/1.5/2.5px with regular = today's 1.5.
5. **Default equals absent.** Setting a key to `null` **or to its default** removes it, on both the verb and the pane, so a node styled and then reset is byte-identical to one never styled.
6. **Translucent soft fills.** `--*-soft` tokens are 10–18% alpha, so the dot grid and an edge under a tinted node show through. Accepted, and checked live in both themes. An opaque ground layer is a follow-up only if the matrix shows it hurts legibility.
7. **Dashed versus unknown.** A user-dashed box could read as the dashed "unknown kind" fallback (`4 3`). Call: dashed is `6 4`, and unknown kinds ignore style, so the fallback stays plain.
8. **Older builds.** C3 holds for open and Save. But an _older_ build's agent `update_node` with `props` still replaces the whole object and drops `props.style`; only this build's verb keeps it. Documented, not fixable from here.
9. **ACK scope.** The ACK gains `shapes[].style` only. It does not also start listing `props` keys, although it never has; that is out of U3's scope.
10. **Undo after a theme switch** (spec silent). Attrs are derived from `data` and kept out of history through X6 History's `beforeAddCommand`, so ⌘Z restores the style, not stale colours.
