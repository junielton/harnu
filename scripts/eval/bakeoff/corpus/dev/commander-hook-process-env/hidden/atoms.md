| id   | requirement                                                                                                                                                                                                 |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-1  | There is a supported way to run user code before a subcommand processes its environment-backed options, so that `process.env` values set by that code are seen by the subcommand's `Option.env()`.          |
| R-2  | The user code can read the parent command's already parsed options, such as the path of the env file given by a program-level option or its default.                                                        |
| R-3  | The mechanism works for programs using `enablePositionalOptions`, with program options before the subcommand name.                                                                                          |
| R-4  | The user code can be asynchronous, as in the request's example, and the environment it sets is still seen by the subcommand.                                                                                |
| O-1  | The feature is a `preSubcommand` event on the existing `.hook()` method, which returns the command for chaining, still throws for unrecognised events, and is added to the `HookEvent` type in the typings. |
| O-2  | The listener receives `(thisCommand, subcommand)`: the command owning the hook and the direct subcommand about to run.                                                                                      |
| O-3  | The listener runs after the owning command has processed its own options and before the subcommand processes any of its CLI or environment options.                                                         |
| O-4  | The hook fires only for direct subcommands of the command it is added to, is not inherited, and with nested subcommands each level's hook fires once, outermost first.                                      |
| O-5  | Several `preSubcommand` listeners on one command run in the order they were added.                                                                                                                          |
| O-6  | Async listeners are awaited in sequence with `.parseAsync()` before the subcommand starts; synchronous listeners work with `.parse()` and the subcommand runs synchronously.                                |
| O-7  | A listener that throws or rejects propagates the failure out of `.parse()` or `.parseAsync()`, and the subcommand does not run.                                                                             |
| O-8  | The hook fires for a subcommand dispatched by name, by alias (passing the real subcommand), as a default command, and for a stand-alone executable subcommand before the process is spawned.                |
| O-9  | The hook does not fire when no subcommand is dispatched: the command runs its own action, no subcommand was given, or the name is not a known subcommand.                                                   |
| O-10 | `preSubcommand` runs before the subcommand's `preAction`, action and `postAction`, and the existing action hooks are unchanged.                                                                             |
| O-11 | Option precedence is unchanged: CLI beats environment, environment beats default, and a value from the environment has source `env` and goes through the option's custom parser.                            |
