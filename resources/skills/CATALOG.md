# Harnu bundled skills

The skills Harnu ships with the app. This directory is a valid Claude Code plugin
tree (`.claude-plugin/plugin.json` + `skills/<name>/SKILL.md`); Harnu stages the
**enabled** subset into its own userData directory and passes it to a spawned
session as `--plugin-dir`. A skill that is switched off is simply not staged, so
the session cannot see it even in principle.

Inside a session the skills arrive namespaced under the plugin name — a bundled
`mission` is invoked as `harnu:mission`. Personal skills of the same name are
never shadowed, renamed or removed; both are offered.

The marker comment on the first line is the **catalog version**. Bump it (`vN` →
`vN+1`) whenever the content of any shipped `SKILL.md` changes — `bundled-skills.ts`
parses it into `BUNDLED_SKILLS_VERSION` and compares it against the staged
`.stamp` to decide whether a folder's staged copy must be rewritten after an app
update. Individual skills are not independently versioned: the catalog moves with
the app release.

Everything under this directory is English-only (`CLAUDE.md` → Language policy)
and model-facing. In particular, each `SKILL.md`'s `description` is both the
CLI's trigger text **and** the one-line purpose the Settings → Skills panel
renders, so it is deliberately not translated.

| `orchestrate-delivery` | Plan an objective as a Harnu mission of milestones and steps, dispatch one session per step, have a second session settle every criterion, and hand the operator a report, for an objective too large for one session ("orchestrate this", "break this down and dispatch it", "deliver this epic") and never to implement one unit yourself, review a PR or merge                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

| `status`               | Render the state of every feature, task or mission in flight as a fixed six-line glance card — progress bar per front, what is running now, what is done, what is next, what needs the operator, what is open — built from mission_list, mission_get, the board and the PRs, never from memory; use it whenever the operator asks "status?", "where are we", "is it done", "what's left", "what do you need from me" or "how's the mission", when they return after being away, and as the header of every report-back, mission tick and delivery report.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `read-aloud`           | Speak a short, ear-friendly summary of a result — the `speak` verb inside Harnu, a TTS command outside it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `report-back`          | The shared final-report format for any multi-step run: a flat rail of executed steps (✓/-/!/✗ with concrete outcomes), a gutter ledger for what is owed (`you` — always printed, `— nothing, you're clear` when nothing is) and any open question, a links list of everything the reader might open, and a summary of at most 3 lines. Use it whenever a task involved a pipeline or several sequential steps and you're about to write the wrap-up message — shipping a PR, reconciling branches, a deploy, a batch of file changes, a scaffold — or whenever the operator asks 'what did you do?', 'summarize what was done', 'where is the report?', or complains a final summary was a wall of prose. Other pipeline skills reference this as their output contract. Do NOT use for simple Q&A — a question gets a direct answer, not a report.                                                                                                                                                                                    |
| `draft-to-prompt`      | Transform a rough idea, voice-note-style draft, or vague request into a production-quality prompt for Claude models (Haiku, Sonnet, Opus, Fable 5). Also use it when the user wants a boot prompt for a new session, worktree, or dispatched agent.                                                                                                                                                                                                                                                                                                                                                                                              |
| `one-by-one`           | Drain a pile of open decisions one question at a time, and write every answer where it lasts. Reads the spec's Open decisions table (the `D-n` rows) or a wall of open questions, serves ONE decision per message with a recommendation, and after each answer marks that row `resolved` in the spec (chosen option, date), appends one structured line to project memory `decisions`, and logs it on the mission when a step is gated by it (an open one that gates a step is an operator blocker, and only the operator clears it). Use when the operator says '/one-by-one', 'one by one', 'one at a time', 'um por vez', 'vamos por partes', or reacts to a dense message with 'this is too much'; also when a spec has open D-n rows, or when you are about to send more than ~5 questions at once. Do NOT use to walk the operator through executing manual actions (step-by-step), to stress-test a plan with questions you generate (grill-me), or for a plain summary — this skill resolves decisions, it never decides them. |
| `grill-me`             | The operator's stress test of a spec or plan, between draft and approval. Interviews the operator relentlessly, one question at a time with a recommended answer, walking the design tree branch by branch — and every question that survives lands somewhere visible in the spec: a `D-n` row in Open decisions, an `## Amendments` row, or a non-goal. Ends with a list of what it wrote and what it could not place. Use when the operator says '/grill-me', 'grill me', 'stress-test this plan', 'poke holes in this spec', 'me questiona', or wants a plan challenged before anything is built. Do NOT use to resolve decisions that already exist in a spec (one-by-one), to walk through manual actions (step-by-step), or to start implementing — the plan is not enacted until the operator says the understanding is shared.                                                                                                                                                                                                 |
| `step-by-step`         | Walk the operator through a list of manual actions only they can perform — dashboard clicks, commands on a machine the agent cannot reach, secrets to create, DNS to point, a release to cut — one step per message, and record each action as an operator criterion on the relevant Mission step so the list survives the session. Criteria are added with `mission_add_ac` (`by: 'operator'`); the skill reports which remain open and never settles one itself (the operator ticks them in the Mission pane). Use when the operator says '/step-by-step', 'walk me through this', 'guide me step by step', or reacts to a 'pending with you' list by asking how to do it. Do NOT use to resolve decisions (one-by-one), to stress-test a plan (grill-me), for a fixed runbook of a known procedure, or when the agent can run the actions itself — then just do them.                                                                                                                                                               |
| `spec`                 | Called at every entry, before any work starts, and most calls end Small: it names the door the operator came in by and the tier, in one message, and a Small entry (a one-line bug, a PR comment, a red CI, a question) gets its first step with no file, no mission and no tool call. Only Medium, Large and Complex work goes on to a spec at `docs/specs/YYYY-MM-DD-<slug>/spec.md`. Two verbs: `/harnu:spec <entry>` (triage, then authoring above Small) and `/harnu:spec check [--cards]` (runs the checker staged with this skill: the spec gate's rules, capability order, request-atom coverage and, with `--cards`, card-versus-spec drift; works in any repo). Use at the start of any task, ticket, bug, question, PR comment, red CI, design or vague idea — 'spec this', 'how big is this?', 'triage this', 'check the spec', 'lint the cards against the spec'. Do NOT use to dispatch cards (orchestrate-delivery), to grade acceptance criteria (delivery-verifier) or to drain open decisions (one-by-one).          |
| `your-move`            | Tell the operator, in a card they can act on, the moment a turn leaves something only they can unblock. Applies the end-of-turn test, picks one of five kinds (decide, go_no_go, provide, do, check), writes the card so it makes sense with no other context, and files it with the `your_move` verb when that is available. Use at the end of any turn where you stop to ask, park on an approval, hand off a manual step, or hit a blocker nobody else can clear, and whenever a question raised earlier is still open after you moved on to other work. Do NOT use for a tool permission (that stays in the Approval Inbox), for a question you can settle by reading the code or the docs, for work another agent or a running process will finish by itself, or to close or dismiss a card — no agent can.                                                                                                                                                                                                                       |

## Features

A feature is switched on and off in the same panel, but it is not a skill: nothing
under `features/<name>/` is staged as a `SKILL.md`. `FEATURE.md` carries the
`name` and `description` the panel renders; `bundled-skills.ts` decides what the
feature adds to the staged plugin. A feature is never a worker `/mention` and has
no "Also outside Harnu" install.

| Feature      | What it stages                                                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `doc-reader` | `agents/doc-reader.md` (Haiku, `Read, Grep, Glob`) and a `PreToolUse` http hook on `Read\|Bash` to the Hook Bridge read gate. Never staged into an `observe` tick or a steward. |
